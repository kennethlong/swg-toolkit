## 3. Six defects found by live checkpoints — none by any automated gate

This is the headline. 692 passing tests, a plan checker, and 13 cross-AI review rounds caught none of
these. Two had sat in `overlay.cpp` for weeks.

1. **Esc key toggled the game's settings menu** (`2ec00e3`). Structural: SWG polls input via
   **DirectInput, not the Win32 queue**, so `hkWndProc` cannot consume a keystroke. Sketch 020-A only
   ever specified Esc as a BUTTON (`im-btn`), not a KEY (`im-key`) — removing the binding moved the
   implementation *closer* to the sketch. **Known limitation: no overlay key can be claimed
   exclusively on this client without engine-side DirectInput arbitration; F/G/R double-fire too.**
2. **Stale pre-shim building-id fallback** (`cb6f369`). `armDecorationEdit` fell back to the picked
   object's OWN id when `getContainingBuildingId` returned 0 — a workaround whose own comment said
   *"until the provider ships it"*, and the provider shipped it (v25) on 07-30. Everything was armable
   including buildings viewed from outside, and the refusal path was unreachable.
3. **Re-entrant `loadScene` FATAL'd the client** → caused Plan 16. Draining outside Present was
   NECESSARY BUT NOT SUFFICIENT; the fix is Utinni's **two-frame** state machine
   (`game.cpp:499-554`). The discriminator that cracked it: it crashed in-world but SUCCEEDED from the
   login screen, where there is no player/scene to release.
4. **No scene-change pointer invalidation existed anywhere** (`eb54583`, `879e4f8`). Borrowed
   `Object*`s were nulled only at declaration. Leading candidate for the 3,424-fault HUD-blank run.
5. **Live Inspector missing from the default layout** (`68332bc`, LAYOUT_VERSION 5→6). The
   launch/attach panel had never been in `buildInitialLayout`; 05.1-10's 4→5 bump wiped it from saved

  picks a route, never sees a container, and is never refused for standing in the wrong place. The
  editor resolves the container and picks `.ilf` vs `.ws` itself.

## 5. ⚠ TWO BLOCKERS FOR WAVE 3

### 5a. Plan 12's checkpoint step is misleading as written — FIX BEFORE EXECUTING

`.planning/todos/pending/reload-scene-is-lossy.md`: **"Reload current scene" leaves the world
degraded.** Verified live — the cantina was GONE, collision was gone (ran through walls up to NPCs
known to be behind them), snapshot creatures missing. Everything returned AT ONCE after moving around.
NPCs were unaffected (server-streamed). A buildout-vs-authored hypothesis is RULED OUT — the banthas
returned in the same instant as the buildings.

Mechanism: our reload is only `wsUnloadSnapshot()` + `wsLoad()`. Utinni binds spatial-subdivision
handles, `removeFromWorld`, `unload` and `clearPreloadList` that we never call, and records its own
note that *"unload resets the sticky ms_sceneName so reload isn't empty"*.

**Impact:** Plan 12's ADD checkpoint says *"Trigger 'Reload current scene'. Confirm exactly ONE
instance"*, and Plan 15 reloads to confirm rotation persisted. **A correctly-persisted object can read
as MISSING**, producing a false failure — or a "fix" to a non-bug. Reword those steps (use a full scene
load, or require moving around until the world re-registers) before running 12 or 15.

Secondary: post-reload, collision loss makes a placement click resolve to building id `0`, which now
correctly REFUSES. Right behavior, confusing symptom.

### 5b. Plan 11 inherits two teleport defects — decide how bookmarks handle them

`.planning/todos/pending/cell-aware-teleport.md` (TWO distinct defects in one file):

1. **Cell-aware teleport.** Teleport writes the world transform only and never reparents the player's
   cell (`object::setParentCell` advertised but UNBOUND), so teleporting INSIDE a POB renders the
   interior see-through. Confirmed from both directions: walking out the door repairs it, because
   crossing a portal makes the engine reassign the cell. **Extended 2026-08-02: a SCENE LOAD triggers
   it too — not teleport-specific.** Open question blocking a blind fix: whether the transform must
   become cell-relative (o2p) once reparented, given `getTransformO2P` exists for the read side.
2. **Stale player pointer after reload.** Intermittent "teleport does nothing". Instrumentation
   FALSIFIED both naive explanations (5/5 clicks registered, 5/5 writes landed, read-back matched,
   `getPlayer()` never null). Leading hypothesis: `getPlayer()` briefly returns the OLD freed player,
   so the write "succeeds" into freed memory and even instrumentation reports success. The trace to
   confirm it is already in the build. Note `object::isActive` is NOT the fix — calling it on freed
   memory is itself UB.

**Plan 11 builds D-07 teleport bookmarks. Bookmarking a spot inside a building you are decorating is
the primary use case and is exactly the broken one.** Decide whether bookmarks carry a cell reference
alongside x/y/z.
