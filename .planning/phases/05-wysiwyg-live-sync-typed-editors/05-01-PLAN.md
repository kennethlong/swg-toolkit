<objective>
Extend the existing Phase-3 seqlock read channel with a second, independent seqlock region in the
SAME named file-mapping that carries the toolkit-to-agent write command (D-02), and add the pure,
testable read-verify guard comparator the agent will use before applying any write (D-03) — now
covering transform AND scale independently, and carrying a real diagnostic address (REVIEWS.md Fix
B/C).

This plan is pure contract + native-core-adjacent (`packages/live-inject`) plumbing — no Win32 calls,
no rva_table/agent_main integration yet (that is 05-03), no host N-API export yet (that is 05-04). It
establishes the byte layout and the guard algorithm both later plans build on.

Purpose: LIVE-03 requires a zero-allocation, 60fps command path from the renderer into the injected
agent, and a fail-closed guard (SC #2) that never has a force-write escape hatch, but that DOES let an
explicit "Revert ALL" re-baseline itself (REVIEWS.md Opus MEDIUM finding) without ever accepting an
arbitrary forward write. Both must be correct at the byte level before any C++ agent logic consumes
them.

Output: Extended `LIVE_CHANNEL_LAYOUT` contract (320→396 bytes), extended `LiveState` struct + seqlock
helpers, and a new pure `write.h/.cpp` guard module with independent transform/scale gating.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Renderer (untrusted-by-convention JS) → shared file-mapping | The command region is written by host-process JS reachable from the renderer bundle; malformed or hostile values must not corrupt the read-frame region or crash the agent. |
| Shared file-mapping → injected agent (in-game process) | The agent trusts only its own locally-captured `expectedXform`/`expectedScale`, never an externally-asserted "this is fine" flag — the guard is the only gate, and `REBASELINE_GUARD` can only reset the baseline to the CURRENT live bytes, never accept an arbitrary forward-write target. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-05-01 | Tampering | channel.cpp channelWrite | mitigate | Byte count is the named `LIVE_READFRAME_BYTES` constant, not struct-size arithmetic — extending the struct can never silently widen the read-frame write span into the new command region (Task 1). |
| T-05-02 | Tampering | write.cpp checkWriteGuard | mitigate | Exact (not tolerance) float compare against the agent's own last-known-good transform AND scale, independently — any external change, however small, fails closed on that channel; no bypass path exists at this layer. |
| T-05-03 | Repudiation/DoS | channel.h struct evolution | mitigate | Six new `static_assert(offsetof(...))` lines catch any future accidental reordering/padding regression at compile time, mirroring the existing four asserts' proven pattern. |
| T-05-26 | Elevation of privilege | CMD_FLAG_REBASELINE_GUARD | mitigate | Rebaseline only ever sets the agent's expected-bytes state to bytes it reads itself from the live object THIS frame — it never accepts transform/scale values from the command payload as the new baseline, so it cannot be used to smuggle an unguarded forward write (REVIEWS.md Opus MEDIUM fix, implemented agent-side in 05-03). |
</threat_model>
