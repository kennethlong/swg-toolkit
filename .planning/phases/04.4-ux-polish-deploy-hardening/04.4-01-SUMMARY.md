# Phase 04.4 Plan 01: Delete/Restore/Undo Service Layer Summary

**`deleteProject()` service that restores the client via a newly-shared `deploymentReset.ts` (also used by `DeployDialog.handleReset`), parks the project into a crash-safe completion-marker trash protocol for session-scoped Undo, and wires a startup purge into `App.tsx`.**

## Accomplishments

- Extracted the record-shape restore dispatch from `DeployDialog.handleReset` into a shared
  `deploymentReset.ts` (`resetDeploymentFromRecord`) — eliminates the "two restore code paths
  for the same operation" risk the plan flagged; `DeployDialog.tsx` now delegates to it with
  unchanged (default) behavior.
- Implemented `deleteProject(projectFolder)`: restores the bound client (cfg-model or
  loose-model) via the shared dispatch with `cleanupArtifacts:false`, then parks the whole
  project (studioDir + umbrella folder) into `.trash/<entryId>/{studio,project}` behind a
  round-3 completion-marker protocol — the marker is written only after both renames succeed.
- Implemented `useDeleteUndoStore` (session-scoped Zustand): `restore(id)` guards against an
  occupied destination (throws, no partial rename, entry stays retryable) and
  `purgeStaleTrash()` removes only MARKED (provably complete) entries, leaving unmarked
  (crash-mid-park) entries on disk with a named warning.
- Wired `purgeStaleTrash()` into `App.tsx`'s mount effect, surfacing unmarked-entry warnings
  via `console.warn` plus a small, dismissible, non-blocking banner.
- Added `removeRecentProject` to `recentProjects.ts` and corrected its stale header comment
  (predated the 04.1-02 project/client decouple).

## Issues Encountered

None. One implementation subtlety worth recording for future readers: the persisted
`deployRecord` for a shadow-base deploy (via `updateChangesetDeployRecord`) is flattened into a
`CfgDeployRecord`-shaped object (no `shadowDir`/`patchEntry` fields) before being written to
`manifest.json` — so `deleteProject`'s cross-session read of that record takes the
`restoreCfg` primary path (byte-pristine whole-file restore) rather than the shadow-specific
`resetShadow` fallback. This is correct behavior for delete (the cfg ends up pristine either
way) and is a pre-existing limitation already documented in `shadowBaseService.ts`'s own
DEFERRED note (cross-session reset needs a discriminated-union persisted type) — not a gap
introduced by this plan.
