## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] `window.__testHooks` was never actually installed in any real Electron launch — `process.env['SWG_TEST_MODE']` is unreadable in the renderer**
- **Found during:** Task 1, first attempt to run the spec — `window.__testHooks !== undefined` assertion failed on every launch, with or without `SWG_TEST_MODE` set.
- **Issue:** `installTestHooks()` (04.4-09) gated on `process.env['SWG_TEST_MODE'] === '1'`. Empirically verified (direct-launch diagnostic scripts, several iterations) that this read is `undefined` inside the renderer's own page script even when Playwright's `electron.launch({ env })` correctly sets it for the Electron main process — Chromium renderer child processes do not inherit the full main-process environment.
- **Fix:** `main.ts` forwards the (main-process-verified) flag to the renderer via `webPreferences.additionalArguments: ['--swg-test-mode=1']`; `testHooks.ts` reads `process.argv.includes('--swg-test-mode=1')` instead of `process.env`.
- **Files modified:** `packages/renderer/src/testHooks.ts`, `packages/backend/src/main.ts`
- **Verification:** diagnostic Electron launch confirms `typeof window.__testHooks === 'object'`; spec's `hooksPresent` assertion passes in both scenarios.
- **Committed in:** `3b8f49d`

**2. [Rule 1 - Bug] Vite's client-build `process.env` stub broke `SWG_TEST_MODE` in main.ts AND `appDataRoot()`/`getStudioDir()` in the renderer — every project/studio path resolved as a RELATIVE path off cwd**
- **Found during:** Task 1 — Baseline-revert assertion failed inexplicably; traced to a persisted `deployRecord.snapshotPath` that was a *relative* string (`"swg-toolkit\\studios\\...\\snapshots\\swgemu.cfg.bak"`), confirmed by finding a real, junk `swg-toolkit/studios/` directory created next to the repo root during test runs.
- **Issue:** Vite's default client-build behavior statically replaces the bare `process.env` token with a build-time-empty object literal (verified via the built bundle: `var D={}` / `var xC={}` standing in for every `process.env.X` read). This affected `main.ts`'s own `SWG_TEST_MODE` gate (built via `vite.main.config.ts`) AND the renderer's `appDataRoot()` (`process.env['SWG_TOOLKIT_DATA_ROOT']` / `process.env['LOCALAPPDATA']`, built via `vite.renderer.config.ts`) — both silently fell through to their final `?? '.'`/no-op defaults.
- **Fix:** Added `define: {'process.env': 'process.env'}` to both `vite.main.config.ts` and `vite.renderer.config.ts` — the standard Vite workaround to suppress the client-build `process.env` stub for a genuine Node-context build.
- **Files modified:** `vite.main.config.ts`, `vite.renderer.config.ts`
- **Verification:** built bundle's `process.env.SWG_TEST_MODE` / `process.env.LOCALAPPDATA` reads confirmed present (not stubbed) via grep on the built JS; subsequent test runs show real `C:\Users\...\AppData\Local\swg-toolkit\studios\...` paths in persisted deployRecords.
- **Committed in:** `3b8f49d`

**3. [Rule 1 - Bug] `ConsolePanel.tsx`/`LogPanel.tsx` crashed the ENTIRE app to a blank page on every boot ("Maximum update depth exceeded")**
- **Found during:** Task 1 — every diagnostic Electron launch showed `document.body.innerText === ''` and a `pageerror` reading "Maximum update depth exceeded" (minified) / "The result of getSnapshot should be cached to avoid an infinite loop" (dev build), regardless of `SWG_TEST_MODE`.
- **Issue:** `useLogStore((s) => s.entries.filter((e) => e.channel === 'console'))` (and the Log-tab equivalent) called `.filter()` **inside** the Zustand selector, returning a brand-new array reference on every single call. React's `useSyncExternalStore` (which Zustand's `useStore` is built on) compares consecutive `getSnapshot()` results via `Object.is`; since a fresh `.filter()` result is never reference-equal to itself, React concluded the store was perpetually changing and re-rendered indefinitely, hitting its infinite-loop safety cap and unmounting the whole tree. This is almost certainly the true root cause of the ALREADY-DOCUMENTED (04.4-09 deferred-items.md) "2 pre-existing e2e/04-workspace.spec.ts failures" — both symptoms (missing 'Welcome' tab text, theme-select timeout) are exactly what a permanently-blank React root produces.
- **Fix:** Select the raw, stable `entries` array (`useLogStore((s) => s.entries)`) and derive the channel-filtered view via `useMemo`, matching the pattern already used elsewhere in this codebase (`DeployPanel.tsx`'s `uncommittedCount`).
- **Files modified:** `packages/renderer/src/panels/ConsolePanel.tsx`, `packages/renderer/src/panels/LogPanel.tsx`
- **Verification:** post-fix diagnostic launch shows real rendered content (`"SWG Toolkit\nFile\nEdit\n...\nOpen a project\n..."`), zero `pageerror`s across 5s of polling.
- **Committed in:** `3b8f49d`

**4. [Rule 1 - Bug] Baseline-revert `restoreCfg` restored into the WRONG file; loose-override "first deploy" of a brand-new version silently deployed via cfg/absolute-path instead**
- **Found during:** Task 1 — after a successful cfg-model deploy + "Deploy Baseline (revert to stock)", the client cfg still contained the deployed `.include` line; separately, choosing "Loose override dir" for a never-before-deployed version's first Deploy threw `ENOENT ... swgtoolkit.cfg`.
- **Issue (4a):** `syncLiveToVersion.ts`'s Baseline-revert cfg branch called `restoreCfg(liveCfgRecord.cfgPath, liveCfgRecord.snapshotPath)` — but `.cfgPath` on a `CfgDeployRecord` is the TOOLKIT-owned cfg (`swgtoolkit.cfg`), not the client ROOT cfg that `snapshotCfg` actually snapshotted (stored as `.includeTargetPath`). This overwrote `swgtoolkit.cfg` with the client-root snapshot and left the real client cfg's `.include` line in place forever. **Issue (4b):** `applyModel` for a target changeset with no prior `deployRecord` (its first-ever deploy) always fell back to `'cfg'`, with no way for the caller to signal "the user picked Loose override dir" — DeployDialog's own `deployModel==='loose-override'` branch correctly routed into `syncLiveToVersion`, which then internally re-derived (and got wrong) which model to actually apply.
- **Fix:** (4a) `restoreCfg(liveCfgRecord.includeTargetPath, liveCfgRecord.snapshotPath)`. (4b) Added `ReconcileCtx.intendedApplyModel?: 'loose' | 'cfg'`, consulted only when the target has no existing record; `DeployDialog.tsx`'s loose-override branch now passes `intendedApplyModel: 'loose'` (and the absolute-path branch passes `'cfg'` explicitly, matching the existing default).
- **Files modified:** `packages/renderer/src/services/syncLiveToVersion.ts`, `packages/renderer/src/panels/deploy/DeployDialog.tsx`
- **Verification:** Scenario 1's revert-to-Baseline assertion (`cfgBytes` no longer matches `.include`) passes; Scenario 2's first-time loose-override deploy writes the staged file into the override dir and passes; all 46 pre-existing renderer unit tests (`syncLiveToVersion.test.ts`, `DeployDialog.test.tsx`, `VersionHistoryBody.test.tsx`) still green — the fix is additive (new optional ctx field, defaults preserve prior behavior for already-deployed targets).
- **Committed in:** `3b8f49d`

**5. [Rule 1 - Bug] Ground-truth model correction — no silent reconcile on version-row select**
- **Found during:** Task 1, re-reading the CURRENT `VersionHistoryBody.tsx` per CLAUDE.md's ground-truth mandate before writing assertions.
- **Issue:** The plan's own text (and its "fact-check pass" revision note, and 04.4-09-SUMMARY.md's `requires` frontmatter) asserted that selecting a saved version silently reconciles the live client via `syncLiveToVersion`. Direct source read shows `handleRowClick -> doSelect -> selectVersion` (changesetService.ts) — which only moves `activeVersionId` and materializes staging, never touching `deployedVersionId` or calling `syncLiveToVersion`. This was an intentional design change (code comment: "D-04 SUPERSEDED 2026-07, crew consult") that postdated whatever informed the plan's assumption.
- **Fix:** Spec assertions corrected to the verified model — selecting a row leaves `deployedVersionId` unchanged; only the Deploy dialog moves it, for both new and re-navigated versions.
- **Files modified:** `e2e/07-deploy-flow.spec.ts` (spec logic only — no product code change; this is a test-correctness deviation, not a product bug)
- **Verification:** Scenario 1/2 Test 4 explicitly asserts `deployedVersionId` is unchanged after a row click, and this passes consistently.
- **Committed in:** `3b8f49d`
