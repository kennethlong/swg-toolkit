<objective>
Build the delete/restore/undo SERVICE layer for `delete-project-with-restore` (the phase's highest-severity item): a `deleteProject(projectFolder)` function that restores the bound client to stock (model-appropriate reset, via a NEW shared `deploymentReset.ts` also used by `DeployDialog.handleReset` — eliminating the two-copies drift risk), parks the project + full changeset history for session-scoped undo (never a hard delete), and a session purge that reclaims stale trash from a prior session/crash on next app startup.

This plan delivers the SERVICE + STORE half of the vertical slice (TDD). Plan 04.4-10 builds the UI half (sketch 017 kebab/confirm/toast/dimmed-rows) on top of this.

**Locked undo contract (this plan, 04.4-10, and 04.4-14 all state this identically — do not diverge):** Undo restores the parked project's folders/changeset history byte-for-byte. Undo does **NOT** re-deploy or re-apply anything to the client. If the user wants the client to reflect a deployed state again after Undo, they re-deploy through the normal Deploy dialog. Rationale: (a) the todo's AC3 phrases re-deploy-on-undo as one *option* among others ("Options: ... with an Undo affordance that restores them (and re-applies the live deploy if it was reverted on delete)"), not a hard requirement; (b) CONTEXT.md D-04/D-05 describe undo purely in terms of the parked project rows, never mention re-deploying; (c) `resetLoose` deletes the B3 snapshot it restores from (verified, see revision note above), so re-deploying on undo would need to re-derive deploy state from `flatten()` + the record's `writtenFiles` list rather than a true byte-identical restore of what was live — a materially different, unbuilt feature; (d) auto-re-deploying on Undo risks clobbering a client the user has manually changed in the interim, which is the exact failure mode `client-deploy-design-tenets` guards against. AC5's test bar ("undo restores the project + all changeset version folders byte-for-byte and re-lists it") does not require a client re-deploy assertion, and this plan's tests match that bar exactly.

Purpose: today there is no in-app delete; a manual folder-delete orphans a modified client cfg or leaves deployed override files behind. Reusing the EXISTING restore machinery (never re-deriving it) is the core risk to manage here.
Output: `deleteProject.ts`, `deploymentReset.ts` (new shared restore module), `deleteUndoStore.ts`, a `removeRecentProject` export, a corrected `recentProjects.ts` header comment, and a startup trash-purge wired into `App.tsx`.
</objective>
