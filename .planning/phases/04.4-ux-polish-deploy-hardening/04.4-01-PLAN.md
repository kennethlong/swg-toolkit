<objective>
Build the delete/restore/undo SERVICE layer for `delete-project-with-restore` (the phase's highest-severity item): a `deleteProject(projectFolder)` function that restores the bound client to stock (model-appropriate reset), parks the project + full changeset history for session-scoped undo (never a hard delete), and a session purge that reclaims stale trash from a prior session/crash on next app startup.

This plan delivers the SERVICE + STORE half of the vertical slice (TDD). Plan 04.4-10 builds the UI half (sketch 017 kebab/confirm/toast/dimmed-rows) on top of this.

Purpose: today there is no in-app delete; a manual folder-delete orphans a modified client cfg or leaves deployed override files behind. Reusing the EXISTING restore machinery (never re-deriving it) is the core risk to manage here.
Output: `deleteProject.ts`, `deleteUndoStore.ts`, a `removeRecentProject` export, and a startup trash-purge wired into `App.tsx`.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| UI action → deleteProject | User-triggered destructive operation; project folder name is attacker-adjacent input (comes from disk enumeration, not remote, but still user-controlled naming) |
| deleteProject → filesystem | Restores/moves real client cfg files and project directories |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-04.4-01 | Tampering | `.trash/<id>-<token>` path construction from a project name | mitigate | `isConfinedToRoot(target, studiosRoot/.trash)` gate before every `fs.renameSync`, mirroring the existing `getStudioDir` basename+space-sanitize pattern |
| T-04.4-02 | Repudiation | Non-fatal per-step restore failures silently swallowed | mitigate | `restoreErrors: string[]` collected and returned, never discarded — plan 10's toast surfaces them (⚠ variant) |
| T-04.4-03 | Denial of Service | Stale `.trash` entries accumulate across crashed sessions, filling disk | mitigate | Unconditional purge-on-boot (Task 3) — no manual cleanup dependency |
| T-04.4-04 | Information Disclosure | Deleted project's cfg snapshot bytes remain in `.trash` until next boot | accept | Session-scoped by design (maintainer decision D-05); local single-user desktop tool, no remote exposure |
</threat_model>
