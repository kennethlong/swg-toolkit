## Codex Review

﻿**Summary**

Overall, the phase is well researched and the plan set is strong: it reuses existing deploy/restore machinery, names the sketch contract, separates Core3 and swg-main correctly, and adds real-Electron coverage for the blind spots that caused prior UAT misses. The main risks are not missing scope, but internal contradictions and a few feasibility mismatches against the current code. The highest-risk items are delete undo semantics, `SWG_TEST_MODE` hook placement/typing, server-push path persistence, and real-asset fixture activation.

**Strengths**

- The plans consistently honor the project’s “verify against ground truth” rule, especially for `.eft`, Core3, swg-main, and viewport orientation.
- Delete project is correctly framed as “restore first, then park,” and it reuses `restoreCfg`, `deactivatePatch`, and `resetLoose` rather than inventing a second rollback path.
- Sketch 017 is treated as a UI contract with enumerated must-haves. That is exactly the right level of specificity for this repo.
- E2E coverage targets real Electron and explicitly gates `console.error` / `pageerror`, which addresses the known jsdom blind spot.
- Core3 and swg-main are intentionally split into separate services. That avoids a premature abstraction over two different mechanisms.

**Concerns**

- **HIGH: Delete undo semantics conflict across plans.** Plan 01 says undo restores the project folders only and “no re-deploy attempt”; Plan 14 expects undo to put the client back into the post-deploy, non-pristine state. Those cannot both be true.
- **HIGH: `resetLoose()` deletes snapshots during restore.** I verified `resetLoose` unlinks `snapshotPath` after copying it back. If delete calls `resetLoose` before parking the studio dir, undo may not have the data needed to recreate the previous deployed state.
- **HIGH: Trash move shape is underspecified.** Plan 01 says move both `studioDir` and umbrella project folder into one `trashPath`, then restore `trashPath` back to two original paths. That needs explicit subdirectories, e.g. `.trash/<id>/studio` and `.trash/<id>/project`.
- **HIGH: Test hooks are installed too late.** Plan 09 installs `window.__testHooks` from `WorkspaceShell`, but deploy/delete E2E flows need hooks on the Welcome/New Project screens before a workspace shell exists. Install from renderer bootstrap or `App.tsx`.
- **HIGH: IPC typing in Plan 09 does not fit current `TypedIpcRenderer`.** `IpcChannels` currently maps channel to return type and `invoke(channel, defaultPath?)`. `test:set-stub-paths(channel, paths)` needs typed argument support, not just adding a `void` return entry.
- **HIGH: Server push reset records are local-only in Plan 12.** If the app closes after a server push, the UI loses the record needed to reset. That weakens the “restore-on-reset” promise for external server files.
- **MEDIUM: Plan 02/11 logging installs from ConsolePanel.** If the user never opens Console, console capture and main-log forwarding may never start. Logging should be installed once at app startup.
- **MEDIUM: Plan 03 says create `StatusBar.test.tsx`, but the file already exists.** Extend the existing test instead. Also verify `viewportStore.loadComplete` signature before encoding the test API.
- **MEDIUM: Plan 04 forces a non-identity rotation.** If human verification shows identity is actually correct and the issue is camera default, the plan currently disallows the correct outcome. The acceptance should be “matches SIE,” not “must be non-identity.”
- **MEDIUM: Plan 05 real fixture activation may not be CI-enforceable.** `fixtures-real` assets are usually gitignored and local-only. If CI must enforce CORE-05, add a synthetic committed STAG/EFCT fixture or a CI fixture-copy gate.
- **MEDIUM: Plan 06’s codec lookup conflates compressor code and archive version.** `getCodecFor(int compressorOrVersion)` is ambiguous. Use explicit functions like `codecForCompressor()` and `codecForTreVersion()`.
- **MEDIUM: Plan 07 and 12 disagree on Core3 path shape.** Plan 07 says `serverConfig.path` may point at `conf/`; Plan 12 calls `path.join(serverConfig.path, 'conf')`. Pick one contract and enforce it.
- **MEDIUM: Plan 08/12 swg-main config path is unresolved.** Plan 12 includes a placeholder for `servercommon.cfg`; this should be resolved before implementation, likely `exe/shared/servercommon.cfg`.
- **LOW: Plan 10 kebab menus need explicit event propagation handling.** Row click plus kebab click can accidentally open the project unless `stopPropagation()` is included.
- **LOW: E2E specs are very ambitious.** Plans 13/14 may be brittle unless the hook surface exposes stable actions instead of relying heavily on text/UI selectors.

**Suggestions**

- Resolve delete undo first: decide whether undo restores only the toolkit project, or also re-applies the prior client/server deployment. Update Plans 01, 10, and 14 to match.
- Before calling `resetLoose` during delete, preserve enough deployment state for undo, or explicitly document that undo does not reapply deployment and fix Plan 14’s expectations.
- Define the trash directory layout precisely and test both project and studio restore from separate parked subpaths.
- Move `installTestHooks`, `installConsoleCapture`, and `installMainLogForward` to an app-level startup point, not panel/workspace mount points.
- Redesign typed IPC to support per-channel argument tuples, e.g. `IpcInvokeArgs` plus `IpcInvokeReturn`, before adding test-only channels.
- Persist server push records in the workspace manifest or a small server-deploy record file, so reset survives panel remount and app restart.
- Split Plan 05 into “parser change” and “fixture activation” if real asset extraction remains machine-local.
- In Plan 04, change acceptance to allow identity/camera adjustment if that is what SIE parity proves.
- In Plan 12, require a dry-run/confirmation display for external server path writes, matching the caution used for client deployment.
- For Plans 13/14, prefer test hooks that perform stable app actions and expose state snapshots over fragile selector-heavy flows.

**Risk Assessment**

Overall risk: **MEDIUM-HIGH**.

The phase goals are achievable and the plans mostly target the right code. The risk comes from cross-plan semantic drift: delete undo expectations differ, test hooks may be unavailable at the moment E2E needs them, and server push lacks durable reset state. Fixing those before execution would bring the plan set down to **MEDIUM** risk.

## 4. Suggestions

1. **Plan 01 — Harden trash targets:** In `deleteProject`, derive paths from `readManifest` + `workspace.json`: always move `getStudioDir(projectFolder)`; move umbrella via `getDefaultProjectFolder(meta.projectName)`; **assert** `isConfinedToRoot` for both under app data root; **never** move paths equal to `meta.clientPath`. Add test G: “client-bound project delete does not move client install.”

2. **Plan 01 — Match `handleReset` completely:** Extract shared `resetDeploymentFromRecord(rec, opts?)` from `DeployDialog.handleReset` (restore + artifact cleanup), call from Reset and delete. Avoid two drift-prone copies.

3. **Plan 04 — Reconcile with source comments before rotating:** Task 2 should start from the **current** `StaticMeshView` comment (identity = front, residual = yaw). Candidate rotations should be **±90° Y** (left/right diagonal), not ruled-out 180° Y. If D-17 shows identity is already front-aligned, escalate: either amend D-16 to allow default camera azimuth change, or close todo as “verified acceptable.”

4. **Plan 09 — Add `data-testid` / hook contract:** Extend `testHooks.ts` with explicit actions: `openProjectDialog()`, `createProject(...)`, `stageFile(...)`, `saveVersion()`, `selectVersion(id)`, `openDeployDialog()`, `deleteProjectViaKebab(...)`. Reduces selector fragility in 13/14.

5. **Plan 09 — CI step:** After Vite builds, add a lightweight check: `.vite/build/main.js` exists + optional `node -e` import smoke, or run existing `e2e/01-boot.spec.ts` as gate before adding 06/07.

6. **Plan 05 — CI fixture strategy:** Either commit minimal synthetic STAG + PPSH fixtures (allowed — `.eft` not gitignored), or add CI step to run extract script when `SWG_INFINITY_PATH` secret is set. Don’t claim CORE-05 gate runs in CI until one path is chosen.

7. **Plan 07/12 — Document `serverConfig.path` contract:** One line in wizard/README: Core3 = `MMOCoreORB/bin` root; swg-main = repo root containing `exe/shared/servercommon.cfg`. Plan 12 should use that contract, not guess `path.join` segments.

8. **Plan 02/11 — Boot-time logging:** Call `installConsoleCapture()` from `App.tsx` mount (alongside trash purge), not only ConsolePanel — captures early renderer errors per D-12 bar.

9. **Wave 0 consolidation:** Research lists missing test files; consider a thin **04.4-00** plan that lands empty RED tests + CI build step first so Wave 1 parallel TDD doesn’t duplicate scaffolding.

10. **Align undo semantics:** Update todo AC5 or plan 01 success criteria to state explicitly: undo restores parked project bytes only; user must re-deploy if they want live client state back (unless you implement re-deploy).

## Sonnet Review (fresh instance)

### Summary

This is an unusually well-grounded plan set for a 14-plan, 8-todo phase. I spot-verified roughly two dozen of the plans' and RESEARCH.md's specific file/line citations directly against the repo (`SWG-Toolkit`) and sibling ground-truth projects (`swg-client-v2`, `Core3`, `swg-main`) — `StatusBar.tsx`'s hardcoded mesh text, `VfsTree.tsx:373`'s dim-label token, the duplicated `SWG_ORIENTATION` identity constant + its "180°Y reverted" history in both view files, `DeployDialog.tsx`'s `handleReset` record-shape dispatch, `changesetService.ts`'s store-independent `readManifest`/`writeManifest` vs. store-coupled API, `TreArchive.cpp`/`TreBuilder.cpp`/`Zlib.h`'s codec seam and `ZLIB_MAX_BLOCK` cap, `Effect.cpp`/`Effect.h`'s PTXM-done/STAG-missing gap, the `mesh-roundtrip.test.ts` EFCT skip-on-missing-fixture pattern, `ci.yml`'s genuinely missing pre-E2E build step, and `WorkspaceInfo.serverConfig`'s exact shape — and every one checked out exactly as claimed. That level of fidelity is rare and substantially de-risks this phase. The plan set also shows real architectural discipline: zero file-modification overlaps across all nine Wave-1 plans (enabling true parallelism), a deliberate refusal to force one abstraction across the two structurally-different server-push mechanisms, and consistent "reuse the existing restore dispatch, don't re-derive it" instructions that directly target the project's own documented risk pattern (`feedback-executor-integration-blind-spot`). The concerns below are real but narrow and fixable pre-execution — none invalidate the overall plan.

### Strengths

- **Exceptional ground-truthing.** Nearly every "current state" claim in RESEARCH.md and the plans (hardcoded StatusBar text, VfsTree token line, orientation constant + history, DeployDialog dispatch logic, native-core codec seam, EFCT test skip behavior, CI's missing build step, Core3/swg-main config mechanisms) verified byte-for-byte against real source during this review.
- **Clean wave partitioning.** Cross-checked `files_modified` across 04.4-01 through 04.4-09 (all Wave 1, `depends_on: []`) — no two plans touch the same file, so the "independent" label is actually true, not just asserted. 04.4-08 explicitly calls out and resolves what would otherwise have been a same-file dependency with 04.4-07 by splitting `core3-parity.md`/`swg-main-parity.md`.
- **"Don't re-derive" discipline.** Delete (04.4-01) is required to reuse `cfgActivator`/`looseOverrideDeploy`'s exact dispatch from `DeployDialog.handleReset` rather than reimplement restore logic, with an explicit grep-based acceptance criterion guarding against the Pitfall-5 trap (reading manifest via `useWorkspaceStore` instead of the store-independent API, which would break deleting a non-open project — the common case).
- **Correctly refuses a false abstraction.** 04.4-07/08 implement Core3 (Lua-array injection) and swg-main (loose-file override) as genuinely separate services rather than forcing a shared "server deploy target" interface — backed by real, verified mechanism differences, not just architectural taste.
- **D-17's human checkpoint is properly load-bearing.** 04.4-04's Task 3 is a real `checkpoint:human-verify`/`autonomous:false` blocking gate, not a rubber-stamp, and the plan explicitly forbids re-trying the already-falsified 180°Y hypothesis.
- **Regression-first framing for the codec refactor.** 04.4-06 explicitly requires byte-identical behavior before/after, and preserves the MOUNT-05 graceful-classify behavior and the V6000 write-refusal rather than silently changing behavior under cover of a "refactor."

### Concerns

**HIGH**
- **04.4-03 Task 1 asserts a false premise that risks clobbering existing test coverage.** The plan states "Create `StatusBar.test.tsx` (new — none exists per RESEARCH.md's... note, which this task resolves)". I verified `packages/renderer/src/shell/StatusBar.test.tsx` **already exists** (258 lines, from `04.3-09-PLAN.md` Task 2, covering sketch-008 S6/S7/P9 assertions) with a nontrivial mocking harness (`vi.mock('@swg/native-core', ...)`, a stubbed `Worker`, SAB stubs). The plan's `read_first` list for this task doesn't include the file at all. If the executor follows the plan literally with a fresh `Write` instead of an `Edit`, it will destroy existing, working test coverage for unrelated sketch-008 status-bar behavior (deployed-version label, dock-state chip, scan message). This must be fixed before execution: reframe as "extend `StatusBar.test.tsx`" and add it to `read_first`.
- **04.4-11's action text requires touching a file not in its declared scope.** Task 1 says to call `installMainLogForward()` "from the SAME mount point `installConsoleCapture()` is already called from (`ConsolePanel.tsx`'s mount effect...)" — but `ConsolePanel.tsx` is absent from 04.4-11's `files_modified` frontmatter. This is precisely the class of drift the project's own `feedback-executor-integration-blind-spot` memory warns about: logic described in prose that isn't reflected in the enforced artifact list. An executor or gate that treats `files_modified` as authoritative will either skip the wiring (leaving main-process events never forwarded, silently failing D-13) or violate the plan's declared scope.

**MEDIUM**
- **04.4-04's rotation-derivation logic is thinner than it reads.** Task 2 reasons "since 180°Y showed the mesh's back, identity already shows the front" — but the very existence of the `viewport-default-facing-axis` todo implies the current identity state is *also* wrong (otherwise there'd be nothing to fix). The plan then narrows the retry space to Y-axis-only candidates (π/2, −π/2), which risks spending the single mandated D-17 human-verify cycle on the wrong axis if the true mismatch isn't a pure yaw offset. RESEARCH.md itself flags this as MEDIUM confidence; the plan should say what to do if none of the Y-only candidates match (e.g., fall back to deriving the full rotation from a matched screenshot/known reference rather than continuing to guess on one axis).
- **Server-push trust gap is accepted, not mitigated, with no sanity check.** 04.4-07/08 (wired via 04.4-12) deliberately sidestep confirming `serverConfig.path` actually points at the *running* server instance (a separate WSL2 mount vs. a git checkout for Core3; a Docker bind-mount vs. repo checkout for swg-main) — explicitly dispositioned "accept" in both threat models. There's no lightweight liveness/sanity check (e.g., does `conf/config.lua` actually parse at that path? does `hostPort` respond?) before writing, unlike the descriptive-confirm-modal discipline (D-03) applied to the client-side delete. A push could "succeed" (file written, Lua line inserted) while reaching nothing the maintainer is actually running.
- **04.4-06's TDD framing is strained for what is fundamentally a refactor.** Task 1 is nominally "RED," but the plan itself pre-authorizes the possibility that the black-box parity assertions pass immediately (since the public binding surface is unchanged by design) and falls back to a native-level unit test in that case. That's a reasonable hedge, but `type: tdd` doesn't cleanly fit a pure interface-seam change — worth relabeling `type: execute` with an explicit before/after byte-diff regression test as the real gate, rather than forcing an artificial RED step that may not exist.
- **04.4-12's cross-plan interface is a soft dependency, not a hard one.** Task 2's draft call guesses `path.join(serverConfig.path, 'servercommon.cfg')` for the swg-main push but flags in a comment "confirm the exact relative path from that plan's SUMMARY before wiring" — reasonable given `depends_on: ["04.4-07", "04.4-08"]`, but there's no acceptance criterion forcing that confirmation to actually happen; an executor moving fast could wire the guessed path and ship a UI button that silently fails.
- **04.4-09 ships an unused stub hook**, `getDeployPhase: () => null`, that neither downstream e2e spec (13 or 14) appears to call (both lean on `getChangesetManifest()` instead) — a small violation of D-08's own "build only the hooks these specs need" rule, shipping speculative surface ahead of a consumer.

**LOW**
- 04.4-01 and 04.4-10 both list `deleteProject.ts` in `files_modified`, but 04.4-10's narrative only describes UI-level work; it's unclear what (if anything) changes in the already-tested service in the later plan. A one-line clarification would prevent an executor from making unnecessary changes to tested code.
- 04.4-07's "RESOLVED" framing of Open Question 1 is really a scope change (auto-discovery → user-provided path) rather than a technical resolution of the WSL2 transport question — accurate in substance but could read as more settled than it is.
- 04.4-13/14 rely on `SWG_TEST_MODE` env propagating from the Playwright Electron launch into the renderer's `window.__testHooks`, but neither spec's acceptance criteria include an early sanity assertion (`window.__testHooks !== undefined`) before relying on it deeper in the scenario — a broken-plumbing failure would surface confusingly rather than immediately.
