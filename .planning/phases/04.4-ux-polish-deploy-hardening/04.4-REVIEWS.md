## Codex Review

## Summary

Round-2 is materially stronger than the first pass: the D-04a undo ruling is now mostly consistent across delete service, UI, and E2E plans; sketch 017 is treated as a real UI contract; the e2e build gap is addressed; server push is split correctly between Core3 and swg-main; and the `syncLiveToVersion` fact-check corrections are good. I would still not sign off unchanged. There are a few high-risk implementation contradictions, especially delete’s “byte-preserving trash” contract versus shared reset artifact cleanup, Core3 path transport, and an incomplete TRE codec seam.

## Strengths

- The no-redeploy-on-undo ruling is now consistent in `04.4-01`, `04.4-10`, and `04.4-14`.
- `04.4-10` correctly enumerates sketch 017 elements and preserves the dialog-only dimmed-row nuance.
- `04.4-09` fixes the real CI build-before-E2E blind spot and avoids polluting production IPC contracts with a test-only channel.
- `04.4-07` / `04.4-08` correctly avoid a false shared abstraction for Core3 versus swg-main.
- `04.4-04` now handles the viewport orientation uncertainty honestly and keeps the human verification gate.
- The fact-check passes around `syncLiveToVersion` versus `setLiveVersion` are valuable and prevent a bad instrumentation/test model.

## Concerns

- **HIGH — `04.4-01-PLAN.md`: shared reset cleanup can break byte-preserving undo.**  
  The plan extracts the full `DeployDialog.handleReset` body, including artifact cleanup. In current code, absolute-path cleanup unlinks `rec.patchPath`, and the plan itself says `patchPath IS the studioDir path`. If delete calls that before parking `studioDir`, the trash copy is no longer byte-for-byte complete. This contradicts the undo contract.

- **HIGH — `04.4-07-PLAN.md` / `04.4-12-PLAN.md`: Core3 `TrePath` is not Windows-writable as planned.**  
  The real checked config has `TrePath = "/home/swgemu/Desktop/SWGEmu"`. A Windows renderer cannot simply copy the generated `.tre` to that literal Linux path. The plan says it avoids WSL UNC discovery, but the copy step still needs a host-accessible mapping or explicit user-provided server data path.

- **HIGH — `04.4-06-PLAN.md`: TRE codec seam is incomplete.**  
  The plan routes payload extract/build through codecs, but current TRE code also inflates TOC/name blocks in `TreArchive.cpp` and deflates TOC/name blocks in `TreBuilder.cpp`. If D-21 means “TRE read/write path is pluggable,” these hardcoded zlib calls remain outside the seam.

- **MEDIUM — `04.4-01-PLAN.md`: outside-project path handling can still delete the wrong studio.**  
  The plan skips moving an umbrella folder outside `getDefaultProjectsDir()`, but still derives and moves `studioDir` from `path.basename(projectFolder)`. A malicious or mistaken outside path with the same basename as a real project could park the real project’s studio.

- **MEDIUM — `04.4-02-PLAN.md`: console wrapping needs a restore/reset path for tests.**  
  `installConsoleCapture()` globally monkey-patches `console.*` and installs window listeners. The plan tests idempotency but does not specify uninstall/reset of original console methods between tests, which risks cross-test contamination.

- **MEDIUM — `04.4-07`, `04.4-08`, `04.4-12`: server-push record clearing is ambiguous.**  
  Some behavior text says reset clears the persisted JSON; later action text says the caller may clear it. `04.4-12` says “check SUMMARYs.” That is too late for a plan contract. The record shape and clear responsibility should be locked now.

- **MEDIUM — `04.4-09`, `04.4-13`, `04.4-14`: test hook surface may be under-specified.**  
  `04.4-09` exposes dialog stubbing and store reads only, while D-08 mentions action triggers. `04.4-14` says to assert a `listProjects()`-equivalent “via `window.__testHooks`,” but no such hook is planned. Either add the hook or require UI-only assertions.

- **MEDIUM — `04.4-11-PLAN.md`: early main-process logs may be lost.**  
  `sendMainLog('app ready...')` can fire before the renderer subscribes inside `installConsoleCapture()`. Dialog logs will work, but the app-lifecycle log is unreliable unless sent after renderer load or buffered.

- **LOW — `04.4-10-PLAN.md`: possible double-push wording.**  
  Task 2 says call `deleteProject()`, “then push a TrashEntry,” then notes it is already done inside `deleteProject`. Clarify that UI never pushes directly.

- **LOW — `04.4-05-PLAN.md`: synthetic STAG fixture could validate the implementation’s own assumptions.**  
  The plan is source-grounded, but a real fixed-function STAG fixture, if findable, would be a stronger complement than synthetic-only CI coverage.

## Suggestions

- Split `deploymentReset.ts` into client restore and artifact cleanup, or add `cleanupArtifacts?: boolean`; delete should restore the client but not unlink files inside the studio before parking.
- In `deleteProject`, refuse or no-op entirely for project folders outside the known project list/root unless explicitly allowed; do not move basename-derived studios for untrusted paths.
- For Core3, add a `serverTrePathHost` / “Core3 TRE data folder” setting, or implement a documented WSL path translation strategy. Do not rely on `Core3.TrePath` being directly writable from Windows.
- Expand `TreCodec` routing to TOC/name inflate and deflate, or explicitly rename the goal to “payload codec seam” and document why TOC/name remain stock.
- Add `resetConsoleCaptureForTests()` or equivalent internal test helper that restores original console methods and removes listeners.
- Lock server push reset semantics now: either record includes `studioDir` and reset clears persistence, or UI always clears persistence after reset. Tests should match one model.
- Add the missing E2E hooks intentionally, such as `listProjects`, `openProjectDialog`, or `getDeleteUndoPending`, if the specs are expected to avoid brittle DOM archaeology.

## Risk Assessment

**Overall risk: MEDIUM-HIGH.** The plans are much improved and mostly aligned with phase goals, but this phase is broad and touches destructive filesystem operations, native compression infrastructure, CI, Electron hooks, and external server configs. The delete artifact-cleanup contradiction and Core3 path issue are both real correctness blockers. Fixing those in the plans should bring the phase down to **MEDIUM** risk.

## Concerns

### HIGH

- **[04.4-10-PLAN.md] Neither row surface refreshes its list after delete/undo — the sketch's signature behaviors (dimmed row, row-disappears) may not render until the component remounts.** I read the actual source: `ProjectListDialog.tsx:48-51` loads `projects` via `useEffect(() => {...}, [isOpen])` — it only re-fetches when the dialog transitions open, not on every render. `WorkspaceEntry.tsx:164-203` loads `recents` via `useEffect(() => {...}, [])` — mount-only, never again. Plan 04.4-10's Task 2 says the dimmed row shows for "every `pending` entry whose `originalFolderPath` matches a project no longer in `listProjects()`'s output" and that the Welcome row "simply disappears" — but if `deleteProject()` runs while the dialog stays open (the exact case sketch 017 designs for — delete without closing the list), neither component re-invokes `listProjects()`/`getRecentProjects()` afterward, so the stale `projects`/`recents` arrays keep showing the just-deleted project as a normal, clickable row (or not at all, depending on which array the dimmed-row logic reads from) until the dialog is closed and reopened. This isn't a hypothetical — it's the literal state-management pattern in the file today, and no task in 04.4-01 or 04.4-10 mentions calling `setProjects(listProjects())` / `setRecents(...)` after delete or after `restore()`. This is the single biggest risk to the phase's flagship feature actually looking right on screen.
- **[04.4-01-PLAN.md] Deleting the CURRENTLY-OPEN project moves its folders on disk *before* releasing anything the running app holds open on them.** Task 2's own step ordering is: (3) `fs.renameSync` studioDir + umbrella folder into `.trash`, (4) `removeRecentProject`, (5) *then* `useWorkspaceStore.getState().close()` if the deleted project is open. I checked `workspaceStore.ts` — `close()` is a pure state setter; there's no `unmountTre`/`disposeMount`/`releaseHandle` call anywhere in `packages/renderer/src/services/` visible from a repo-wide grep. If the open project is using the shadow deploy model, its shadow dir lives *inside* `studioDir` (`shadowBaseService.ts:253`) and may be actively mounted/read by the native addon for the live viewport. Renaming a directory tree on Windows while the native module holds open file handles into it (memory-mapped TRE reads, or a worker thread mid-parse) risks `EBUSY`/`EPERM`, which the plan's try/catch turns into a `restoreErrors` entry rather than a hard failure — but that means the delete could *partially* succeed (client restored, recent-project entry removed) while the folder move silently fails, leaving the project neither cleanly deleted nor cleanly present. None of Tests A-G in 04.4-01 exercise "delete the project that is currently open with a live native mount" — they all use isolated tmp fixtures, not a real mounted workspace.
- **[04.4-01-PLAN.md / 04.4-07-PLAN.md / 04.4-08-PLAN.md] Delete never resets a project's server-side push.** `deleteProject.ts` (04.4-01 Task 2) only calls `resetDeploymentFromRecord` against the *client-side* deploy record from the changeset manifest. It has no knowledge of `serverPush.core3.json` / `serverPush.swgmain.json` (07/08) sitting in the same `studioDir` it's about to park into `.trash`. Those files travel into the trash with the rest of the studio dir, but the **actual side effects they represent are never undone**: Core3's `config-local.lua` still has the `table.insert(Core3.TreFiles, 1, "swgtoolkit_<slug>.tre")` line, and the copied `.tre` still sits in the server's `TrePath`; swg-main's compiled-data override files are still sitting in the server's searchPath dir. After a project delete, a running Core3/swg-main instance keeps loading a now-orphaned override indefinitely — with no UI surface left to reset it, since the record's owning project is gone (parked in a purge-on-next-boot trash dir). This is a real, product-visible regression risk this phase itself introduces (server push is new in this same phase) and the close-out audit in 04.4-07 Task 1 won't catch it because it audits realized client-side claims, not this new cross-plan interaction.

### MEDIUM

Task 1/Task 2 describe the confirm modal and its Delete button but never mention disabling the button (or otherwise guarding against a double-click / rapid double-submit) while the operation is in flight. A second click before the first `deleteProject()` call resolves could race two concurrent renames of the same `studioDir`, or double-park into two different `.trash/<id>-<token>` folders with divergent restoreErrors state.
