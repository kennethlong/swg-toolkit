<objective>
Refactor the TRE **payload** compression call sites (`TreArchive::extractEntry`'s `treInflate` call and `TreBuilder::build`'s per-entry `zlibCompress` call) behind a small pluggable `TreCodec` interface, per D-21's architecture constraint: "make the TRE read/write path a pluggable codec interface, not hardcoded, so custom compression/encryption can be dropped in" (open-source extensibility for forks like Restoration's proprietary v6000 encryption).

**Scope, stated explicitly (round-2 fix — see revision note above):** "the TRE read/write path" for codec-pluggability purposes means the PER-ENTRY PAYLOAD path only. `TreArchive.cpp`/`TreBuilder.cpp` ALSO inflate/deflate the archive's TOC and name blocks (lines ~192/215 read, ~333/357 write) — those calls stay hardcoded stock zlib, DELIBERATELY, because TOC/name-block compression is archive-enumeration metadata that must be universally readable (in plain zlib) before any per-entry codec can even be selected — this is true for every known TRE fork, including the already-ground-truthed encrypted-Restoration v6000 case (memory `tre-version-oracles-and-v6000-encryption`). This is a scoping decision, not an incomplete refactor.

This is a SEAM refactor, not new functionality: `TreArchive`/`TreBuilder` callers stay the same; only the PAYLOAD compression call becomes indirect through TWO explicitly-named lookup functions — `codecForCompressor(int compressor)` at the read call sites and `codecForTreVersion(int version)` at the write call site — rather than one ambiguously-named function overloaded across two different integer domains. The existing V6000-write-refusal behavior (`TreBuilder.cpp:204` `isEnumerateOnly` throw) and the existing per-payload read-side graceful classify (MOUNT-05, already landed in 04.3-10/11) are BOTH preserved — this plan does not add v6000 write support, it makes the PAYLOAD seam pluggable for a future/fork codec to do so.

Purpose: architecture constraint from the product-thesis todo (D-21) — the payload codec interface, not new compression capability, and not a claim of TOC/name-block pluggability that the format itself doesn't support meaningfully.
Output: `TreCodec.h`/`.cpp` + `TreArchive.cpp`/`TreBuilder.cpp` payload call sites wired through it, zero behavior change for existing fixtures, TOC/name-block calls explicitly documented as out-of-seam.
</objective>
