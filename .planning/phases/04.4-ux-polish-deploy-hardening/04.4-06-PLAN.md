<objective>
Refactor the TRE compression call sites behind a small pluggable `TreCodec` interface, per D-21's architecture constraint: "make the TRE read/write path a pluggable codec interface, not hardcoded, so custom compression/encryption can be dropped in" (open-source extensibility for forks like Restoration's proprietary v6000 encryption).

**Scope, stated explicitly (ROUND 3 — maintainer ruling, REVERSES round-2's payload-only narrowing; see revision note above):** "the TRE read/write path" for codec-pluggability purposes now covers BOTH the per-entry payload path (`codecForCompressor`/`codecForTreVersion`, unchanged from round 2) AND the archive's TOC/name-block path (`codecForBlockCompressor`, NEW this round). `TreArchive.cpp`/`TreBuilder.cpp`'s TOC/name-block inflate/deflate calls (lines ~192/215 read, ~333/357 write) are now routed through the codec seam too, keyed on the archive's own header fields (`tocCompressor`/`blockCompressor`) — necessarily a DIFFERENT selection axis than the per-entry `compressor` field, since the entry's compressor is unknown until the TOC itself has been decoded (a real chicken-and-egg constraint on the lookup's design, per the maintainer's ruling this is a constraint to design around, not a reason to exclude these sites). Round-2's technical analysis — independently re-verified by Cursor's round-3 spot-check (CONSULT-R3-cursor.out) — that a payload-only seam is architecturally sound and sufficient for any per-entry fork codec (e.g. Restoration's encryption) remains TRUE, and is preserved as the rationale for why `codecForCompressor`/`codecForTreVersion` exist as a lookup pair SEPARATE from `codecForBlockCompressor` (different keying, different lifecycle). But the maintainer's ruling is that D-21's literal wording ("the TRE read/write path") should be honored in full, not narrowed to the subset of that path which happens to satisfy the one known fork use case.

This is a SEAM refactor, not new functionality: `TreArchive`/`TreBuilder` callers stay the same; the per-entry PAYLOAD compression calls AND the TOC/name-block compression calls all become indirect through THREE explicitly-named lookup functions — `codecForCompressor(int compressor)` at the per-entry payload read call sites, `codecForTreVersion(int version)` at the per-entry payload write call site, and `codecForBlockCompressor(int compressor)` (round-3, NEW) at the TOC/name-block read AND write call sites — rather than one ambiguously-named function overloaded across multiple domains. The existing V6000-write-refusal behavior (`TreBuilder.cpp:204` `isEnumerateOnly` throw) and the existing per-payload read-side graceful classify (MOUNT-05, already landed in 04.3-10/11) are BOTH preserved — this plan does not add v6000 write support, it makes the FULL read/write path (payload AND TOC/name-block) pluggable for a future/fork codec to extend.

Purpose: architecture constraint from the product-thesis todo (D-21) — the full codec interface (payload + TOC/name-block), per the maintainer's literal reading of D-21's wording, not new compression capability.
Output: `TreCodec.h`/`.cpp` + `TreArchive.cpp`/`TreBuilder.cpp` payload AND TOC/name-block call sites wired through it, zero behavior change for existing fixtures, three clearly-named lookup functions covering the entire TRE read/write path.
</objective>
