- **ROADMAP success criterion #5 is SATISFIED.** SC #5 reads: "...a mesh's authored front faces the default camera like SIE... OR — an accepted, consciously-documented alternative close... the checkpoint confirms mesh identity is already correct and the residual gap is camera-azimuth-only, which is treated as satisfying this criterion by that characterization alone." That is exactly this plan's outcome. The camera-default azimuth match shipped in Task 3 (below) is a bonus that happens to ALSO satisfy the literal "faces the default camera like SIE" reading, making this outcome the stronger of the two SC #5 paths — but the plan does not require it; the identity characterization alone would have been sufficient.
- **No camera-default follow-up todo needed.** The plan's round-2 revision note explicitly scoped "match SIE's exact default azimuth" as an out-of-scope candidate follow-up, to be recorded as a new todo only if wanted. - **Framing fix (OrbitControls retargeting) was also found and fixed in-task**, per the maintainer's explicit round-1 request ("Can we adjust that so that the mesh is centered and fits the viewport"). Root cause: `useAutoFrame` set `camera.position` and called `camera.lookAt(center)`, but never set `OrbitControls.target` — since `OrbitControls` (`makeDefault`, `enableDamping`, in `Viewport.tsx`) re-aims the camera at its own `target` (defaulting to `(0,0,0)`) on every `update()`, and SWG meshes are anchored at the feet (not centered at origin), the feet ended up centered and the head clipped out of the frustum on load. Fixed by reading `controls` via `useThree((s) => s.controls)` and setting `controls.target` to the bounds center (or `(0,0,0)` in the empty-box fallback) before calling `controls.update()`.

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug, found mid-checkpoint] OrbitControls never retargeted — feet-origin framing clipped the mesh head**
- **Found during:** Task 3 (D-17 checkpoint, round 1 UAT)
- **Issue:** `useAutoFrame` in both `StaticMeshView.tsx` and `SkinnedMeshView.tsx` set `camera.position` and called `camera.lookAt(center)` on mesh load, but never updated `OrbitControls.target`. `OrbitControls` (`makeDefault`) re-aims the camera at its own target (default `(0,0,0)`) on the next `update()`, silently discarding the `lookAt()` call. Because SWG meshes are anchored at the feet (not bbox-centered at the origin), this recentered the viewport on the feet and clipped the head out of the top of the frustum on every initial load — an explicit maintainer-reported bug ("the bottom of the mesh is centered..., clipping the top of the mesh").
- **Fix:** Read the active controls via `useThree((s) => s.controls)`; set `controls.target` to the computed bounds center (or `(0,0,0)` in the empty-box fallback) and call `controls.update()` after positioning the camera. The `framed` latch ref now only fires once `controls` exists (added to the effect's dependency array), so a mesh mounting a beat before `OrbitControls` registers still gets framed correctly on the next pass.
- **Files modified:** `packages/renderer/src/panels/viewport/StaticMeshView.tsx`, `packages/renderer/src/panels/viewport/SkinnedMeshView.tsx`
- **Verification:** Maintainer round-2 UAT, verbatim: "facing and framing look right now, approved". Renderer vitest suite (350/350) and `tsc --noEmit` both green after the fix.
- **Committed in:** `a06b98a` (Task 3 commit)

**2. [Rule 4-adjacent, but explicitly maintainer-requested in-task — not a unilateral architectural call] Default camera azimuth mirrored to match SIE**
- **Found during:** Task 3 (D-17 checkpoint, round 1 UAT)
- **Issue:** Maintainer reported the same (correctly-oriented, non-mirrored) mesh appeared to face "the opposite side" in our viewport vs. SIE's default view — screenshots showed the same front, viewed from opposite azimuths, not a mesh rotation problem.
- **Fix:** Mirrored the default camera position's azimuth quadrant from `+X/+Z` to `-X/+Z` (`center.x - dist*0.707` instead of `center.x + dist*0.707`; empty-box fallback `set(-3, 2, 3)` instead of `set(3, 2, 3)`) in both view files' `useAutoFrame`. `SWG_ORIENTATION` (mesh rotation) is untouched — this is purely a camera placement change.
- **Files modified:** `packages/renderer/src/panels/viewport/StaticMeshView.tsx`, `packages/renderer/src/panels/viewport/SkinnedMeshView.tsx`
- **Verification:** Maintainer round-2 UAT approval (see above).
- **Committed in:** `a06b98a` (Task 3 commit, same commit as fix #1 — same contiguous `useAutoFrame` edit in both files, not separable)

**3. [Rule 3 - Blocking, pre-existing/unrelated] vite.main.config.ts npm/pnpm start regression carried forward**
- **Found during:** Continuation session start (working tree already contained this uncommitted change when this continuation executor began; not introduced by this plan's tasks)
- **Issue:** 04.4-09 added an unconditional `MAIN_WINDOW_VITE_DEV_SERVER_URL: 'undefined'` / `MAIN_WINDOW_VITE_NAME` define block for CI's standalone (non-forge) vite builds. electron-forge's `ViteConfigGenerator` resolves the final build config as `mergeConfig(forgeConfig, userConfig)` with `userConfig` WINNING, so this unconditional define erased the live dev-server URL forge injects during `serve`/`start`, causing `main.ts` to fall back to the packaged `app://` path — which forge's dev `start` command never builds (its `preStart` hook `fs.remove()`s `.vite` entirely) — breaking every `pnpm start`/`npm start` boot with `ERR_FILE_NOT_FOUND`.
- **Fix:** `vite.main.config.ts`'s `defineConfig` is now a function of the config env; the two `MAIN_WINDOW_*` defines apply only when `forgeConfigSelf` is ABSENT from that env (the forge-only extension key set by `@electron-forge/plugin-vite`'s config resolution) — standalone/CI builds still get the defines they need; forge-driven builds no longer have them clobbered.
- **Files modified:** `vite.main.config.ts`
- **Verification:** Verified both paths — standalone build substitutes the tokens (0 unreplaced occurrences), and `pnpm start` boots clean under forge.
- **Committed in:** `2a751f1` (separate, unrelated commit — kept out of the Task 3 commit per proper scope separation; tagged `04.4-09` since that's the plan that introduced the regression, not `04.4-04`)
