# Phase 04.4 Plan 12: Server Push UI Wiring Summary

**Wired the 04.4-07 (Core3) and 04.4-08 (swg-main) server-push services into a real "Server Push" section in VcsPanel.tsx — Push/Reset buttons, disk-backed record rehydration, per-flavor post-push reload guidance, and a firm unconditional reset-then-clear-record contract.**

## Performance

- **Duration:** ~15 min
- **Completed:** 2026-07-04
- **Tasks:** 2 (combined into one commit — see Decisions)
- **Files modified:** 2 (1 modified, 1 created)

## Accomplishments

- `VcsPanel.tsx` now renders a "Server Push" section, visible only when the open workspace's
  `serverConfig` is set, showing `serverConfig.type` and `serverConfig.path` as read-only text.
- On mount (and whenever `serverConfig`/`studioDir` change), the panel calls
  `readCore3PushRecord`/`readSwgMainPushRecord` to rehydrate the last push record from disk —
  the Reset button is available immediately after a panel remount or app restart, not only
  within the session that performed the push.
- "Push to Server" is disabled with a visible "no saved version yet" reason when
  `manifest.activeVersionId` is null/undefined.
- `handleServerPush` dispatches on `serverConfig.type` using the frozen path contracts:
  Core3 `confDir = path.join(serverConfig.path, 'conf')`; swg-main `servercommonCfgPath =
  path.join(serverConfig.path, 'exe', 'shared', 'servercommon.cfg')`.
- After a successful push, per-flavor guidance renders: Core3 shows the restart-required copy
  (TreFiles is read once at boot); swg-main shows the reloadTable/reloadServerTemplate-or-restart
  copy — this closes the "push succeeded but server looks unchanged" gap called out in the
  RESEARCH.md ADDENDUM.
- `handleServerReset` calls `resetCore3TreOverride`/`resetSwgMainOverride` and THEN
  unconditionally calls `clearCore3PushRecordFile`/`clearSwgMainPushRecordFile` — the round-2
  locked contract, verified by a passing test asserting invocation order via
  `mock.invocationCallOrder`.
- All push/reset errors surface as inline `VerificationStatus` text (never silent).
- Added `VcsPanel.test.tsx` (8 tests) covering: section visibility gated on `serverConfig`,
  disk-backed rehydration, `activeVersionId` gating, both push dispatch paths + their exact
  guidance copy, reset-then-clear ordering, and error surfacing.

## Decisions Made

- **Combined Tasks 1-2 into a single commit.** Both tasks modify the same contiguous "Server
  Push" block added to `VcsPanel.tsx` in this plan — Task 1's UI/state scaffolding and Task 2's
  handler wiring are not separable without artificial churn (e.g. writing handlers as no-ops
  first, then filling them in a second commit, purely to satisfy a one-commit-per-task rule on
  code that was designed together). Both tasks' acceptance criteria are verified by the same
  test file.
- **`activeVersionId` and manifest reads happen directly in the render body / handler bodies**,
  not cached via a separate `useEffect`+`useState` pair. This matches the existing codebase
  convention (`ProjectListDialog.versionCountFor`, `DeleteUndoToast.safeChangesetCount`) of
  calling `readManifest`/derived best-effort helpers directly at the point of use rather than
  introducing a redundant cache that could go stale relative to other panels mutating the
  manifest.
