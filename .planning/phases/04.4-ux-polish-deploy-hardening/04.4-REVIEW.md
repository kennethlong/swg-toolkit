## Critical Issues

### CR-01: TRE name-block `fileNameOffset` is never bounds-checked — OOB read on hostile archives

**File:** `packages/native-core/modules/core/tre/TreArchive.cpp:282, 447, 464-472` (also consumed at `packages/native-core/modules/core/tre/TreBuilder.cpp:419` via `nameAt`)
**Issue:** `resolve()`, `resolveTombstoneIndex()`, and `nameAt()` all compute `m_nameBlock.c_str() + m_entries[mid].fileNameOffset` where `fileNameOffset` is a raw `int32` read from the archive TOC (`readLE32s(r + 20)` at line 248) with **no validation against `m_nameBlock.size()` and no negative check**. A hostile or corrupted `.tre` can set `fileNameOffset` to a negative value or a value far past the name block, producing an out-of-bounds read in `SWG_STRICMP` / `std::string` assignment — a renderer-process crash or info-leak primitive. This is inconsistent with the file's own threat-model discipline (T-01-01/02/03/19 caps are all enforced; this field alone is trusted). `TreBuilder::repack` amplifies it: `source.nameAt(e.fileNameOffset)` copies from the unvalidated offset into a new archive.
**Fix:** Validate at parse time (once, in `TreArchive::parse`'s TOC unpack loop):
```cpp
// after e.fileNameOffset = readLE32s(r + 20);
if (e.fileNameOffset < 0 ||
    static_cast<size_t>(e.fileNameOffset) >= nameData.size()) {
    throw std::runtime_error(
        "TreArchive::parse: TOC fileNameOffset out of name-block bounds (T-01-02)");
}
```
(Validating against `nameData.size()` before `m_nameBlock.assign` also guarantees every stored name is NUL-terminated within the block, since `std::string::c_str()` provides the terminal NUL at the block end.)

## Warnings

### WR-01: Effect.cpp reads SCAP capability levels big-endian; the client reads them little-endian — wrong `scapValues` and potentially wrong `bestImplIndex`

**File:** `packages/native-core/modules/core/formats/Effect.cpp:49-61, 347-353`
**Issue:** `parseImpl` reads SCAP entries via `readI32BE()` (explicit byte swap, justified by the comment "SCAP capability levels stored with htonl/ntohl"). Ground truth falsifies this: the real client reads SCAP with `iff.read_int32()` — a raw memcpy, i.e. **little-endian** on Windows (`../swg-client-v2/.../ShaderImplementation.cpp:375,435,494` + `Iff.h:575-580` `read_misc` raw copy) — exactly the same convention as the PTXM `textureTag` this file already handles as LE. The byte-swapped values are not order-preserving: e.g. `ShaderCapability(2,0)=0x00020000` swaps to `0x00000200` while `ShaderCapability(1,4)=0x00010004` swaps to `0x04000100`, **inverting** the "highest max SCAP" comparison at Effect.cpp:474-481, so a multi-IMPL effect can select a lower-capability IMPL (wrong samplers/blend for rendering). Existing tests don't catch it because the CI-enforced synthetic fixture has one IMPL and the real-fixture assertions never inspect `scapValues`.
**Fix:** Read SCAP with the LE reader and drop the BE variant (or keep it only where a chunk is genuinely ntohl-stored — none in this file):
```cpp
// SCAP chunk — client reads via iff.read_int32() (raw LE memcpy). NOT htonl/BE.
while (cv.bytesLeft() >= 4) {
    impl.scapValues.push_back(static_cast<int32_t>(cv.readU32LE()));
}
```
Also update the `readI32BE` doc comment (or delete the now-unused function) and Effect.h's IMPL-selection note.

### WR-02: CI Playwright steps use bash `\` line continuations in pwsh run blocks — steps fail on windows-latest

**File:** `.github/workflows/ci.yml:74-81` (and the same pattern risk at 148 if ever wrapped)
**Issue:** The workflow has no `defaults.run.shell`; on `windows-latest` the default `run` shell is **pwsh**, where a trailing `\` is not a line continuation. The step executes `pnpm playwright test --forbid-only \` (with a literal `\` argument), then attempts to run `e2e/01-boot.spec.ts \` etc. as standalone commands — the step fails regardless of test health, and the newly-added 06/07 specs never run in CI.

        shell: bash

### WR-03: Core3 push idempotent-replace regex can clobber ANOTHER project's mount line (slug prefix collision)

**File:** `packages/renderer/src/services/core3ServerPush.ts:311-324`
**Issue:** `toolkitLinePattern` matches `"swgtoolkit_${escapeRegex(safeSlug)}_[^"]*"`. Because `sanitizeToken` keeps `_` in slugs, project slug `my` produces the pattern `swgtoolkit_my_[^"]*` which ALSO matches project `my_proj`'s line `table.insert(Core3.TreFiles, 1, "swgtoolkit_my_proj_ab12cd34.tre")`. When two projects push to the same Core3 server, the shorter-slug project's push silently **replaces the other project's insert line** (and its `.replace` is non-global, so only the first match — nondeterministic which). The other project's archive stays on disk but is no longer mounted, and its own record now points at a line that no longer exists.
**Fix:** Match the exact prior line from the persisted record instead of a slug-prefix regex:
```ts
const prior = readCore3PushRecord(studioDir);
const priorLinePattern = prior
  ? new RegExp('^[\\t ]*' + escapeRegex(prior.insertedLine) + '[\\t ]*$', 'm')
  : null;
if (priorLinePattern && priorLinePattern.test(existing)) {
  newConfigLocalContent = existing.replace(priorLinePattern, insertedLine);
} else { /* append */ }
```
(You already read `priorRecord` at line 290 — reuse it.)

### WR-04: `deleteProject` can throw from the `.complete.json` write, violating its own "never thrown (D-05)" contract

**File:** `packages/renderer/src/services/deleteProject.ts:132-149`
**Issue:** Both renames are individually try/caught, but the completion-marker `fs.writeFileSync` at line 139 is not. A disk-full/permission error there propagates out of `deleteProject()` — after both renames already succeeded — so the caller (modal `onConfirm`) sees an exception, the toast/undo entry IS pushed but the recents entry is never removed (`removeRecentProject` at line 167 is skipped), leaving a recents row pointing at a now-parked folder. The function's contract is "non-fatal per-step failures, never thrown".
**Fix:** Wrap the marker write; on failure, fall into the same "no marker" degraded path:
```ts
if (studioMoved && projectMoved) {
  try {
    fs.writeFileSync(path.join(entryDir, '.complete.json'), JSON.stringify(completeMarker));
  } catch (e) {
    restoreErrors.push(`Failed to write completion marker: ${String((e as Error)?.message ?? e)} — entry will not be auto-purged.`);
  }
}
```

### WR-05: `restore()` on a partially-parked entry half-restores and then bricks the retry

**File:** `packages/renderer/src/state/deleteUndoStore.ts:100-134` (interacts with `deleteProject.ts:151-163`)
**Issue:** `deleteProject` pushes a `TrashEntry` even when only ONE of the two renames succeeded (verified by design in deleteProject.test.ts case K). `restore()` checks both **destinations** but never checks that both **sources** exist. For a studio-moved/project-move-failed entry: `renameSync(trashStudioPath, ...)` succeeds, then `renameSync(trashProjectPath, ...)` throws ENOENT — the entry stays in `pending` (the `set` filter never runs), but a retry now fails the `fs.existsSync(entry.originalStudioDir)` occupied-destination guard **forever**, with a misleading "already exists; move or remove it" message about a directory restore itself just created. The Undo toast offers this dead-end Undo for every partial park.
**Fix:** Pre-check source existence and restore only the halves that were actually parked:
```ts
const studioParked  = fs.existsSync(entry.trashStudioPath);
const projectParked = fs.existsSync(entry.trashProjectPath);
if (studioParked)  fs.renameSync(entry.trashStudioPath,  entry.originalStudioDir);
if (projectParked && !entry.umbrellaMoveSkipped)
  fs.renameSync(entry.trashProjectPath, entry.originalFolderPath);
```
(And only run the occupied-destination guards for the halves that are parked.)

### WR-06: `syncLiveToVersion` loose revert silently no-ops when `ctx.priorLiveLooseRecord` is omitted, even though the live changeset's own loose record is in hand

**File:** `packages/renderer/src/services/syncLiveToVersion.ts:242-248, 310-313`
**Issue:** `liveModel` is derived from `liveDeployRecord` having `overrideDir` (line 183-188), but the Baseline revert (line 246) and the loose→cfg cross-model reset (line 311) execute `resetLoose` **only** when `ctx.priorLiveLooseRecord` was passed. If a caller supplies the manifest (which carries the loose record on the live changeset) but not the ctx field, the revert is skipped with no error — the client keeps the stale loose overrides while `deployedVersionId` moves to Baseline. DeployDialog happens to pass the same record via `deployRecordRef`, but that rehydration can miss (manifest unreadable at dialog-open, `deployedVersionId` unset) and other callers (e.g. the Undo path) must each re-implement the plumbing.
**Fix:** Fall back to the live record already resolved in this function:
```ts
const liveLoose = (liveDeployRecord && 'overrideDir' in liveDeployRecord)
  ? (liveDeployRecord as LooseDeployRecord)
  : priorLiveLooseRecord;
...
if (liveModel === 'loose' && liveLoose) resetLoose(liveLoose);
```

### WR-07: `parsePassData` short-chunk guard (14) is smaller than the bytes actually consumed (17) — throws instead of defaulting

**File:** `packages/native-core/modules/core/formats/Effect.cpp:306-326`
**Issue:** The guard `if (cv.bytesLeft() < 14) return blend;` is documented as "too short to be valid — return defaults", but the function consumes **17** bytes (5 skips + zWrite + zCompare + 4 blend reads + alphaTestEnable + skip(4) + alphaTestFunc). A DATA chunk of 14-16 bytes passes the guard, `skip(4)` clamps to end, and the final `readI8()` throws `FormatParseError` — which propagates out of `parseEffect()` and fails the whole effect instead of yielding the intended opaque-default blend.
**Fix:** `if (cv.bytesLeft() < 17) return blend;` (or wrap the reads in try/catch returning `blend`).

### WR-08: `efctChunkPayload` bounds check can wrap on 32-bit arithmetic

**File:** `packages/native-core/modules/core/formats/Effect.cpp:79-88`
**Issue:** `payloadStart + payloadLen > srcSize` is `uint32 + uint32` — a corrupted `declaredLength` near `UINT32_MAX` wraps the sum below `srcSize`, passing the check and creating a chunk view that reads far past the source buffer (all EFCT chunk readers then read OOB). Whether Iff.cpp pre-validates child extents or not, this parser takes raw `srcData/srcSize` and should not rely on it.
**Fix:**
```cpp
const uint64_t end = static_cast<uint64_t>(leaf.byteOffset) + 8ull + leaf.declaredLength;
if (end > srcSize) throw FormatParseError("efctChunkPayload: chunk extends beyond source buffer");
```

### WR-09: Negative TOC `offset` bypasses the T-01-02 bounds guard in `extractEntry` and `repack`

**File:** `packages/native-core/modules/core/tre/TreArchive.cpp:334-341`; `packages/native-core/modules/core/tre/TreBuilder.cpp:436-446`
**Issue:** `e.offset` is a signed `int32` from the TOC. In `extractEntry`, the guard `static_cast<int64_t>(e.offset) > streamLen - readLen` passes for any negative offset (negative < positive), and `stream.read(e.offset, ...)` is then called with a negative offset — behavior depends entirely on the `IInputStream` implementation (a memory-backed stream would index before the buffer). `repack` has the same shape (`e.offset + readLen > sourceSrcLen` with negative offset passes). `extractAt` was already hardened for exactly this (F-5, unsigned-safe form at lines 370-383); the two older call sites were not.
**Fix:** Add `e.offset < 0` to both guards (or convert to the same unsigned subtraction form used by `extractAt`).

### WR-10: `treInflate` documents Adler-32 validation it does not perform

**File:** `packages/native-core/modules/core/compress/Zlib.h:46` (contract), `packages/native-core/modules/core/compress/Zlib.cpp:72-101` (implementation)
**Issue:** `Zlib.h` declares "`@throws std::runtime_error on inflate failure, bad Adler32, or cap exceeded`" and Zlib.cpp's header cites Utinni's "Adler32 validation at :679" as ported behavior — but the implementation strips the 2-byte header AND the 4-byte Adler trailer and raw-inflates (`-MAX_WBITS`), so the checksum is **never** verified. A corrupted code-2 payload whose deflate stream stays parseable decodes to silent garbage on the `extractEntry` path (the `extractAt` path has the independent F-4 length gate; `extractEntry` has nothing). Callers relying on the documented throw get no signal.
**Fix:** Either compute `adler32()` over the produced output and compare against the stored trailer (the vendored zlib exports `adler32`), or correct the Zlib.h contract + Zlib.cpp provenance comments to state explicitly that Adler validation is intentionally skipped and why.

### WR-11: logService's VITEST guard compares against `'1'` but Vitest sets `VITEST='true'` — the guard never fires

**File:** `packages/renderer/src/services/logService.ts:88-106` (contrast `packages/renderer/src/panels/ConsolePanel.tsx:31`)
**Issue:** The 04.4-11 main-log subscription is guarded by `process.env['VITEST'] !== '1'`, with a comment claiming it "matches 04.4-02's own idiom exactly, so it protects logService.test.ts's DIRECT call". Vitest sets `VITEST='true'`, and ConsolePanel's actual idiom is the truthy check `!process.env['VITEST']`. `'true' !== '1'` is always true, so the subscription IS attempted during every vitest run — it only survives by accident (in a non-Electron process, `require('electron')` resolves to the binary-path string, destructuring yields `undefined`, and the `ipcRenderer?.on?.` optional chain no-ops). The guard is dead code and the comment is false.
**Fix:** `if (typeof process === 'undefined' || !process.env['VITEST']) { ... }` — matching ConsolePanel.tsx:31.
