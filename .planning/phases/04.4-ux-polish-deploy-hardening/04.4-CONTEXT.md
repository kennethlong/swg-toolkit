## Implementation Decisions

### Delete UX & undo surface
- **D-01:** Delete affordance in BOTH ProjectListDialog rows AND the Welcome screen recents rows
  (WorkspaceEntry). Destructive-action styling.
- **D-02:** **Sketch-first (maintainer) — DONE 2026-07-03:** sketch **017-delete-project-flow**
  built and approved, **winner = Variant B (kebab menu + inline dimmed recoverable rows)**. The
  sketch is the UI contract for the delete surface (sketch 007 does not govern this element).
  Plans MUST name sketch 017 and enumerate its elements as must_haves: per-row ⋯ kebab (Open ·
  Reveal studio folder · Delete project…) on BOTH surfaces, descriptive confirm modal with
  numbered plan lines, undo toast (8s, ⚠ restore-failure variant), inline dimmed dashed
  struck-through recoverable rows with Restore.
- **D-03:** Confirm = descriptive modal listing exactly what will happen (client cfg restored /
  loose overrides reverted per deploy records, project parked for session-undo), Delete/Cancel.
  NOT type-project-name. Per sketch 017: numbered plan lines vary by deploy model (cfg restore /
  loose revert / never-deployed "nothing to restore") + amber "currently open — workspace will
  close" line when applicable.
- **D-04 (REVISED by sketch 017 winner, 2026-07-03):** Undo surface = transient toast with Undo
  button immediately after delete PLUS **inline dimmed rows**: the deleted project stays in place
  in ProjectListDialog as a dimmed/dashed/struck-through row with a Restore button ("deleted just
  now · N versions parked") until app close — **the row IS the trash entry; no separate
  "Recently deleted" section** (the section idea from discussion was superseded by the approved
  sketch). (Undo stack semantics per the todo: session-scoped, purged at shutdown + stale-trash
  purge on next startup.)
- **D-04a (maintainer ruling, 2026-07-03, post-review):** Undo restores the parked project
  bytes only — it does **NOT** re-deploy/re-apply anything to the client. This overrides the
  sketch-017 demo's toast copy for the deployed-project case (`index.html` `restoreProject()`
  shows "deploy re-applied to client"), which is hereby the ONE known, intentional divergence
  from the sketch contract. Explicitly confirmed by the maintainer ("no re-deploy on undo
  confirmed") after the cross-AI review round surfaced the contradiction. Locked identically
  in plans 04.4-01 / 04.4-10 / 04.4-14; undo toast/copy must not imply a re-deploy.
- **D-05 (from todo, locked 2026-06-29, not re-asked):** restore-client-first order;
  `.trash` parking (no hard rm); deleting the currently-open project closes workspace → Welcome;
  restore steps non-fatal per-step but failures surfaced; never-deployed project = park only,
  no cfg I/O.

### E2E scope & test seams
- **D-06:** Fixture client trees for BOTH deploy models: a cfg-model fixture (minimal
  `swgemu.cfg` + searchTree layout) AND a loose-override fixture (dev-client searchPath dir).
  Never a real install.
- **D-07:** Spec scenarios re-based on the 04.3 model (select = silent reconcile via
  `syncLiveToVersion`; Deploy dialog only for NEW versions). The todo's pre-04.3 scenario sketch
  (Section C slot preview etc.) is superseded where it conflicts — the loop to drive is:
  boot(zero console errors) → non-workspace-folder UI feedback → new project → stage →
  save version → select/reconcile → deploy → revert.
- **D-08:** SWG_TEST_MODE hook surface = **spec-driven, MCP-shaped**: build only the hooks these

  coherent env-gated surface the future MCP server consumes as-is (extends the `window.__*`
  pattern; memory `design-test-hook-points-for-harness`). Never shipped live.
- **D-09:** Project-delete flow gets its OWN real-Electron spec: delete → confirm →
  client-pristine assert → undo → restored, against the fixture tree.
- **D-10:** Console gate strictness = fail on error-level (`console.error` + `pageerror`);
  warnings logged but allowed.
- **D-11 (context, not re-asked):** CI lean job (windows-latest) already runs non-packaged
  Playwright on every push — new specs join it; ensure build-before-E2E so specs run against a
  renderer bundle built from current source.

### Console/Log tabs
- **D-12:** Tab semantics: **Console = dev stream** (mirrored `console.*`, window errors,
  unhandled rejections — replaces DevTools for basic diagnosis); **Log = structured app events**
  (mounts, deploys, reconciles, injections, restores) with levels.
- **D-13:** Capture scope = renderer + main: renderer `console.*` wrap + an IPC channel
  forwarding main-process log lines.
- **D-14:** Instrument key services this phase: small `logService`; the deploy/reconcile/mount/
  delete paths this phase touches emit structured events so the Log tab is useful on day one.
- **D-15:** MVP features = lean: ring buffer (~2k entries), autoscroll with pause-on-scroll-up,
  level color coding, Clear button, copy-line. No search/filter UI yet.

### Viewport / statusbar / VFS polish

  (mirrors io_scene_swg_msh `axis_forward='Z', axis_up='Y'`). Camera/grid/orbit untouched; static

  — do not conflate.)
- **D-17:** Facing verification = human-verify checkpoint (autonomous:false): maintainer eyeballs

- **D-18:** Statusbar = straight fix: bind to active mesh (name + summed verts for the shown LOD)

### Product-thesis remaining scope (folded)
- **D-20:** Close-out audit: verify the todo's realized claims against shipped code (lazy shadow,
  cfg snapshot/restore, B3 loose snapshot, baseline node, reconcile-to-version), record the locked
  decisions in docs/memory, then retire the todo.
- **D-21:** Pluggable TRE codec interface: refactor the TRE read/write path in native-core behind

- **D-22:** Server TRE push = **ground-truth AND implement** (maintainer, 2026-07-03): investigate
  how Core3 (`../Core3`, WSL2) and swg-main (`../swg-main`, Docker) configure their TRE/data
  search paths using their REAL configs as evidence (#1-constraint rules apply — real source/
  configs, not docs), write verified findings into `docs/05-server-integration`, AND ship a
  working server deploy target that registers the override archive into at least one server
  flavor's TRE config with restore-on-reset (server-side analog of `cfgActivator`).
- **D-23:** This supersedes STATE.md's "server TRE search-path deferred to Phase 8" note for the
  push mechanism itself; deeper server integration (template sync etc.) remains later-phase.
- **D-24:** Server-push mounts (maintainer, 2026-07-03, mount-research pass): both server flavors
  run in Linux (Core3 in WSL2, swg-main in the official SWGSource VirtualBox VM) and the toolkit
  targets their LIVE trees via host-visible mounts — Core3 via `\\wsl.localhost\<distro>\...` UNC
  (TRE copy leg usually lands on a plain Windows path because the maintainer's `config-local.lua`
  sets `TrePath=/mnt/d/...`), swg-main via the VM's Samba share (`\\<vm-ip>\SWG\swg-main`). The
  toolkit **walks users through the mount setup** (docs walkthroughs in
  `docs/05-server-integration/*` + wizard/UI copy) rather than adding an SSH/exec transport this
  phase. Per-flavor reload semantics are source-verified and surfaced as mandatory post-push UI
  copy (Core3: restart required; swg-main: live for new assets, `reloadTable`/
  `reloadServerTemplate` for loaded ones). Full evidence: 04.4-RESEARCH.md ADDENDUM.

## Existing Code Insights

### Reusable Assets
- **Restore machinery (delete reuses, does NOT rebuild):** `cfgActivator.restoreCfg` /
  `deactivatePatch` (cfg models), `looseOverrideDeploy.resetLoose` (B3 snapshot) — exactly what
  the Deploy dialog's Reset uses.
- **Session undo stack (04.3 D-06)** already backs reconciles — the delete undo mirrors its
  session-scoped pattern (park in `studios/.trash/<id>-<token>/`).
- **Console/Log panels exist** (`panels/ConsolePanel.tsx`, `panels/LogPanel.tsx`, registered in
  `WorkspaceShell.tsx:77-78` as dockview ids `console`/`log`) — seeded stubs to wire, not new tabs.
- **`window.__*` proof-hook pattern** (StatusBar.tsx owner, consumed by e2e/) — the seed of the
  SWG_TEST_MODE surface (D-08).
- **`packPatch(flatten(activeVersionId))`** — the override archive the server deploy target (D-22)
  registers server-side.
- **StatusBar.tsx** (`packages/renderer/src/shell/StatusBar.tsx`) + `useViewportStore` — D-18.
- **VfsTree.tsx:360** — the exact line for the dim-label fix.

### Established Patterns
- Sketches are the UI contract — D-02 makes the delete flow sketch-first.
- Env-gated test hooks, never shipped live (`SWG_TEST_MODE`).
- Native addon statically links zlib — codec-interface refactor (D-21) must preserve this.
- e2e specs run against a BUILT renderer bundle — build-before-E2E required (D-11).
- Append-only history invariant (changesetService) extends to delete: nothing destroyed, only parked.

### Integration Points
- `deleteProject` service → ProjectListDialog + WorkspaceEntry rows; workspace close path when
  deleting the open project.
- logService → renderer console wrap + main-process IPC forward + deploy/reconcile/mount/delete
  service emit points → ConsolePanel/LogPanel.
- Facing rotation → the scene group in StaticMeshView/SkinnedMeshView/Viewport (one shared group).
- Codec interface → native-core TRE read/write path (TreArchive extract/pack).
- Server deploy target → new service parallel to `cfgActivator`, driven by the same deploy records.
