## Summary

This phase clears eight small-to-medium hardening items across a codebase that is otherwise stable and well-tested (272 renderer tests green per STATE.md). The two "high" items — delete-with-restore and E2E deploy coverage — both hinge on architecture that already exists and should be **reused, not rebuilt**: the deploy-record shape (`CfgDeployRecord` / `LooseDeployRecord`) persisted in `manifest.json` per changeset already carries everything needed to restore a client to stock (including `includeTargetPath`, the root cfg path — so delete does NOT need the workspace to be open or `selectedClient` state to run a restore), and the existing Playwright harness (`electron-helpers.ts`, `04-workspace.spec.ts`) is a solid pattern to extend, but has a **verified, real infrastructure gap**: CI's lean job runs `playwright test` directly with no Vite/Forge build step beforehand, while the renderer bundle it depends on (`.vite/build/main.js`, `.vite/renderer/main_window/`) is gitignored and not produced by any lean-job step today. This must be fixed as part of `e2e-deploy-flow-coverage` (confirms D-11's premise was correct, not hypothetical).

Three items are effectively "finish what's stubbed": Console/Log panels are already registered dockview tabs (not broken/unselectable as the stale symptom claims) — the only work is a `logService` + wiring, not new panel plumbing. The status-bar mesh-name bug is **not** a stale-binding bug — `StatusBar.tsx` renders a **literal hardcoded string** (`shared_landspeeder.msh`, `4,812 verts`) with no store subscription at all; this is a from-scratch wire-up, not a fix. The VfsTree dim-label fix is confirmed safe: only two theme files (`default.css`, `high-contrast.css`) define `--color-text-muted`/`--color-text-faint` at all (the other three inherit or override only accent tokens), and in both, `--color-text-muted` is meaningfully lighter — no new token is needed.

The viewport facing-axis fix has real history to account for: `StaticMeshView.tsx` and `SkinnedMeshView.tsx` each already have a `SWG_ORIENTATION` constant that was **rotated 180° on Y, found wrong (showed the mesh's back), and reverted to identity** — this is documented in the current source comments. The plan must not blindly reapply `rotateY(Math.PI)`; it needs a different hypothesis (grounded in io_scene_swg_msh's `axis_conversion(to_forward='Z', to_up='Y')`, which is a Blender-axis conversion and not a drop-in Three.js rotation), gated on the mandated D-17 human-verify checkpoint. The duplicated `SWG_ORIENTATION` constant in both view files is also a DRY opportunity the plan should take (one shared module).

The biggest research payoff was ground-truthing the two server flavors for D-22: **Core3 and swg-main use completely different mechanisms**, and the "server-side cfgActivator" framing in the todo only fits one of them. Core3 (`MMOCoreORB/bin/conf/config.lua`) has an explicit `Core3.TreFiles` ordered array + `TrePath`, loaded via `DataArchiveStore::loadTres` in list order (index 0 = highest priority, confirmed against the array's own ordering: `default_patch.tre` first, `bottom.tre` last) — and `conf/config-local.lua` is parsed by the **same Lua VM** after `config.lua` (`ConfigManager.cpp:33-44`), so a non-destructive override can `table.insert(Core3.TreFiles, 1, "swgtoolkit_override.tre")`, an exact mechanistic analog of our own `.include`/`ensureInclude` pattern. swg-main (`exe/shared/servercommon.cfg`), by contrast, has **no TRE archives at all server-side** — it reads directly from loose compiled data directories via `[SharedFile] searchPath0/1/2=` pointing at `data/sku.0/sys.*/{compiled,built}/...` — so its "deploy target" is architecturally a **loose-file override** (closer to our existing `looseOverrideDeploy.ts` pattern) than a TRE-archive push.

**Primary recommendation:** Reuse the deploy-record dispatch pattern from `DeployDialog.handleReset` verbatim for delete (dispatch on record SHAPE, not a model enum); fix the CI build gap as the first task of the E2E work (it blocks everything else in that todo); implement the Core3 and swg-main server pushes as two genuinely different services (Lua-array injection vs. loose-file write) rather than one shared abstraction; and treat the viewport facing fix as a research-then-verify loop, not a single-shot rotation constant change.

### Viewport facing-axis fix (D-16/D-17) — current state and the trap to avoid

**Current code (verified 2026-07-03):**
```typescript
// StaticMeshView.tsx:58 and SkinnedMeshView.tsx:77 — DUPLICATED, both identity today
const SWG_ORIENTATION = new THREE.Euler(0, 0, 0);
```
Both files' comments explicitly document that a **180° Y rotation was already tried and reverted**: "The 180° Y guess showed the model's back... Identity here keeps winding/normals correct." This means:

1. **Do not reapply `rotateY(Math.PI)`** as the first hypothesis — it was already tried in Phase 02-03 and produced the wrong result (mesh's back facing the camera).
2. The ground-truth reference (`io_scene_swg_msh/io_scene_swg/__init__.py:332`, `@orientation_helper(axis_forward='Z', axis_up='Y')`) computes its `global_matrix` via **Blender's `axis_conversion(to_forward='Z', to_up='Y')`**, applied via `mesh.transform(global_matrix)` directly to raw imported SWG vertex data (`import_mgn.py:117`). This is a Blender-internal axis-remap (converting raw SWG-authored coordinates into Blender's own default display axes: `-Y` forward, `+Z` up) — it is **not** a matrix that drops in unchanged as a Three.js `group.rotation`, because Three.js's own default axes (`Y`-up, camera looks down `-Z`) differ from Blender's defaults along a different pair of axes. The plan must derive the equivalent Three.js-space rotation mathematically (or empirically iterate) rather than transcribing the Blender Euler values directly.
3. D-17 already accounts for this uncertainty by gating closure on a **human-verify checkpoint** (protocol_droid_red + one more asymmetric mesh, side-by-side with SIE) — the plan should treat this as an iterate-and-verify task, not a one-shot constant change, and should budget for at least one wrong-guess cycle given the documented history of the first attempt.
4. **DRY opportunity:** since `SWG_ORIENTATION` is duplicated verbatim in both `StaticMeshView.tsx` and `SkinnedMeshView.tsx`, the plan should extract it to a single shared module (e.g. `viewport/orientation.ts`) so the eventual fix only needs to change one place and both static + skinned meshes stay in sync (D-16 explicitly requires both to inherit the same fix).

### Server TRE/data push — Core3 vs swg-main (D-22) are architecturally DIFFERENT mechanisms

**Core3 (WSL2) — TRE-array injection, closely analogous to `cfgActivator`:**
```
MMOCoreORB/bin/conf/config.lua:
  Core3.TrePath = "/home/swgemu/Desktop/SWGEmu"
  Core3.TreFiles = { "default_patch.tre", "patch_sku1_14_00.tre", ..., "bottom.tre" }
```
- `ConfigManager::loadConfigData()` (`ConfigManager.cpp:33-44`) runs `conf/config.lua` first, then **conditionally** runs `conf/config-local.lua` (only if it exists — `File::setReadOnly()` guards it) **in the SAME Lua VM** — so `config-local.lua` can mutate the already-populated `Core3` table without redeclaring it.
- `DataArchiveStore::loadTres(path, treFilesToLoad)` (`DataArchiveStore.cpp:56-88`) iterates `treFilesToLoad` **in array order** and calls `treeDirectory->unpackFile(path + "/" + file)` for each — the array's own contents (`default_patch.tre` first = newest/highest-priority patch, `bottom.tre` last = oldest base data) confirm **index 0 = highest priority**.
- **Non-destructive server push mechanism (mirrors our own `.include`/`ensureInclude` pattern):** write/append to `conf/config-local.lua` a Lua statement that prepends our override archive:
  ```lua
  table.insert(Core3.TreFiles, 1, "swgtoolkit_<project>.tre")
  ```
  and copy/place the built override `.tre` into `Core3.TrePath` (or point `TrePath` at a toolkit-writable dir via the same config-local.lua file — needs a design decision during planning). Restore-on-reset = remove our `table.insert` line (or the whole config-local.lua if toolkit-authored) — same append-not-overwrite discipline as `workspaceService.ts`'s pre-commit hook pattern.
- **Environment note:** this file lives on the WSL2 filesystem (`../Core3` per AGENTS.md). Writing to it from the Windows Electron renderer means either a `\\wsl$\<distro>\...` UNC path or the mapped drive the maintainer's WSL2 setup exposes — this is environment-specific and should be confirmed with the maintainer at plan time (see Open Questions).

**swg-main (Docker) — loose-file override, closely analogous to `looseOverrideDeploy.ts`:**
```
exe/shared/servercommon.cfg:
  [SharedFile]
  searchPath2=../../data/sku.0/sys.shared/compiled/game/
  searchPath2=../../data/sku.0/sys.server/compiled/game/
  searchPath1=../../data/sku.0/sys.shared/built/game/
  searchPath1=../../data/sku.0/sys.server/built/game/
  searchPath0=../../data/sku.0/sys.client/compiled/clientdata/
```
- **There is no `.tre`/TRE-archive concept anywhere in the swg-main server config** — it is a from-source SWG server build that reads game data directly from the **loose compiled source tree** via `[SharedFile] searchPath0/1/2=` (note: this is the exact same `[SharedFile]` section format as the CLIENT cfg the toolkit already parses via `clientLocator.ts`/`cfgActivator.ts` — same underlying `ConfigFile.cpp`-family code shared between client and server builds).
- Note the file has **two `searchPath2=` lines with different values** (`sys.shared/compiled/game` and `sys.server/compiled/game`) — multiple values under the same numeric key stack (both are loaded at that priority tier); this repeats the client-side `[SharedFile]` multi-value-per-key pattern already handled by `scanSharedFile` in `clientLocator.ts` — that existing parser is a strong candidate to reuse/extend for the server cfg rather than writing a second one.
- **Push mechanism:** write staged/modded files directly into the highest-priority server data directory (need to confirm empirically whether `searchPath2` beats `searchPath0` the same LAST-wins-or-highest-number-wins way as the client — the memory `TreeFile searchTree precedence` notes "priority DESC wins" for the client; the server almost certainly shares the same `ConfigFile.cpp` resolution code, so treat this as the working hypothesis but verify against `servercommon.cfg`'s actual runtime behavior or `ConfigFile.cpp` if time allows). This is architecturally a **server-side `looseOverrideDeploy`**, not a TRE push — the existing `looseOverrideDeploy.ts` (B3 snapshot + non-destructive write + resetLoose) is the direct pattern to port, targeting the server's data dir instead of a client `searchPath` dir.
- **Environment note:** no docker-compose file exists inside the `swg-main` repo itself — the Docker orchestration is external to this repo (per AGENTS.md, the maintainer runs it separately). The actual bind-mount / volume path the toolkit would need to write into is **not discoverable from the repo alone** and must be confirmed with the maintainer (see Open Questions).

**Conclusion for planning:** D-22 cannot be implemented as a single shared "server deploy target" abstraction across both flavors — Core3 needs Lua-array injection + `.tre` file placement; swg-main needs loose-file writes into a compiled-data directory. Recommend implementing them as two independent services from the start (per Claude's Discretion: "which server flavor first, second if cheap else follow-up todo" — given the mechanisms are this different, treat "cheap" generously; a genuinely shared abstraction is not the right target).

### Native-core TRE codec pluggability (D-21)

The natural refactor seam already exists as an isolated function: `treInflate(compressor, src, srcLen, declaredUncomp)` in `packages/native-core/modules/core/compress/Zlib.h`/`.cpp`.     throw std::runtime_error("TreBuilder::build: V6000 is enumerate-only ...");

D-21's "pluggable codec interface" should wrap `treInflate`/an eventual `treDeflate` behind a small interface (e.g. a `TreCodec` abstract struct with `inflate`/`deflate` methods, a default `ZlibCodec` registered for 0004/0005, and a registration point a fork could extend) rather than restructuring `TreArchive`/`TreBuilder` themselves — those callers stay the same, only the compression call becomes indirect. ## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---|---|---|---|
| Client-cfg restore-to-pristine | A new "undo the cfg edit" routine for delete | `cfgActivator.restoreCfg(rootCfgPath, snapshotPath)` (whole-file, byte-pristine) with `deactivatePatch` as the no-snapshot fallback — exact same dispatch `DeployDialog.handleReset` already uses | Two restore code paths for the same operation is exactly the kind of drift that produced the W9 line-surgery bug this project already fixed once; reuse the proven dispatch |
| Loose-override restore | A new "revert the searchPath files" routine | `looseOverrideDeploy.resetLoose(record)` (B3 restore-or-delete per `preExisted`) | Same rationale — already correct and tested |
| Session-scoped undo stack | A generic in-memory undo/redo framework | A simple `.trash/<id>-<token>/` move + a small Zustand-backed list of pending trash entries, purged on `before-quit` | D-05/D-04 scope this narrowly (session-only, single delete-undo use case) — a general undo framework is over-engineering for one operation |
| Console/Log ring buffer | A logging library (winston/pino/loglevel) | A ~30-line hand-rolled fixed-size array ring buffer in a Zustand store | D-15 explicitly scopes this lean (~2k entries, no search/filter yet); a full logging library is unnecessary weight for a renderer-local ring buffer feeding two dockview panels |
| Server TRE/data push | A generic "server adapter" plugin system | Two concrete services (`core3ServerPush.ts`, `swgMainServerPush.ts` or similar) each targeting their real, verified mechanism | The two flavors' mechanisms are fundamentally different (Lua-array vs. loose-file); a premature abstraction would either leak Core3-isms into swg-main or vice versa |
| PTXM sampler parsing | A generic "shader binary reader" | Follow the existing `parseEffect`/`ShaderImplementationPassStage` parsing conventions already in native-core for FORM/chunk traversal | Matches the project's established IFF-parsing idiom (byte-exact round-trip discipline, CORE-05 harness) |

**Key insight:** every "high" item in this phase is dominated by risk of **re-deriving already-correct logic** (delete re-implementing restore, a new undo framework, a new ring-buffer dependency) rather than risk of missing functionality. The plan should bias hard toward "call the existing function" over "write a parallel implementation."

## Common Pitfalls

### Pitfall 1: CI's E2E job has no build step before `playwright test` — a real, present gap
**What goes wrong:** `.vite/build/main.js` (the Electron main entry, `package.json#main`) and `.vite/renderer/main_window/` (the renderer bundle served via `app://`) are gitignored (`.gitignore:11` — `.vite/`) and are only produced by Electron Forge's Vite plugin during `electron-forge start`/`package`/`make`. `ci.yml`'s `lean` job runs `pnpm playwright test --forbid-only e2e/01-boot.spec.ts ...` directly, with **no prior build step** — it does not call `pnpm start`, `pnpm package:ci`, or any raw `vite build` invocation.
**Why it happens:** `playwright.config.ts`'s own comments are internally contradictory (one block says a `webServer` config starts the Vite dev server at `localhost:5173`; a later block says "NOTE: webServer is NOT configured here" and describes the `app://` protocol reading from `.vite/renderer/main_window/`) — this is stale documentation drift, not a deliberate two-mode design. The actual config has no `webServer` entry.
**How to avoid:** Add an explicit lean build step to `ci.yml` before the E2E step — the fast option is running the three underlying `vite build` commands directly (`vite build -c vite.main.config.ts`, `vite build -c vite.preload.config.ts`, `vite build -c vite.renderer.config.ts`) rather than the full `electron-forge package` (which the lean job's own comments say to deliberately avoid, since it's slow/native-rebuild-heavy). This is squarely what D-11 ("ensure build-before-E2E") already flagged — this research confirms it is a real, currently-unaddressed gap, not a hypothetical one.
**Warning signs:** If a NEW e2e spec (e.g. `06-delete-flow.spec.ts`) is added without this fix, it will either (a) fail to launch Electron at all in a clean CI checkout, or (b) silently run against a stale `.vite/` output left over from a previous local run if the runner's workspace isn't clean — both are worse than an obvious immediate failure.

### Pitfall 2: The viewport facing-axis fix has a documented false start — don't repeat it
**What goes wrong:** Reapplying `rotateY(Math.PI)` (180° Y) as the "obvious" SWG→viewer rotation. This was already tried in an earlier phase and reverted — both `StaticMeshView.tsx` and `SkinnedMeshView.tsx` currently ship `SWG_ORIENTATION = new THREE.Euler(0, 0, 0)` (identity) specifically because 180°Y showed the mesh's back.
**Why it happens:** The io_scene_swg_msh ground truth (`axis_forward='Z', axis_up='Y'`) is easy to misread as "just rotate 180 on Y" without checking that Blender's `axis_conversion` output is being applied to convert INTO Blender's own default axes (`-Y` forward, `Z` up) — a different reference frame than Three.js's defaults (`Y` up, camera down `-Z`) — so the two systems' "obvious" fixes are not the same rotation.
**How to avoid:** Treat this as an iterate-and-verify task from the start (consistent with D-17's mandated human-verify checkpoint) — budget at least one wrong-guess cycle, and extract the duplicated `SWG_ORIENTATION` constant into one shared module first so subsequent guesses only require a one-line change in one place.
**Warning signs:** If the plan's task for this todo has no verification/iteration step and treats it as "apply the known-correct rotation," that's a sign the plan re-derived the already-falsified 180°Y hypothesis.

### Pitfall 3: Status-bar mesh-name "fix" scoped as a binding fix will under-estimate the work
**What goes wrong:** Treating D-18 as "find the stale binding and point it at the right store field" — there is no binding to find; `StatusBar.tsx:245-247` is hardcoded JSX text with zero store subscription.
**Why it happens:** The original todo's framing ("bound to a stale source... probably the first/last SAB-proof mesh") is a plausible-sounding guess that turned out to be wrong; the actual code never wired this up at all (it's Phase-0-era seed/proof content that was never replaced).
**How to avoid:** Scope the task as "add a `useViewportStore` subscription" (name from `loadStatus.filename`, vert count summed across `parsedMesh.shaderGroups[].vertexCount`), not "fix the binding."
**Warning signs:** none really — this is a small, contained fix either way, but under-scoping it in the plan (as "one-line change") could produce a task with no acceptance test for the actually-new subscription logic.

### Pitfall 4: Server TRE push — one shared "server deploy target" abstraction across Core3 + swg-main
**What goes wrong:** Building a single service interface (e.g. `serverDeployTarget.push(archive)`) that both flavors implement, based on the todo's "server-side analog of cfgActivator" framing — this framing only fits Core3.
**Why it happens:** The todo's Open Question 1 assumed both server flavors have "a TRE search path" analog to the client. Ground-truthing shows swg-main has **no TRE concept server-side at all** — it's loose-file `searchPath` resolution, architecturally identical to the CLIENT loose-override deploy model, not the TRE-archive model.
**How to avoid:** Implement two concrete, independently-testable services from the start (see Architecture Patterns above); do not force a shared interface until (if ever) a third flavor shows the same shape as one of these two.
**Warning signs:** A plan task titled "implement server deploy interface" with sub-tasks for "Core3 adapter" and "swg-main adapter" is a sign the abstraction was designed before the mechanism difference was known — this research should prevent that ordering.

### Pitfall 5: Delete restore path silently depending on the workspace being open
**What goes wrong:** Writing `deleteProject` to call `updateChangesetDeployRecord`/`clearChangesetDeployRecord` (which read `useWorkspaceStore.getState().studioDir` — i.e., assume the target project IS the currently-open workspace) instead of the store-independent `readManifest(studioDir)`/`writeManifest(studioDir, ...)` pair.
**Why it happens:** `changesetService.ts` has both a store-coupled API (`updateChangesetDeployRecord`, `clearChangesetDeployRecord` — used by `DeployDialog` because that always operates on the open workspace) and a store-independent API (`readManifest`/`writeManifest`, which take `studioDir` directly — used by `listProjects()` for exactly this reason). It's easy to reach for the former by pattern-matching on `DeployDialog.handleReset` without noticing the difference.
**How to avoid:** `deleteProject(projectFolder)` must derive `studioDir` via `getStudioDir(projectFolder)` and call `readManifest(studioDir)` directly (mirroring `listProjects()`'s approach), never the store-coupled helpers — this is what makes deleting a non-open project (the common case, since delete is invoked from `ProjectListDialog`/`WorkspaceEntry` which list OTHER projects) actually work.
**Warning signs:** A test that only exercises deleting the CURRENTLY OPEN project would not catch this — the plan's test matrix (per the todo's AC5) must include deleting a project that is NOT open.

### Known Threat Patterns for this stack

| Pattern | STRIDE | Standard Mitigation |
|---|---|---|
| Path traversal via a malformed project name/id when constructing the `.trash/<id>-<token>/` path | Tampering | Reuse `getStudioDir`'s existing basename-only + space-sanitization pattern (`workspaceService.ts:98-101`) and `pathSafety.ts`'s confinement checks — do not string-concatenate user-derived names into fs paths without going through these |

| Writing to an external WSL2/Docker-mounted path that turns out to be the WRONG server instance (stale/duplicate checkout) | Tampering (unintentional) | Confirm the target path is the ACTUALLY-RUNNING server's config (Open Questions above) before any write; consider a confirmation/dry-run step in the plan for the server-push feature, analogous to the existing destructive-action confirm modal pattern used for delete |
