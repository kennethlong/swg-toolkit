# Phase 04.3 Plan 04: Reconcile Engine Implementation Summary

Wave-1 GREEN implementation for the Pillar A reconcile engine. syncLiveToVersion, useUndoStore, and setLiveVersion go from throwing stubs to fully working logic. Turns all 19 Wave-0 RED tests from plans 02 and 04 in scope GREEN.

## What Was Built

**Task 1 — syncLiveToVersion reconcile engine:**
- `syncLiveToVersion.ts`: full H4-split reconcile loop. flatEqual noop fast path; undo snapshot pushed before every mutation; Baseline = revert-only (resetLoose for loose-live, restoreCfg for cfg-live); loose apply via deployLoose with priorRecord (H2 internal prune); cfg apply via deactivatePatch(live) + deactivatePatch(target idempotency) + activatePatch; updateChangesetDeployRecord persists the returned record; setLiveVersion moves the single live pointer atomically.
- `syncLiveToVersion.test.ts`: added `updateChangesetDeployRecord: vi.fn()` to changesetService mock (Rule 1 fix — original Wave-0 mock omitted it; GREEN impl calls it on successful loose apply; without the mock it throws at runtime).

**Task 2 — useUndoStore session undo stack:**
- `undoStore.ts`: replaced no-op stub with real `create(set, get)` Zustand store. `push` appends and sets canUndo=true; `undo` pops top, updates canUndo from remaining.length; `clear` empties stack. No persist middleware — purely in-memory.

**Task 3 — setLiveVersion atomic single-pointer mover:**
- `changesetService.ts`: implemented `setLiveVersion(id)`: validates id exists (same H2c guard as selectVersion); sets BOTH `activeVersionId` and `deployedVersionId` in ONE `writeManifest` call (D-08 invariant — never diverge); updates changesetStore's active and deployed version pointers.
- `changesetService.test.ts`: 4 new unit tests using real temp dirs: (1) both pointers equal after call, (2) both fields present in manifest, (3) null clears both, (4) BASELINE_ID always valid.

## Deviations from Plan

**1. [Rule 1 - Bug] Added `updateChangesetDeployRecord: vi.fn()` to Wave-0 test mock**
- **Found during:** Task 1 implementation
- **Issue:** The Wave-0 test mock for `./changesetService` in `syncLiveToVersion.test.ts` omitted `updateChangesetDeployRecord`. The stub body threw before reaching the persist step, so the omission was invisible in RED phase. The GREEN implementation calls `updateChangesetDeployRecord(targetId, newRecord)` after a successful loose apply (test case (c), where deployLoose mock returns a real LooseDeployRecord making `newRecord` defined). Without the mock, calling `undefined(...)` throws TypeError and the test crashes.
- **Fix:** Added `updateChangesetDeployRecord: vi.fn()` entry to the mock factory in `syncLiveToVersion.test.ts`. The test's intent (routing behavior verification) is fully preserved; only the mock is made complete.
- **Files modified:** `packages/renderer/src/services/syncLiveToVersion.test.ts`
- **Commit:** 785cfee

**2. isBaseline computed from `desired.length === 0` (not `targetId === BASELINE_ID`)**
- **Found during:** Task 1 design
- **Issue:** The plan specifies "Baseline (desired empty) is REVERT-ONLY". Using `desired.length === 0` is more robust — it handles any target whose flatten produces an empty set (including theoretical future empty-delta versions), not just the BASELINE_ID sentinel.
- **Impact:** No test impact; both approaches pass all 6 test cases. The `desired.length === 0` form is strictly correct to the plan's stated intent.
