## Summary

The load-bearing unknown — **D-12, the branch-tree graph library gate — resolves to HAND-ROLLED SVG.** No surveyed React-19-compatible library clears the gate, and the gate is cheaper than it looks: the model is a single-parent rooted tree (no merges, D-11), and **sketch 002-A is already a working hand-rolled SVG reference implementation** — it contains the exact lane geometry, node templates, bezier connector, and dashed WIP stub as static markup. The implementation task is to parameterize that static SVG over the real changeset graph with a simple depth/lane-assignment pass. Pulling in `@gitgraph/react` (the obvious candidate) FAILS because it fuses the commit node and the row text into one SVG/canvas unit and cannot render a 90px gutter beside independently-laid-out React rows (which carry hover actions, ▸-expand carets, ver-pips); it is also 4 years stale (last publish 2022). React Flow / reaflow are pannable-canvas node editors — the wrong interaction model for a vertical scrolling version list. Layout-only libs (dagre/d3-dag/elkjs) just compute coordinates you'd still render yourself — unjustified bundle weight for a trivial tree layout.

**Pillar A's reconcile engine is mostly assembly, not new construction.** Every primitive exists: `changesetService.flatten(versionId)` materializes any version's full file set by walking `parentId`; `looseOverrideDeploy.deployLoose/resetLoose` does B3 snapshot+restore for loose; `cfgActivator.activatePatch/restoreCfg/deactivatePatch` does the absolute/cfg path; each `SwgChangeset.deployRecord` already tags its deploy type. The genuinely new piece is one service — `syncLiveToVersion(targetId)` — that diffs `flatten(target)` against the live set and applies/reverts per-file using each file's stored deploy model, plus a session undo stack (D-06) and collapsing the `activeVersionId`/`deployedVersionId` pair into a single "live" pointer (D-08).

**Pillar B is ground-truth-verified and ready to spec.** I measured the real v6000 container live: `patch_sku3_24_shared_00.tre` is `EERT6000`, `numberOfFiles=0`, all header fields zero, and a `78 9c` **plain-zlib** stream begins immediately at offset 36 — directly falsifying the blanket `isEnumerateOnly(V6000)` refusal. The entries for these containers live only in the master `.toc` (`tocReader.readTocIndex` from 04.2-03 already parses it but the mount never sourced entries from it). The faithful fix: for searchTOC clients, source the entry set from the master `.toc`, extract payloads at the indexed offset with a per-payload inflate-then-classify, and resolve searchPath loose overrides lazily.

**Primary recommendation:** Hand-roll the branch-tree SVG (parameterize sketch 002-A); build `syncLiveToVersion` as a thin diff-and-apply over the existing deploy primitives; rewire the searchTOC mount to source entries from the master `.toc` and make `isEnumerateOnly` a per-payload runtime classification. Run the de-anchoring crew + byte-exact v6000 test before merging Pillar B (D-16).

**The gate (from D-12 + sketch 002-A):** a 90px lane gutter rendered as a *separate column* beside independently-laid-out React row content; custom node templates (gray-hollow root/older, accent-filled live node + inner dot, branch-point markers); CSS-var accent theming; cubic-bezier "branch-from vN" connectors; a dashed uncommitted-changes WIP stub above the live node.

**The decisive architectural fact:** sketch 002-A `[CITED: .planning/sketches/002-version-graph-timeline/index.html:339-382]` already splits the surface into `.lane-col` (`flex: 0 0 90px`, an `<svg width=90>`) sitting *beside* `.graph-rows-col` (`flex: 1`, plain React rows with `.row-actions`, `.ver-pip`, `.ver-label`, ▸-expand). ### Hand-rolled lane-assignment algorithm (single-parent rooted tree, no merges)

The data already supports this: `SwgChangeset.parentId` builds the tree; `branchSet()` in `VersionHistoryBody.tsx:33-41` detects chronological branch-starts (a HINT for theming only — lane assignment MUST use topology, see step 5; keying lanes on branchSet is the bug reviewed-out below). The renderer just never drew lanes. Algorithm the planner can scope as concrete tasks:

```
INPUT: changesets[] (each {id, parentId, timestamp, label, deltas}), liveVersionId, hasUncommittedWork
ROW LAYOUT (vertical) — layout.rows is the SINGLE row-order source:
  1. Order rows OLDEST-first by timestamp. This MATCHES the current VersionHistoryBody sort
     (VersionHistoryBody.tsx:70-72 is oldest-first — NOT newest-first; the old "newest-first matches
     current sort" claim was FALSE). The component MUST render rows from layout.rows in this order;
     do not re-sort downstream (else the gutter and rows vertically reverse). Each changeset = one row
     at rowIndex r; rowY(r) = 52*r + 26.
LANE ASSIGNMENT — by TOPOLOGY (parentId), NOT chronological adjacency:
  2. Walk rows in layout.rows order. Track laneOf[id] and a free-lane set.
  3. root (no parentId): lane 0. The TRUNK (lane 0) is the first-child chain from the root: a node
     INHERITS its parent's lane iff it is its parent's FIRST-placed child (earliest in row order).
  4. Every ADDITIONAL child of a parent (not the first-placed) is a branch: assign the lowest FREE
     lane > 0 (allocate a new lane if none free). A lane is freed once that branch node's SUBTREE is
     fully emitted (past its last descendant's row) — classic git-graph recycling, bounded width.
  5. Do NOT key lane/trunk membership on branchSet() (chronological predecessor) — that mis-lanes a
     continue-on-branch node. Counterexample (the exact bug this fixes): v1<-v2<-v3 (trunk) + v4(parent
     v2) + v5(parent v4). Topology: v3 inherits v2 -> lane 0; v4 is v2's 2nd child -> lane 1; v5 is v4's
     first child -> INHERITS lane 1. v5 connects to v4 (same-lane line), NOT a false trunk to v3.
  6. lane -> x = 22 + 46*lane. Each CONCURRENTLY-ACTIVE lane MUST get a DISTINCT x; do NOT collapse
     lanes onto a 90px clamp. width = max(90, 22 + 46*maxConcurrentLane + 8); >2 simultaneous lanes
     WIDEN the gutter (D-11 "any number of branches") rather than overlapping at the clamp.
CONNECTORS (SVG paths in the gutter) — every NON-root node draws ONE connector to its parentId:
  7. same lane (laneOf[node] === laneOf[parent]): vertical trunk <line> parent->node.
  8. cross lane: cubic bezier from PARENT (parentLane) to NODE (its lane):
     M {parentX} {parentY} C {parentX+34} {parentY} {branchX} {midY} {branchX} {branchY}
NODES (SVG circles, custom templates per D-13):
  9. root (no parent in graph): gray hollow circle (fill=surface, stroke=text-faint, r=6).
 10. live node (id === liveVersionId): accent-filled (fill=accent, r=9) + inner dot (r=4, fill=accent-text).
 11. branch-point / older nodes: gray hollow (r=6); branch nodes may use a slightly larger ring.
WIP STUB (D-13):
 12. If hasUncommittedWork: dashed <line> (stroke-dasharray) from y=0 up to the live node, in the live node's lane.
vN ORDINAL CONVENTION (single source — feeds meta line + status footer (06) + statusbar live: vN (09)):
 13. vN = 1-based index of the changeset in oldest-first chronological order (v1 = oldest non-Baseline
     changeset); DERIVED from layout.rows position, never stored (manifest holds UUIDs + labels only).
     Baseline renders as "Baseline", not vN. Use this same derivation everywhere a vN appears.
```

`[CITED: sketch 002-A:349-381]` provides the exact SVG primitives (line/path/circle), stroke colors as CSS vars, and the bezier control-point convention to copy. The implementation should keep the gutter SVG a pure function of `(rows, laneOf, liveVersionId, hasUncommittedWork)` and let the rows render as today's React list (re-themed per A12/A13/D-13).

**Planner guidance:** scope this as (1) a `laneLayout(changesets)` pure function with unit tests on branch/no-branch/deep-branch fixtures, (2) a `<LaneGutter>` SVG component, (3) re-theme the existing row list to the 002-A row contract, (4) the status footer (A11) and WIP stub (A5). ### The new piece — `syncLiveToVersion(targetId)`

A single diff-and-apply between two flattened states. Pseudocode (planner-facing):

```
syncLiveToVersion(targetId):
  desired = flatten(targetId)                       // changesetService.flatten
  live    = flatten(liveVersionId)                  // current live pointer (or a tracked live set)
  if flatEqual(desired, live): return               // no-op fast path (flatEqual)

  snapshot = captureSession()                        // D-06: push onto session undo stack BEFORE mutating
  model    = deployModelOf(targetId)                 // from target's deployRecord shape (loose vs cfg)

  # forward-apply + backward-revert in ONE op: diff by virtualPath
  toWrite  = desired \ live   (by virtualPath+sha)   // present in desired, missing/changed in live
  toRemove = live \ desired   (by virtualPath)        // present in live, absent from desired

  if model == loose:
      # resetLoose(priorRecord) then deployLoose(desired) is the simplest correct form:
      # deployLoose already B3-snapshots + prunes via priorRecord. Prefer that over hand-diffing.
      record = deployLoose(desired, resolveOverrideDir(cfg), { studioDir, priorRecord: liveLooseRecord })
  else: # absolute/cfg
      # restore stock cfg, then activate the target's patch (or restoreCfg for Baseline)
      ...deactivatePatch(prior) / restoreCfg(...) then activatePatch(target build) ...

  setLivePointer(targetId)                            // D-08 single pointer (see below)
```

**Key design decisions for the planner:**

1. **Prefer "reset-prior + deploy-target" over per-file hand-diffing for loose.** `deployLoose` already does B3 snapshot + `priorRecord` prune correctly (`looseOverrideDeploy.ts:85-88,121-129`). Reconcile = `deployLoose(flatten(target), overrideDir, {priorRecord: prevLiveLooseRecord})`. Baseline = `resetLoose(prevLiveLooseRecord)` (empty desired). This reuses tested code and keeps B3 invariants. Per-file diffing is an optimization to defer.
2. **Single "live" pointer (D-08).** Today there are two pointers: `manifest.activeVersionId` (edited) + `manifest.deployedVersionId` (live), and `VersionHistoryBody.tsx:66-67` computes a `stale` banner when they differ. D-08 eliminates the divergence: selecting === reconciling === both pointers move together. Cleanest minimal change: keep both fields for storage compatibility but **always set them together in `syncLiveToVersion`** so they never diverge; remove the `stale` banner (it becomes dead). Do NOT delete the fields (migration risk) — make them invariantly equal.
3. **Deploy-model picker scope (D-10/VER-07).** The picker governs only a NEW forward deploy (`DeployDialog`). When `syncLiveToVersion` runs for an existing version, it reads the model from that version's `deployRecord` — no picker. The first deploy of a freshly-saved version is the ONLY place the picker shows.

### Master `.toc` (SearchTOC) format — VERIFIED, working reader exists

The toolkit's `tocReader.ts` already parses this correctly and is the reference. Layout `[VERIFIED: tocReader.ts:107-141 + tre_reader.py:335-413 + swg-client-v2 TreeFile_SearchNode.h:270-299]`:

- **Header (36 bytes LE):** magic `" COT"`=0x544F4320 @0, version `"1000"`=0x30303031 @4, tocCompressor:u8 @8, fileNameBlockCompressor:u8 @9, unused×2 @10-11, numberOfFiles:u32 @12, sizeOfTOC:u32 @16 (`= numberOfFiles×24`), sizeOfNameBlock:u32 @20, uncompSizeOfNameBlock:u32 @24, numberOfTreeFiles:u32 @28, sizeOfTreeFileNameBlock:u32 @32.
- **Tree-file name block** (NUL-terminated names) follows the header; `readTocTreeNames` reads it (`tocReader.ts:154-178`).
- **TOC entry (24 bytes LE)** `[VERIFIED: tocReader.ts:228-251 + tre_reader.py:380-389]`: compressor:u8 @0, unused:u8 @1, **treeFileIndex:u16 @2**, crc:u32 @4, fileNameLength:u32 @8 (disk stores LENGTH; offset rebuilt cumulatively), offset:u32 @12, length:u32 @16, compressedLength:u32 @20.
- **Resolution** is engine-faithful CRC-keyed binary search (`tocReader.ts:273-315`), replicating `SearchTOC::localExists` (`TreeFile_SearchNode.cpp:783-836`). On CRC collision, case-insensitive name tiebreak. NOT a Map/keep-first (H1 invariant).

The entry's `treeFileIndex` → `treeNames[index]` gives the container `.tre`; `offset`/`length`/`compressedLength`/`compressor` are read from THAT `.tre` (after `TOCTreePath` prefix). This is the missing wiring: `readTocIndex` exists but the mount only ever called `readTocTreeNames`.

### Per-.tre container format — VERIFIED byte-exact

`[VERIFIED: TreArchive.cpp:124-250 + TreVersion.h + tre_reader.py:159-261, proven against real bottom.tre/SwgRestoration_00.tre]`:
- **Header 36 bytes:** token `EERT` @0, version ASCII forward (`"5000"`/`"6000"` etc.) @4, then numberOfFiles, tocOffset, tocCompressor, sizeOfTOC, blockCompressor, sizeOfNameBlock, uncompSizeOfNameBlock (7×u32).
- **TOC record CRC-FIRST for ALL versions:** crc@0, length@4, offset@8, compressor@12, compressedLength@16, fileNameOffset@20. Stride 24, except **V6000 stride 32** (+8 pad). `[VERIFIED: TreVersion.h:80-89, TreArchive.cpp:233-247]`. The old "size-first" layout is FALSIFIED — do not reinstate.
- **Compressor:** 0=none, 2=zlib (1=deprecated/raw-deflate — Utinni treats as raw deflate, C++ fatals; OPEN whether real "5000" archives contain compressor=1, flagged in CONSULT-04 D2 — low risk, no observed instance).
- **Empty-internal-TOC containers (v6000 sku3):** `numberOfFiles=0` → the internal TOC parse yields zero entries (current behavior = `entryCount 0`). Entries come from the master `.toc` instead.

### Override / load-order resolution — VERIFIED

`[VERIFIED: CONSULT-04 sonnet vs swg-client-v2 TreeFile.cpp:285-308,453-461 + TreeFile_SearchNode.cpp:397-401]`: **higher explicit priority number wins; within a priority tier, first-added (lower config index) wins.** Search walks a priority-DESC-sorted node list front-to-back, returns first match. A `length==0` TOC entry is a **deletion tombstone** that stops the search chain (shadow-delete). The toolkit's `treAutoMount` already sorts `rawPriority DESC` then assigns compact priorities (`treAutoMount.ts:106-111`), and `TreArchive::resolve` honors the tombstone (`TreArchive.cpp:294-297`). This matches the engine; no change needed beyond entry-sourcing.

## Common Pitfalls

### Pitfall 1: Re-introducing sketch drift via a graph library's default render
**What goes wrong:** A git-graph lib renders its own row/commit layout, silently replacing the 002-A row contract (the exact failure that created this phase — a flat list shipped from an "extract existing component" task).
**How to avoid:** Hand-roll the SVG gutter as a separate column; keep rows as React. Verify each 002-A element (A1–A13) against the built surface per the AGENTS.md sketch-diff rule.

### Pitfall 2: Flipping `isEnumerateOnly` alone (does nothing visible)
**What goes wrong:** Making v6000 readable in native-core has zero visible effect because the entries are never sourced (empty internal TOC). The master-`.toc` entry sourcing is the load-bearing fix.
**How to avoid:** Sequence MOUNT-01 (entry sourcing) BEFORE/with MOUNT-04 (enumerate-only). The byte-exact test (MOUNT-03) must extract a master-sourced v6000 payload, not an internal-TOC one.

### Pitfall 3: Conflating Restoration v6000 (encrypted) with SWG-Source v6000 (plain zlib)
**What goes wrong:** Treating the version tag as the encryption discriminator re-breaks one of the two. The existing fixtures `restoration-SwgRestoration_*.tre` are ENCRYPTED v6000; `patch_sku3_*` are PLAIN-ZLIB v6000.
**How to avoid:** Classify per-payload (inflate success). Test BOTH: swg-source v6000 extracts byte-exact; Restoration v6000 degrades to enumerate-only without crashing (MOUNT-04).

### Pitfall 4: Double-counting self-indexed + master-indexed paths
**What goes wrong:** Mounting both the master `.toc` AND each container's internal TOC duplicates entries / inflates counts.
**How to avoid:** For searchTOC clients, the master `.toc` is the single index (MOUNT-02). Don't also read internal TOCs for the same containers.

### Pitfall 5: Loose-overlay over-enumeration regressing mount perf / surfacing junk rows
**What goes wrong:** Enumerating a whole data-root `searchPath` adds thousands of bogus VFS rows and the archives themselves.
**How to avoid:** Lazy resolution (D-15) — resolve at lookup, never enumerate. Loose winners read via `readVfsEntryBytes`.
