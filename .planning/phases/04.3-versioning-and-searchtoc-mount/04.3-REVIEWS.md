## Consensus Summary

The plan set's **structure** is sound and was repeatedly praised: interface-first Wave-0 stubs, real
file-layer wave separation (no same-file Wave-1 write conflicts — Codex verified), the D-16 de-anchoring
gate before a concrete combined UAT, the hand-rolled-SVG verdict, and disciplined KEEP-lists. Every reused
Pillar-A/B primitive the plans name actually exists with the claimed signature (Codex verified file:line).
The Pillar-B **byte layout** (24-byte master `.toc`, stride-32/CRC-first container TOC, try-inflate-then-
classify) is faithful to the real client + `tre_reader.py` (Cursor verified). **But** the crew surfaced a
cluster of real, execution-blocking defects — at least **5 HIGH** — that the goal-backward checker missed.

### Agreed Concerns (convergent — highest priority)

1. **[HIGH · Pillar B mount→read wiring is structurally incomplete] — Cursor + Codex (independent).**
   Plan 11 sources entries from the master `.toc` and plan 10 builds `extractAt`, but **neither wires
   extraction into the actual read path**, and the renderer-only edit set can't reach it:
   - The frozen `extractAt(offset, length, compressedLength, compressor)` signature **has no container
     locator** — offset alone names no file. The existing native path is `readMountEntry(handle,
     archiveIndex, entryIndex)` → opens `node.path`. Needs `extractAt(pathOrHandle, offset, …)` or
     `extractMountAt(handle, archiveIndex, descriptor)`. *(Codex HIGH; this invalidates the W2 stub I added.)*
   - Native exposes **no API to supply external master-`.toc` entries** through the columnar bridge
     (`mountTreMount`/`getMountEntriesColumnar`/`readMountEntry` only). Plan 11's `files_modified` omits
     `treMount.ts`, `tre_binding.cpp`, and the native mount API. *(Codex + Cursor HIGH.)*
   - The current read path `readVfsEntryBytes → readMountEntry(archiveIndex, entryIndex) → extractEntry`
     uses the container's **internal** TOC, which is empty for `numberOfFiles=0` v6000 containers, so
     browse/open still fails end-to-end after plan 11. `readVfsEntryBytes` is **private inside
     `TreVfsBrowser.tsx`**, not the shared primitive plan 11 assumes. *(Cursor HIGH + Codex MEDIUM.)*
   → Net: as planned, the v6000 mount cannot actually read payloads. This is the "plan-check PASS but
     byte-correct-yet-broken" failure mode RESEARCH itself warned about (Pitfall 2 variant).

2. **[HIGH · the D-08 single "live" pointer is under-specified across plans 02/04/06/07/09] — Codex + Sonnet + Opus (three angles).**
   - `setLiveVersion` is **not stubbed** in plan 02, so plan 06 (which imports it as a "Wave-0 contract")
     **fails typecheck** in the parallel wave. `changesetService` has `selectVersion`/`setDeployedVersion`,
     not `setLiveVersion`. *(Codex HIGH.)*
   - `DeployDialog`'s success handler (plan 07) is **never updated to call `setLiveVersion`** after a new
     forward deploy → `activeVersionId ≠ deployedVersionId` the moment you deploy, re-introducing the
     stale-divergence D-08 deletes. *(Sonnet HIGH.)*
   - The invariant is **not enforced by construction**: `sealVersion` sets only `activeVersionId`;
     `DeployDialog` independently moves `deployedVersionId` and keeps its own stale calc; plan 06 removes
     the stale banner that surfaced divergence; the Baseline node's own `onClick`s still call
     `selectVersion` (pointer-only, no reconcile) so "restore to stock" doesn't fire. *(Opus MEDIUM ×2.)*

3. **[HIGH/MEDIUM · laneLayout fixtures are insufficient AND the algorithm is wrong] — Opus (with Cursor confirming sketch-mapping is otherwise faithful).**
   The lane algorithm keys lane assignment + bezier-vs-trunk on `branchSet()` = **chronological adjacency**,
   not topology. Counterexample `v1←v2←v3` + `v4`(parent v2) + `v5`(parent v4): v5's chrono predecessor IS
   v4 and v5.parent===v4 → v5 ∉ branchSet → **lane 0**, parent v4 in lane 1 → no bezier for v5, no trunk
   segment, **missing connector to real parent**, and a **false trunk line v5→v3**. This is branch-then-
   iterate — the maintainer's mental model — reproducing the exact mis-render this phase exists to fix.
   Planned fixtures (no-branch / off-tip / off-non-tip / deep / WIP) don't include continue-on-branch.

### Divergent / solo findings (single reviewer, still actionable)

- **[HIGH · Opus] Reconcile dispatches on the TARGET's model → loose→Baseline restore-to-stock broken.**
  Baseline has no `deployRecord` → `deployModelOf(Baseline)`='cfg' → loose client + Baseline runs
  `restoreCfg` (no snapshot) and **never removes the loose `override/` files**. Same bug on any
  cross-model navigation (cfg-live→loose-target deploys loose without `deactivatePatch`-ing the live cfg).
  Fix: `revertModel = deployModelOf(LIVE)`, `applyModel = deployModelOf(target)`; Baseline = revert-only.
- **[HIGH · Sonnet] No undo UI affordance anywhere.** `undoStore.push()` is called every reconcile but no
  plan adds a Ctrl+Z handler / button / menu item → UAT VER-04 ("verify undo reverses it") is unperformable.
- **[HIGH · Sonnet] "Branch from here" behavior is unspecified** in the new reconcile model (reconcile
  first? fire D-07 confirm? set parentId for next save? navigate?). D-09 makes it the one click-inexpressible
  action — so its behavior is load-bearing, not chrome.
- **[MEDIUM · Opus] Reconcile never persists the returned `LooseDeployRecord`** (`updateChangesetDeployRecord`)
  → next hop's `priorRecord` is stale → `resetLoose` runs against unlinked snapshots → orphaned override files.
  Forward→back→forward idempotence holds only if each reconcile persists its record.
- **[MEDIUM · Opus] `laneX(l)=clamp(22+46*l, ≤90)` physically supports only 2 lanes** — lane 2→clamped 90,
  overlapping. "deep tree, width≤90" criterion is vacuous (the clamp makes it pass even when nodes overlap).
  D-11 "any number of branches" vs the 90px gutter is in tension for >1 simultaneous branch.
- **[MEDIUM · Cursor] Master `.toc` `length==0` tombstones not filtered** — `tocReader` discards `length`;
  `resolve`/`resolveFull` don't skip tombstones (client `localExists` rejects them) → deletions treated as files.
- **[MEDIUM · Cursor/Codex] Lazy searchPath needs an on-demand resolve helper**, not just deleting
  `injectLooseDirOverlay`'s `readdir` (which lives in `treMount.ts`, NOT `treAutoMount.ts` — so plan 11's
  `files_modified` and its "grep readdir == 0" verification can't pass). No plan adds the resolve-layer
  override lookup; `openInViewer` named but not `TreVfsBrowser`/store.
- **[MEDIUM · Sonnet] In-flight reconcile race** — `syncLiveToVersion` is async, row-click has no guard;
  rapid navigation queues concurrent reconciles, stomps B3 snapshots, inflates the undo stack.
- **[MEDIUM · Sonnet] Cross-plan coordination gaps in parallel Wave 1:** the P9 "shared store/hook" is
  referenced but never named (no Wave-0 stub); `useNoProjectDim` dims by panel-ID "Data" which goes stale
  when plan 09 splits it into Datatable/Console/Log → first-run dim breaks for the bottom pane.
- **[MEDIUM · Cursor] Enumerate-only chip may stay version-tag at archive level** (`MountedArchivesList.tsx`)
  — no plan task moves it to per-entry extract-failure; swg-source v6000 could be mislabeled "encrypted".
- **[MEDIUM · Sonnet/Cursor] P4 not-found rows mapped to welcome but not the wizard** (`NewProjectWizard.tsx`).
- **[MEDIUM · Sonnet] Context-menu compare-to-base / open-in-editor are behavioral, specced as chrome** —
  risk of stub menu items that pass component tests but do nothing.
- **[LOW] Opus:** RESEARCH "newest-first matches current sort" is FALSE (current sort is oldest-first
  `VersionHistoryBody.tsx:71`) → gutter/rows vertically reversed unless `laneLayout.rows` is the single
  row-order source; "vN" ordinal numbering is undefined (manifest stores UUIDs+labels). **Codex:** plan 02
  overstates `resolveOverrideDir` as `string` (real `string|null`). **Cursor:** plan 03 RED grep is brittle.
