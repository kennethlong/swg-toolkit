## Summary

This phase makes the toolkit work with the **dev/modder decoupled client** (swg-client-v2 / SWG Source): a runnable binary dir with `client.cfg` and **zero `.tre`**, whose game data lives in an external install referenced by absolute path. Three capabilities ship as one vertical slice: (1) detect `client.cfg` layouts + manual override; (2) extend the mount to read the FULL base via `searchTOC` (a `.toc` master index) + `searchPath` loose dirs, not just `searchTree`; (3) a "deploy into the top-priority loose `searchPath` override dir" mode.

The good news from this research: **no new byte-level format risk.** The `.toc` SearchTOC format is fully pinned down — the C++ `SearchTOC::Header`/`TableOfContentsEntry` structs (`TreeFile_SearchNode.h:270-299`), the blender plugin's `read_search_toc_header`/`read_search_toc_entries`, and the real 13.8 MB `sku0_client.toc` header all agree exactly (36-byte header, 24-byte entries, on-disk magic ` COT1000`). Mounting the base requires two steps: (a) parse the `.toc`'s tree-name block to get the list of 131 constituent `.tre` archives, then mount them through the existing `mountSearchableAsync`; (b) parse the full 193k-entry global index (`readTocIndex`) to provide TOC-authoritative per-path resolution for the TS VFS layer — ensuring duplicate paths resolve to the engine's exact `.tre` choice, not flat later-added-wins.

The two real engineering decisions for the planner are: **(a)** how to represent `searchPath` *loose directories* in the mount — the native mount (`mountSearchableAsync`) accepts only `.tre` file paths, so loose dirs need a TS VFS overlay or a native extension; and **(b)** the deploy-to-override-dir mode is a genuinely new, *simpler* deploy branch (write loose files into the highest-priority `searchPath` dir, no TRE pack, no `.cfg` surgery) that must NOT reuse the `packPatch`/`cfgActivator` machinery.

**Primary recommendation:** Add a TS `.toc` reader that parses the SearchTOC header + tree-name block (for mount) AND the full 193k-entry index (for accurate per-path resolution); expand each `searchTOC` cfg entry into its constituent TOCTreePath-prefixed `.tre` paths and feed them into the existing native mount via a SINGLE unified priority-ordered call covering all three families; add a `client.cfg` layout row whose TRE dir is resolved from the cfg (not a fixed subfolder); and add a third deploy model `loose-override` that writes staged files straight into the cfg's highest-priority `searchPath` dir with a written-files manifest for non-destructive reset (including snapshot/restore of pre-existing files).

## Capability 2 — `searchTOC` / `searchPath` / `TOCTreePath` mount (TRE-05)

### Mount strategy: constituent-TRE mount + TOC-indexed VFS resolution

A `searchTOC` `.toc` is a *master aggregate index* over N constituent `.tre` archives. Each constituent `.tre` is an independently-valid standard TRE the toolkit's existing native core already mounts. The mount strategy uses two layers:

1. **Mount layer (native):** parse the `.toc` header + tree-name block to get the 131 constituent `.tre` names → prepend `TOCTreePath` → include in a SINGLE unified `mountTrePaths` call covering all three families (searchTOC expanded + searchTree + the precedence-ordered list). This reuses the existing native `mountSearchableAsync`. No new native format work.

2. **Resolution layer (TS, `readTocIndex`):** parse the full 193k-entry global index to build a `Map<normalizedPath, {treeFileIndex, treName}>`. For any logical path P, the AUTHORITATIVE serving `.tre` is `treeNames[entry.treeFileIndex]` — NOT the highest-priority archive that happens to contain P. This is required for correctness on the ~3 duplicate paths in sku0 (e.g. `string/ja/space/space_faction.stf` — see GIVEN A8 counterexample).

> **Why both layers?** The native mount provides byte access (extract, preview) across all 131 archives efficiently; the TS `TocIndex` provides accurate path resolution metadata for the VFS browser display and single-asset lookup routing. They are complementary, not redundant.

### `.toc` (SearchTOC) byte format — VERIFIED THREE WAYS

Verified against: C++ `TreeFile::SearchTOC::Header`/`TableOfContentsEntry` (`TreeFile_SearchNode.h:270-299`), the blender plugin `read_search_toc_header`/`read_search_toc_entries` (`../swg-blender-plugin/swg_pipeline/tre_reader.py:335-413`), AND the real `D:/Code/SWGSource Client v3.0/sku0_client.toc` header bytes (read this session). All three agree exactly.

**Header — 36 bytes, little-endian:**

| Offset | Size | Field (C++ name) | sku0 real value | Notes |
|--------|------|------------------|-----------------|-------|
| 0 | 4 | `token` | `20 43 4F 54` = ` COT` | TAG_TOC. On disk ASCII reads ` COT` (leading space). |
| 4 | 4 | `version` | `31 30 30 30` = `1000` | TAG_0001. On disk ASCII reads `1000`. |
| 8 | 1 | `tocCompressor` | `00` | 0 = uncompressed; nonzero = zlib |
| 9 | 1 | `fileNameBlockCompressor` | `00` | 0 = uncompressed; nonzero = zlib |
| 10 | 1 | `unusedOne` | `00` | alignment |
| 11 | 1 | `unusedTwo` | `00` | alignment |
| 12 | 4 | `numberOfFiles` | `0x0002F3C3` = 193475 | global indexed path count |
| 16 | 4 | `sizeOfTOC` | `0x0046DA48` = 4,643,400 | = 193475 × 24 (uncompressed here) |
| 20 | 4 | `sizeOfNameBlock` | `0x008D06DF` = 9,242,335 | on-disk name block size |
| 24 | 4 | `uncompSizeOfNameBlock` | `0x008D06DF` = 9,242,335 | == sizeOfNameBlock when uncompressed |
| 28 | 4 | `numberOfTreeFiles` | `0x00000083` = 131 | count of constituent `.tre` archives |
| 32 | 4 | `sizeOfTreeFileNameBlock` | `0x00000AC5` = 2757 | bytes of null-terminated `.tre` names |

> ⚠️ **Endianness gotcha for the planner:** the C++ stores `token`/`version` as `Tag` (uint32). On disk the token bytes are `20 43 4F 54` which the human eye reads as ` COT` and the version `31 30 30 30` reads as `1000` — so a full hexdump of the file shows the magic string **` COT1000`**. The blender reader encodes this as `TAG_TOC_LE = struct.pack("<I", 0x544F4320)` and `TAG_0001_LE = struct.pack("<I", 0x30303031)`. Do **not** confuse this with `COT2000` (Restoration, magic ` COT2000`, 8-byte literal) — they differ only in the version digit and `COT2000` is out of scope.

**On-disk block order (after the 36-byte header):**
1. **Tree-file-name block** (`sizeOfTreeFileNameBlock` bytes): `numberOfTreeFiles` null-terminated ASCII `.tre` names back-to-back. (sku0: starts `bottom.tre\0default_patch.tre\0data_animation_00.tre\0…`, 131 names = 2757 bytes.) **This is all the mount needs.**
2. **Table of contents** (`sizeOfTOC` bytes, zlib-compressed iff `tocCompressor != 0`): `numberOfFiles` × 24-byte entries. For sku0: uncompressed, starts at byte 2793.
3. **Name block** (`sizeOfNameBlock` bytes on disk → `uncompSizeOfNameBlock` uncompressed, zlib iff `fileNameBlockCompressor != 0`): packed null-terminated logical path strings. For sku0: uncompressed, starts at byte 4,646,193.

**`TableOfContentsEntry` — 24 bytes, little-endian (CITED: `TreeFile_SearchNode.h:289-299`; Python `SEARCH_TOC_ENTRY_FMT = '<BBHIIIII'`, `tre_reader.py:381`):**

| Offset | Size | Field | Notes |
|--------|------|-------|-------|
| 0 | 1 | `compressor` | 0=stored, nonzero=zlib |
| 1 | 1 | `unused` | |
| 2 | 2 | `treeFileIndex` | uint16; index into the tree-name list → which `.tre` serves this path |
| 4 | 4 | `crc` | uint32 |
| 8 | 4 | `fileNameOffset` | **on disk stores filename LENGTH**; rewritten to cumulative offset after load (C++ `:699-711`; Python `:385-389`): `offset[i] = Σ(length[j]+1) for j<i` |
| 12 | 4 | `offset` | byte offset into the constituent `.tre` payload region |
| 16 | 4 | `length` | uncompressed size |
| 20 | 4 | `compressedLength` | on-disk size when compressed |

> Note on `fileNameOffset` rewrite: the file stores per-entry filename *lengths*; both readers convert them to cumulative offsets into the name block. Any toolkit full-index reader MUST replicate this, exactly as both ground-truth readers do.

> Payload reading via the `.toc` (C++ `SearchTOC::open` `:891-947`): the engine reads payload bytes directly from `m_treeFiles[treeFileIndex]` at `entry.offset` for `entry.length`/`compressedLength` — it does **not** consult the constituent `.tre`'s own internal TOC. For the toolkit's expand-to-`.tre` mount strategy this is irrelevant (the native core reads each `.tre`'s own TOC), but it confirms that `offset` is absolute into the `.tre` file and `treeFileIndex` is authoritative.

### `TOCTreePath` application (A3, confirmed)
For each tree-file name N in the `.toc`, the engine opens the first of: `N` (cwd-relative), then `<TOCTreePath_0> + N`, `<TOCTreePath_1> + N`, … (`TreeFile_SearchNode.cpp:639-668`). `TOCTreePath` is a raw **string prefix** with a trailing slash (e.g. `D:/Code/SWGSource Client v3.0/` + `bottom.tre` = `D:/Code/SWGSource Client v3.0/bottom.tre`). The toolkit must read all `TOCTreePath` values (there can be multiple) and resolve each tree name against them, first-existing wins.

### `searchPath` loose-dir semantics (confirmed)
`SearchPath::makeAbsolutePath` (`:96-105`): logical lookup `texture/foo.dds` → `<m_pathName>/texture/foo.dds`. The dir path is canonicalized to absolute with forward slashes, trailing slash stripped (`:60-76`). `exists`/`open` hit the loose file directly. So a `searchPath` dir overlays loose files by mirroring the logical path tree under it.

### Mount precedence — ONE unified list across all three families
`clientSearchOrder.ts` currently builds the mount order from `searchTree` only, applying a compact priority sequence. Extend `parseSearchTree` → a `parseSearchNodes` that also captures `searchPath` and `searchTOC` entries, tagged by family. Then build ONE flat list across all three families:

- Expand each `searchTOC` into its constituent `.tre` paths (TOCTreePath-resolved), each carrying the TOC entry's raw cfg priority.
- Keep `searchTree` entries with their raw cfg priority.
- Represent `searchPath` dirs as loose-overlay nodes (see decision below), also with their raw cfg priority.
- Sort across ALL families by `(priority DESC, sku DESC, order DESC)`. Assign a SINGLE strictly-descending compact sequence to the whole merged list. Feed `.tre` paths to ONE `mountTrePaths` call. Feed loose dirs to `injectLooseDirOverlay`.

**Why one call is required:** `mountTrePaths` → `mountComplete` (treStore.ts:159-170) does a full `set({...})` REPLACE. Calling it twice (once for searchTree, once for TOC expansion) erases the first mount's store state — the searchTree overlays vanish. This is a runtime correctness bug, not a design choice.

**Why separate compact sequences are wrong:** `clientSearchOrder.ts:137` currently maps searchTree entries to compact `[2,1]` while TOC entries would carry raw `[0,3]`. Post-merge, `sku3.toc@3` would get compact priority 3 > `swgsource_3.0.tre@8`'s compact priority 2 — cross-family order inverts. The fix: sort the full merged list by raw cfg priority DESC, then apply a single compact sequence.

**`ClientMountOrder` contract (Plan 02 output):** to enable this, Plan 02 must add `searchTreeRawPriorities: number[]` (parallel to `trePaths`), `looseDirPriorities: number[]` (parallel to `looseDirs`), and `maxPriority: number` to `ClientMountOrder`. Plan 03's `treAutoMount.ts` uses these to build the unified compact sequence.

Per A1, within one priority the install order is path→tree→toc, so "later added" makes toc win over tree over path *at equal priority*. **In the live swg-client-v2 cfg there are NO equal-priority cross-family collisions** (TOC@0-3, path@5/9/10, tree@7/8), so the simple `priority DESC` ordering is exact here; document the general tie-rule for correctness but it won't bite this client.

### THE decision point: how to mount `searchPath` loose dirs
The native mount API is `mountSearchableAsync(paths: string[], priorities: number[])` (`native-core/index.d.ts:372`) — it accepts **`.tre` file paths only**. There is no loose-dir/`addSearchPath` native API (grep confirms). Options for the planner:

| Option | Approach | Pros | Cons |
|--------|----------|------|------|
| **A. TS VFS overlay (recommended for MVP)** | Scan each `searchPath` dir recursively in TS; inject loose files as override entries into the treStore VFS (the `isOverride` flag already exists in the columnar VFS — `treMount.ts:110`) | No native change; aligns with the loose-override deploy thesis; criterion 4's proof asset is in the TOC base anyway | Loose-dir browse is a TS-side overlay separate from native resolution; must keep in sync on deploy |
| **B. Native `addSearchPath` node** | Extend native mount to register a loose-dir search node mirroring `SearchPath` | One unified resolution path matching the engine exactly | New native work; larger surface; the binary-stays-binary rule applies |

**Recommendation:** Option A for this phase. Mark `isOverride: looseDirRawPriority > maxSearchTreeRawPriority` on injected VfsEntries (where `maxSearchTreeRawPriority = max(order.searchTreeRawPriorities)`). This correctly marks looseDir@10 and looseDir@9 as overrides of the searchTree (max=8), but looseDir@5 as non-override. Flag Option B as a future fidelity upgrade.

## Capability 3 — Loose-override deploy mode (DEPLOY-08)

### What to build
A third deploy model alongside the existing `absolute-path` and `hardlink-shadow` (`DeployDialog.tsx:71`): **`loose-override`**. It writes each staged loose file straight into the client cfg's **highest-priority `searchPath` directory**, mirroring the logical path. No `packPatch` (no `.tre` build), no `cfgActivator` (no `.cfg` surgery), no snapshot of the cfg (the cfg is never touched).

### Flow
1. **Identify the target override dir** from the selected client's cfg: parse all `searchPath` entries, pick the one with the **highest priority** (ties → later-added per A4). In the live client that's `searchPath_00_10 = D:/Code/swg-client-v2/stage/override`. (Reuse the new `parseSearchNodes` from Capability 2.) Surface the chosen dir in the UI for the user to confirm.
2. **Override-dir guard**: if `looseDirs[0].rawPriority > ClientMountOrder.maxPriority`, warn or refuse — the engine won't load a searchPath above `maxSearchPriority`, so deploying there is silent no-op.
3. **Cross-deploy prune**: at the start of `deployLoose`, if a prior `LooseDeployRecord` is provided, call `resetLoose(priorRecord)` first to remove files from the previous deploy that are absent from the new one.
4. **Materialize staged files**: from `flatten(activeVersionId)`, for each `add`/`modify` entry: snapshot the original if `destPath` already exists (`preExisted=true`, snapshot to `<studioDir>/snapshots/<virtualPath>`), then write `<overrideDir>/<virtualPath>` atomically. For `delete` entries: no-op + surface in `skippedDeletes[]`.
5. **Record what was written**: `LooseDeployRecord` listing every absolute file path created, whether it pre-existed, and its snapshot path.
6. **Reset/undo**: for `preExisted=true` entries → RESTORE from snapshot (copy back, delete snapshot); for `preExisted=false` entries → delete. Never touches the `client.cfg`.

### Why snapshot/restore is required (B3)
`ksk_all_spaceterminal.dds` already exists in `stage/override/texture/` from the 2026-06-28 hand-proof. Without snapshot/restore, `resetLoose` would skip the file (`preExisted=true` → was not deleted) → the ORIGINAL bytes are already gone (overwritten). The original content is unrecoverable. Snapshot before overwrite, restore on reset.

### Why this is the right model for this client class
- The cfg is **generated** (A7) — any hand-edit is clobbered on regen. Loose-override touches zero cfg.
- The override dir already has top searchPath priority (proven in-game, A6) — writing there is the modder's actual iterate loop.
- The `maxSearchPriority=12` + slot-chooser logic in `cfgActivator`/`chooseSlot` is blind to `searchTOC`/`searchPath` priorities and would pick a colliding/too-low slot — another reason NOT to reuse the patch-prepend path here.

## Common Pitfalls (cross-cutting)

### Pitfall 1: Hardcoding the override slot number
**What goes wrong:** Code assumes `searchPath_00_10` or `_11`; the live cfg and template disagree, and other installs differ.
**How to avoid:** Always parse the cfg and select the max-priority `searchPath` at runtime. Verified: live=`_10`, template=`_11`.
**Warning sign:** A literal `10`/`11` or `_00_` in deploy code.

### Pitfall 2: Treating ` COT1000` as `COT2000` (or vice-versa)
**What goes wrong:** The two master-index magics differ by one digit; `COT2000` is the encrypted Restoration variant (out of scope).
**How to avoid:** Validate token=` COT` (`20 43 4F 54`) + version=`1000` (`31 30 30 30`) for the SearchTOC path; ` COT2000` 8-byte literal → reject/skip.

### Pitfall 3: Forgetting quote-stripping on cfg values
**What goes wrong:** `searchTOC`/`TOCTreePath` values are quoted (spaces in the path); unstripped quotes make `existsSync` fail → silent empty mount.
**How to avoid:** Strip surrounding `"` after the existing regex capture.

### Pitfall 4: Reusing the patch-prepend cfg surgery for the dev client
**What goes wrong:** `cfgActivator`/`chooseSlot` write a `searchTree` slot into a generated cfg with `maxSearchPriority=12`, blind to the searchTOC/searchPath priorities → colliding/too-low slot, clobbered on regen.
**How to avoid:** The loose-override branch must NOT call `packPatch`/`activatePatch`/`ensureInclude`/`snapshotCfg`.

### Pitfall 5: Regressing searchTree-only clients
**What goes wrong:** Refactoring `parseSearchTree`/`resolveClientMountOrder` breaks Infinity/SWGEmu mount.
**How to avoid:** The unified parser must produce byte-identical mount order for a searchTree-only cfg; keep a test fixture for each existing install (criterion 5).

### Pitfall 6: Double-mount clobbering the store (B1)
**What goes wrong:** Calling `mountTrePaths` twice causes `mountComplete` (treStore.ts:159) to replace the store wholesale, erasing the first mount's archives and vfsEntries.
**How to avoid:** ONE `mountTrePaths` call for the full merged list.

### Pitfall 7: Pre-existing file not restorable after reset (B3)
**What goes wrong:** `deployLoose` overwrites a pre-existing override file; `resetLoose` sees `preExisted=true` and skips it → original bytes gone.
**How to avoid:** Snapshot pre-existing files before overwrite; RESTORE on reset (not skip).
