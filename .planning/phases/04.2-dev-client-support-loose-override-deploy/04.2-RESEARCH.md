## Summary

This phase makes the toolkit work with the **dev/modder decoupled client** (swg-client-v2 / SWG Source): a runnable binary dir with `client.cfg` and **zero `.tre`**, whose game data lives in an external install referenced by absolute path. Three capabilities ship as one vertical slice: (1) detect `client.cfg` layouts + manual override; (2) extend the mount to read the FULL base via `searchTOC` (a `.toc` master index) + `searchPath` loose dirs, not just `searchTree`; (3) a "deploy into the top-priority loose `searchPath` override dir" mode.

The good news from this research: **no new byte-level format risk.** The `.toc` SearchTOC format is fully pinned down — the C++ `SearchTOC::Header`/`TableOfContentsEntry` structs (`TreeFile_SearchNode.h:270-299`), the blender plugin's `read_search_toc_header`/`read_search_toc_entries`, and the real 13.8 MB `sku0_client.toc` header all agree exactly (36-byte header, 24-byte entries, on-disk magic ` COT1000`). And crucially, **mounting the base does not require parsing the 193k-entry global index at all** — the `.toc`'s tree-name block lists its 131 constituent `.tre` archives, each of which is an independently-mountable standard TRE the toolkit's existing native mount already reads. So `searchTOC` support reduces to: read the tree-name block, prepend `TOCTreePath`, mount those 131 `.tre` paths through the existing `mountSearchableAsync` at the TOC's priority.

The two real engineering decisions for the planner are: **(a)** how to represent `searchPath` *loose directories* in the mount — the native mount (`mountSearchableAsync`) accepts only `.tre` file paths, so loose dirs need a TS VFS overlay or a native extension; and **(b)** the deploy-to-override-dir mode is a genuinely new, *simpler* deploy branch (write loose files into the highest-priority `searchPath` dir, no TRE pack, no `.cfg` surgery) that must NOT reuse the `packPatch`/`cfgActivator` machinery.

**Primary recommendation:** Add a TS `.toc` reader that parses only the SearchTOC header + tree-name block (sufficient for mount); expand each `searchTOC` cfg entry into its constituent TOCTreePath-prefixed `.tre` paths and feed them into the existing native mount; add a `client.cfg` layout row whose TRE dir is resolved from the cfg (not a fixed subfolder); and add a third deploy model `loose-override` that writes staged files straight into the cfg's highest-priority `searchPath` dir with a written-files manifest for non-destructive reset.

## Capability 2 — `searchTOC` / `searchPath` / `TOCTreePath` mount (TRE-05)

### The key insight: mount the base WITHOUT parsing the 193k global index

A `searchTOC` `.toc` is a *master aggregate index* over N constituent `.tre` archives. Each constituent `.tre` (`bottom.tre`, `data_animation_00.tre`, …) is an **independently-valid standard TRE** the toolkit's existing native core already mounts. The `.toc`'s 193,475-entry global table is a runtime optimization (one binary search instead of walking 131 archives); it is **not** required to reproduce the file set. The union of the 131 `.tre` internal TOCs *is* the same logical file set (the `.toc` is built from those TREs by `TreeFileBuilder`).

**Therefore the mount strategy is:** parse ONLY the `.toc` header + tree-name block to get the list of constituent `.tre` names → prepend `TOCTreePath` → mount those `.tre` paths via the existing `mountSearchableAsync(paths, priorities)` at the `searchTOC` entry's priority. **No new native format. No 193k-entry parse.** This matches the ROADMAP's "NOT new byte-level format work."

> Cross-check / optional: the full 193k index (`read_search_toc_entries`) gives `(path → which .tre, offset, length)` and is useful for a *verification* pass (does mounting 131 TREs surface the same path set the `.toc` advertises?) and faster single-asset resolution. Recommend building the header+tree-name reader first; treat the full index reader as an optional verification tool, not a mount dependency.

### `.toc` (SearchTOC) byte format — VERIFIED THREE WAYS

Verified against: C++ `TreeFile::SearchTOC::Header`/`TableOfContentsEntry` (`TreeFile_SearchNode.h:270-299`), the blender plugin `read_search_toc_header`/`read_search_toc_entries` (`../swg-blender-plugin/swg_pipeline/tre_reader.py:335-413`), AND the real `D:/Code/SWGSource Client v3.0/sku0_client.toc` header bytes (read this session). All three agree exactly.

**Header — 36 bytes, little-endian:**

| Offset | Size | Field (C++ name) | sku0 real value | Notes |
|--------|------|------------------|-----------------|-------|
| 0 | 4 | `token` | `20 43 4F 54` = ` COT` | TAG_TOC. On disk ASCII reads ` COT` (leading space). |
| 4 | 4 | `version` | `31 30 30 30` = `1000` | TAG_0001. On disk ASCII reads `1000`. |
| 8 | 1 | `tocCompressor` | `00` | 0 = uncompressed; nonzero = zlib |
| 9 | 1 | `fileNameBlockCompressor` | `00` | 0 = uncompressed; nonzero = zlib |
| 10 | 1 | `unusedOne` | `00` | alignment |
| 11 | 1 | `unusedTwo` | `00` | alignment |
| 12 | 4 | `numberOfFiles` | `0x0002F3C3` = 193475 | global indexed path count |
| 16 | 4 | `sizeOfTOC` | `0x0046DA48` = 4,643,400 | = 193475 × 24 (uncompressed here) |
| 20 | 4 | `sizeOfNameBlock` | `0x008D06DF` = 9,242,335 | on-disk name block size |
| 24 | 4 | `uncompSizeOfNameBlock` | `0x008D06DF` = 9,242,335 | == sizeOfNameBlock when uncompressed |
| 28 | 4 | `numberOfTreeFiles` | `0x00000083` = 131 | count of constituent `.tre` archives |
| 32 | 4 | `sizeOfTreeFileNameBlock` | `0x00000AC5` = 2757 | bytes of null-terminated `.tre` names |

> ⚠️ **Endianness gotcha for the planner:** the C++ stores `token`/`version` as `Tag` (uint32). On disk the token bytes are `20 43 4F 54` which the human eye reads as ` COT` and the version `31 30 30 30` reads as `1000` — so a full hexdump of the file shows the magic string **` COT1000`**. The blender reader encodes this as `TAG_TOC_LE = struct.pack("<I", 0x544F4320)` and `TAG_0001_LE = struct.pack("<I", 0x30303031)`. Do **not** confuse this with `COT2000` (Restoration, magic ` COT2000`, 8-byte literal) — they differ only in the version digit and `COT2000` is out of scope.

**On-disk block order (after the 36-byte header):**
1. **Tree-file-name block** (`sizeOfTreeFileNameBlock` bytes): `numberOfTreeFiles` null-terminated ASCII `.tre` names back-to-back. (sku0: starts `bottom.tre\0default_patch.tre\0data_animation_00.tre\0…`, 131 names = 2757 bytes.) **This is all the mount needs.**
2. **Table of contents** (`sizeOfTOC` bytes, zlib-compressed iff `tocCompressor != 0`): `numberOfFiles` × 24-byte entries.
3. **Name block** (`sizeOfNameBlock` bytes on disk → `uncompSizeOfNameBlock` uncompressed, zlib iff `fileNameBlockCompressor != 0`): packed null-terminated logical path strings.

**TableOfContentsEntry — 24 bytes, little-endian (only needed for the optional full-index reader):**

| Offset | Size | Field | Notes |
|--------|------|-------|-------|
| 0 | 1 | `compressor` | 0=stored, else zlib |
| 1 | 1 | `unused` | |
| 2 | 2 | `treeFileIndex` | index into the tree-name list → which `.tre` serves this path |
| 4 | 4 | `crc` | |
| 8 | 4 | `fileNameOffset` | **on disk this is the filename LENGTH**, rewritten to a running offset after load (C++ `:699-711`; python `:385-389`) |
| 12 | 4 | `offset` | byte offset INTO the constituent `.tre` payload region |
| 16 | 4 | `length` | uncompressed size |
| 20 | 4 | `compressedLength` | on-disk size when compressed |

> Note the on-disk→in-memory rewrite of `fileNameOffset`: the file stores per-entry filename *lengths*; both readers convert them to cumulative offsets into the name block (`offset[i] = Σ(length[j]+1)` for j<i). Any toolkit full-index reader MUST replicate this, exactly as both ground-truth readers do.

> Payload reading via the `.toc` (C++ `SearchTOC::open` `:891-947`): the engine reads payload bytes directly from `m_treeFiles[treeFileIndex]` at `entry.offset` for `entry.length`/`compressedLength` and zlib-expands if compressed — it does **not** consult the constituent `.tre`'s own internal TOC. This confirms the offsets are absolute into the `.tre`. For the toolkit's expand-to-`.tre` mount strategy this is irrelevant (the native core reads each `.tre`'s own TOC, which points at the same bytes), but it matters if you ever build a direct `.toc`-payload reader.

### `TOCTreePath` application (A3, confirmed)
For each tree-file name N in the `.toc`, the engine opens the first of: `N` (cwd-relative), then `<TOCTreePath_0> + N`, `<TOCTreePath_1> + N`, … (`TreeFile_SearchNode.cpp:639-668`). `TOCTreePath` is a raw **string prefix** with a trailing slash (e.g. `D:/Code/SWGSource Client v3.0/` + `bottom.tre` = `D:/Code/SWGSource Client v3.0/bottom.tre`). The toolkit must read all `TOCTreePath` values (there can be multiple) and resolve each tree name against them, first-existing wins.

### `searchPath` loose-dir semantics (confirmed)
`SearchPath::makeAbsolutePath` (`:96-105`): logical lookup `texture/foo.dds` → `<m_pathName>/texture/foo.dds`. The dir path is canonicalized to absolute with forward slashes, trailing slash stripped (`:60-76`). `exists`/`open` hit the loose file directly. So a `searchPath` dir overlays loose files by mirroring the logical path tree under it.

### Mount precedence — building one flat ordered list across all three families
`clientSearchOrder.ts` currently builds the mount order from `searchTree` only, sorting `(priority DESC, sku DESC, cfgOrder DESC)` and assigning strictly-descending native priorities. Extend `parseSearchTree` → a `parseSearchNodes` that also captures `searchPath` and `searchTOC` entries, tagged by family. Then:
- Expand each `searchTOC` into its constituent `.tre` paths (TOCTreePath-resolved) at the TOC entry's priority.
- Keep `searchTree` entries as-is.
- Represent `searchPath` dirs as loose-overlay nodes (see decision below).
- Order across ALL families by `(priority DESC, then later-added-first)`. Per A1, within one priority the install order is path→tree→toc, so "later added" makes toc win over tree over path *at equal priority*. **In the live swg-client-v2 cfg there are NO equal-priority cross-family collisions** (TOC@0-3, path@5/9/10, tree@7/8), so the simple `priority DESC` ordering is exact here; document the general tie-rule for correctness but it won't bite this client.

### THE decision point: how to mount `searchPath` loose dirs
The native mount API is `mountSearchableAsync(paths: string[], priorities: number[])` (`native-core/index.d.ts:372`) — it accepts **`.tre` file paths only**. There is no loose-dir/`addSearchPath` native API (grep confirms). Options for the planner:

| Option | Approach | Pros | Cons |
|--------|----------|------|------|
| **A. TS VFS overlay (recommended for MVP)** | Scan each `searchPath` dir recursively in TS; inject loose files as highest-priority override entries into the treStore VFS (the `isOverride` flag already exists in the columnar VFS — `treMount.ts:110`) | No native change; aligns with the loose-override deploy thesis; criterion 4's proof asset is in the TOC base anyway | Loose-dir browse is a TS-side overlay separate from native resolution; must keep in sync on deploy |
| **B. Native `addSearchPath` node** | Extend native mount to register a loose-dir search node mirroring `SearchPath` | One unified resolution path matching the engine exactly | New native work; larger surface; the binary-stays-binary rule applies |

**Recommendation:** Option A for this phase. Criterion 2's load-bearing proof (`ksk_all_spaceterminal.dds` resolves+extracts) is satisfied by the `searchTOC` base mount alone; loose-dir overlay is needed for *browsing* the override dir and showing deployed files, which a TS overlay handles. Flag Option B as a future fidelity upgrade.

### Existing files that change
| File | Change |
|------|--------|
| `services/clientSearchOrder.ts` | `parseSearchTree` → parse `searchPath`/`searchTOC`/`TOCTreePath` too; strip quotes from values; resolve TOCTreePath; emit a unified ordered mount list |
| new `services/tocReader.ts` | TS SearchTOC reader: header (36B) + tree-name block → `.tre` name list; (optional) full 24B-entry index for verification |

### Pitfalls (mount)
- **Quote stripping**: `searchTOC`/`TOCTreePath` values are quoted in the cfg; failing to strip quotes makes file paths not exist → silent empty mount.
- **Forward vs back slashes**: cfg uses forward slashes on Windows; `path.join`/`existsSync` handle both, but string-prefix `TOCTreePath + name` concatenation (mirroring the engine) must preserve the trailing slash.
- **sku suffix is not always `_00_`**: live cfg has `_00_`/`_01_`/`_02_`/`_03_` — use the captured sku group, don't assume.
- **Don't double-mount**: `searchPath_00_9` is the data root; if you also expand TOCs from that same root you can surface the same `.tre` twice. De-dup by absolute path (the existing `seen` set in `clientSearchOrder.ts:122` does this for searchTree — extend it).
- **TRE version 5000 vs the C++ `SearchTree` switch only accepting 0004/0005**: the constituent `.tre` files are version `5000` (`buildTre('5000')` is already the toolkit default per `packPatch.ts:116`), and the native core already reads `v5000` (`treMount.ts:34`). The swg-client-v2 `SearchTree::validate` only accepts `TAG_0004` — but the engine reads these via `SearchTOC` (offset-based), not `SearchTree`, so the version switch is moot for TOC-served files. UNVERIFIED whether the constituent `.tre`s are 5000 or 0005 (the `.toc` reads them positionally regardless); the toolkit native core handles both, so no action — but note it.

## Capability 3 — Loose-override deploy mode (DEPLOY-08)

### What to build
A third deploy model alongside the existing `absolute-path` and `hardlink-shadow` (`DeployDialog.tsx:71`): **`loose-override`**. It writes each staged loose file straight into the client cfg's **highest-priority `searchPath` directory**, mirroring the logical path. No `packPatch` (no `.tre` build), no `cfgActivator` (no `.cfg` surgery), no snapshot of the cfg (the cfg is never touched).

### Flow
1. **Identify the target override dir** from the selected client's cfg: parse all `searchPath` entries, pick the one with the **highest priority** (ties → later-added per A4). In the live client that's `searchPath_00_10 = D:/Code/swg-client-v2/stage/override`. (Reuse the new `parseSearchNodes` from Capability 2.) Surface the chosen dir in the UI for the user to confirm.
2. **Materialize staged files**: from `flatten(activeVersionId)` (the version graph, NOT the live staging store — same W2 rule as the existing deploy, `DeployDialog.tsx:309`), for each entry write `<overrideDir>/<virtualPath>` (create parent dirs). Use the existing `replacementFilePath` source bytes (same source `packPatch` reads, `packPatch.ts:104`). Honor `action`: `add`/`modify` → write file; `delete` → (loose dirs can't tombstone a base file) remove a previously-deployed loose file if present, else no-op + warn.
3. **Record what was written**: a new deploy-record variant listing every absolute file path created (and whether it pre-existed). This is the reset manifest.
4. **Reset/undo**: delete exactly the files this deploy wrote (that did NOT pre-exist), leaving any pre-existing override files and the install + `client.cfg` byte-untouched. (Compare to the existing reset which does cfg line-surgery / snapshot restore — none of that applies here.)

### Why this is the right model for this client class
- The cfg is **generated** (A7) — any hand-edit is clobbered on regen. Loose-override touches zero cfg.
- The override dir already has top searchPath priority (proven in-game, A6) — writing there is the modder's actual iterate loop.
- The `maxSearchPriority=12` + slot-chooser logic in `cfgActivator`/`chooseSlot` is blind to `searchTOC`/`searchPath` priorities and would pick a colliding/too-low slot — another reason NOT to reuse the patch-prepend path here.
- The `ConfigFile` whitespace-truncation constraint (B6, `packPatch.ts:53`) is **moot** here because we never write a cfg value.

### Pitfalls (deploy)
- **Wrong searchPath chosen**: picking `searchPath_00_9` (the shared data root) instead of `_00_10` (the override dir) would write into the shared install. The selector MUST take the max-priority searchPath and SHOULD let the user confirm. Consider also offering a manual override-dir picker.
- **Path traversal**: reuse `isVirtualPathSafe` (`packPatch.ts:85`) before joining `virtualPath` to the override dir — a `..` or drive-letter virtualPath must be rejected (writing outside the override dir).
- **Non-destructive reset accuracy**: must distinguish files this deploy created vs files that already existed in the override dir (e.g. the client ships `stage/override` content). Record a `preExisted` flag per file; reset only removes files it created. Empty-dir cleanup should also only remove dirs it created.
- **`delete` action semantics**: a loose override can't hide a base-TRE file (loose files only ADD/override). A staged `delete` has no clean loose-override equivalent — surface a warning rather than silently dropping it.
- **Idempotent re-deploy**: a second deploy of the same version should be byte-identical and update the written-files manifest, not accumulate stale files. Track and prune files written by a prior loose deploy of the same project.

## Common Pitfalls (cross-cutting)

### Pitfall 1: Hardcoding the override slot number
**What goes wrong:** Code assumes `searchPath_00_10` or `_11`; the live cfg and template disagree, and other installs differ.
**How to avoid:** Always parse the cfg and select the max-priority `searchPath` at runtime. Verified: live=`_10`, template=`_11`.
**Warning sign:** A literal `10`/`11` or `_00_` in deploy code.

### Pitfall 2: Treating ` COT1000` as `COT2000` (or vice-versa)
**What goes wrong:** The two master-index magics differ by one digit; `COT2000` is the encrypted Restoration variant (out of scope).
**How to avoid:** Validate token=` COT` (`20 43 4F 54`) + version=`1000` (`31 30 30 30`) for the SearchTOC path; ` COT2000` 8-byte literal → reject/skip.

### Pitfall 3: Forgetting quote-stripping on cfg values
**What goes wrong:** `searchTOC`/`TOCTreePath` values are quoted (spaces in the path); unstripped quotes make `existsSync` fail → silent empty mount.
**How to avoid:** Strip surrounding `"` after the existing regex capture.

### Pitfall 4: Reusing the patch-prepend cfg surgery for the dev client
**What goes wrong:** `cfgActivator`/`chooseSlot` write a `searchTree` slot into a generated cfg with `maxSearchPriority=12`, blind to the searchTOC/searchPath priorities → colliding/too-low slot, clobbered on regen.
**How to avoid:** The loose-override branch must NOT call `packPatch`/`activatePatch`/`ensureInclude`/`snapshotCfg`.

### Pitfall 5: Regressing searchTree-only clients
**What goes wrong:** Refactoring `parseSearchTree`/`resolveClientMountOrder` breaks Infinity/SWGEmu mount.
**How to avoid:** The unified parser must produce byte-identical mount order for a searchTree-only cfg; keep a test fixture for each existing install (criterion 5).

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
