## Summary

Phase 04.1 is **almost entirely renderer-side React/dockview composition plus Node `fs` plumbing** — the Phase-4 deploy engine (`packPatch`, `changesetService`, `cfgActivator`, `shadowBaseService`, `clientLocator`, `workspaceService`) is complete and verified in-client; this phase **re-composes, re-defaults, and connects** it. Crucially, **no new external npm packages are required** — every capability uses Node builtins (`fs`, `path`, `crypto`, `child_process`) already used throughout the deploy services, plus the already-installed `dockview@6.6.1`, `zustand`, and React 19. That removes an entire risk class (slopsquatting / supply chain) from this phase.

The hard ground-truth (absolute `searchTree` paths accepted verbatim; whitespace truncation; v5000 plain-zlib) is **LOCKED upstream** and must not be re-derived. The genuinely *new* technical work the planner needs is: (1) swap the `shadowBaseService` copy loop to `fs.promises.link` with an EXDEV same-volume guard; (2) add a `projectBinding` service that detects a client, persists `clientPath`+`kind` to a new `.studio/workspace.json`, and auto-drives the existing `mountSearchableAsync`; (3) build a release-pattern detection table to replace the hardcoded `swgemu.cfg`/`Live/` assumptions scattered across `clientLocator`, `DeployDialog`, and `shadowBaseService`; (4) a layout-version key so removing the `staging`/`changesets`/`vcs` panel ids doesn't strand a saved dockview layout; (5) fix a verified duplicate `[SharedFile]` header (two writers); (6) extract `StagingPanelBody` + the timeline body into one `DeployPanel`; (7) seed a Baseline changeset; (8) relocate the cfg snapshot + override build dir to a whitespace-free `.studio` and make undo a whole-file cfg restore; (9) centralize the IPC channel types that caused a silent deploy bug.

**Primary recommendation:** Reuse the existing engine functions verbatim; treat 04.1 as wiring + composition + three small `fs` behavior changes (hardlink, snapshot-restore, `.studio` relocation). Do NOT introduce any new dependency, styling layer, or byte-level format code.

### Pattern 1: Hardlink full-shadow with same-volume guard (D-02 / DEPLOY-06)
**What:** Replace `shadowBaseService.deployShadowBase`'s multi-GB `fs.promises.copyFile` loop with `fs.promises.link` (hardlink). On Windows/NTFS this maps to `CreateHardLinkW` at ~0 cost when source and dest are on the same volume.
**When to use:** Only the opt-in "throwaway isolated client" model. The DEFAULT (D-05) is the absolute-path override `.tre` with NO shadow dir at all.
**Key facts:**
- `fs.link(existing, new)` throws **`EXDEV`** when the hardlink would cross volumes. [CITED: nodejs.org/api/fs.html]
- Detect same-volume up front via `fs.statSync(srcDir).dev === fs.statSync(destParent).dev` (Node's `Stats.dev` maps to the volume serial on Windows). [CITED: nodejs.org/api/fs.html]
- **Fallback ladder when cross-volume:** (1) fall back to `copyFile` (the retired model-C behavior, kept ONLY as the cross-volume fallback), or (2) surface a `--color-warn` "shadow dir must be on the same drive as the client; using copy" notice. Planner picks; both are acceptable.
**Example:**
```typescript
// Source pattern — replaces shadowBaseService.ts:273-280 copy loop
import fs from 'fs';
import path from 'path';

function sameVolume(a: string, b: string): boolean {
  // Stats.dev === volume serial on Windows (per Node fs docs)
  return fs.statSync(a).dev === fs.statSync(b).dev;
}

async function materializeBase(srcLiveDir: string, tmpShadowDir: string): Promise<void> {
  const treFiles = (await fs.promises.readdir(srcLiveDir)).filter(f => f.endsWith('.tre'));
  const canLink = sameVolume(srcLiveDir, path.dirname(tmpShadowDir));
  for (const f of treFiles) {
    const src = path.join(srcLiveDir, f);
    const dst = path.join(tmpShadowDir, f);
    if (canLink) {
      try { await fs.promises.link(src, dst); continue; } catch (e: any) {
        if (e?.code !== 'EXDEV') throw e;  // unexpected — surface it
      }
    }
    await fs.promises.copyFile(src, dst);  // cross-volume fallback only
  }
}
```
The existing `checkFreeDisk` pre-flight (`shadowBaseService.ts:143-185`) should be SKIPPED for the hardlink path (hardlinks consume ~0 bytes) and kept only for the copy fallback. The W4 path-containment guard (`shadowBaseService.ts:237-242`) and W8 cleanup stay.

### Pattern 5: cfg snapshot + whole-file restore into `.studio` (D-06/D-07)
**What:** Before the first cfg mutation, copy the client's original cfg(s) into `.studio` (whitespace-free path). Undo = copy that snapshot back over the client cfg (whole-file), for ALL deploy models. This **supersedes** line-surgery (`deactivatePatch`, `resetShadow`) as the primary reset path.
**Current behavior to change (verified):**
- `cfgActivator.activatePatch` writes the backup as `cfgPath + '.swgtoolkit.bak'` — i.e. NEXT TO the cfg, inside the client dir (`cfgActivator.ts:107-108`). Move into `.studio`.
- `shadowBaseService` writes `.shadow.bak` next to the cfg (`shadowBaseService.ts:305-306`). Move into `.studio`.
- The override build output path is already `.studio/build/<patchName>` (`DeployDialog.tsx:277`) — good, but `.studio` location must become whitespace-free (Pattern 6 / D-06).
**`.studio` relocation (D-06):** `getStudioDir(folderPath) = path.join(folderPath, '.studio')` (`workspaceService.ts:41-43`). If the project folder contains a space (e.g. `My Mod`), an absolute `searchTree=<.studio/build/patch.tre>` value **truncates at the first space** and the client silently fails to load the override. The fix is to resolve `.studio` (or at minimum the `build/` override dir + cfg snapshot) under a **whitespace-free app-root path keyed by project** (e.g. `<appRoot>/.studio/<projectId>/`). This touches `getStudioDir` and every caller that passes `studioDir` (changesetService, shadowBaseService, DeployDialog). [VERIFIED via grep: `studioDir` is threaded through `changesetService.*`, `shadowBaseService.deployShadowBase`, `DeployDialog.handleDeploy`.]

### Pattern 6: dockview layout-version clear (D-03 / DEPLOY-07)
**What:** A `LAYOUT_VERSION` constant; on load, if the persisted layout's version differs (or any panel id is retired), discard it and rebuild via `buildInitialLayout`. Also a user-facing **Reset layout** affordance.
**Current behavior (verified):** `WorkspaceShell.onReady` reads `localStorage[LAYOUT_STORAGE_KEY='swg-workspace-layout']`, tries `api.fromJSON`, and on *throw* falls back to `buildInitialLayout` (`WorkspaceShell.tsx:46-74`). `buildInitialLayout` registers `staging`, `changesets`, `vcs` as `within`-inspector tabs (`workspace-config.ts:96-114`). `panelComponents` registers `staging`/`changesets`/`vcs` (`WorkspaceShell.tsx:38-40`).
**Why try/catch is insufficient:** dockview `fromJSON` does **not** reliably throw on an *unknown component id* — it can leave the dock in a broken/stranded state (dockview issue #341). Removing `staging`/`changesets` and adding `deploy` therefore requires an explicit version guard, not reliance on the catch. [CITED: github.com/mathuo/dockview/issues/341]
**Mechanism:**
```typescript
// workspace-config.ts
export const LAYOUT_VERSION = 2;                       // bump on any panel-id change
export const LAYOUT_STORAGE_KEY = 'swg-workspace-layout';
export const LAYOUT_VERSION_KEY  = 'swg-workspace-layout-version';

// WorkspaceShell.onReady
const savedVer = Number(localStorage.getItem(LAYOUT_VERSION_KEY) ?? '0');
const saved = localStorage.getItem(LAYOUT_STORAGE_KEY);
if (saved && savedVer === LAYOUT_VERSION) {
  try { event.api.fromJSON(JSON.parse(saved)); }
  catch { event.api.clear(); buildInitialLayout(event.api); }
} else {
  buildInitialLayout(event.api);                       // version mismatch → fresh default
  localStorage.setItem(LAYOUT_VERSION_KEY, String(LAYOUT_VERSION));
}
```
`dockview@6.6.1` exposes `api.clear()` for an in-place reset. The **Reset layout** menu/status-bar control calls `localStorage.removeItem(LAYOUT_STORAGE_KEY)` + `api.clear()` + `buildInitialLayout(api)` (no reload needed — the api is already in `apiRef`). `buildInitialLayout` must be updated to add a single `deploy` panel `within` the inspector group (keeping `vcs`).

### Pattern 7: Baseline changeset seed (D-08)
**What:** Seed the manifest with a `Baseline` root node (zero deltas, `parentId: null`) at project creation; set `activeVersionId` to it.
**Why a direct write (not `sealVersion`):** `sealVersion` has an N4 "Nothing new to commit" guard (`changesetService.ts:225-230`) that throws on zero deltas. Baseline must be written directly into the manifest in `createWorkspace` (`workspaceService.ts:215-225` currently writes an empty manifest) or via a dedicated `seedBaseline()` in `changesetService`. The Baseline node renders as the dashed-square root (UI-SPEC Surface 1); "Deploy (reset to stock)" = select Baseline → deploy an empty override.

### Pattern 8: Centralized IPC channel types (centralize-ipc-channel-types)
**What:** Define each IPC channel's return type once and import a typed `invoke` everywhere.
**Why (verified bug):** Every call site locally re-casts `require('electron')` with an inline channel type — `WorkspaceEntry.tsx:26-30` (`pick-dir → string[]`), `StagingPanel.tsx:258-262` (`pick-file → string[]`), `DeployDialog.tsx:176-178` (`pick-dir → string[]`), `TreVfsBrowser.tsx:114-116` (`→ string[]`). The handlers all return `string[]` (`backend/src/main.ts:234-263`). The historical bug: `DeployDialog` once typed `pick-dir` as `string | null`, so `[]` was truthy and `path.join(array,…)` threw → caught silently → client never selected → Deploy stayed disabled (documented in the todo). The fix is a single source of truth in `@swg/contracts` (`ipc.ts` currently only holds SAB message types — extend it with a channel→return-type map) so a handler/return mismatch becomes a compile error.

## Common Pitfalls

### Pitfall 1: Absolute `searchTree` path with a space silently fails to load
**What goes wrong:** The override `.tre` registers but the client never loads it; no error.
**Why:** SWG `ConfigFile` truncates a `searchTree` value at the first whitespace (LOCKED axiom 2). If `.studio` is under a project folder named e.g. `My Mod`, the path truncates.
**How to avoid:** Resolve `.studio` (build dir + cfg snapshot) under a whitespace-free app-root path (D-06, Pattern 5). `buildPatchName` already sanitizes the *filename*; the *directory* is the remaining risk.
**Warning sign:** A green "deployed" toast but no in-game change; the cfg line contains a path that visibly ends mid-directory.

### Pitfall 2: dockview stranded by a retired panel id
**What goes wrong:** After removing `staging`/`changesets`, a returning user's saved layout renders an empty/broken pane and the workflow is soft-bricked.
**Why:** `fromJSON` may not throw on an unknown component id (dockview #341); the existing try/catch never fires.
**How to avoid:** Layout-version guard (Pattern 6) + the user-facing Reset layout control (D-03/DEPLOY-07).
**Warning sign:** Blank panel where Deploy should be; console has no error.

### Pitfall 3: Cross-volume hardlink (EXDEV)
**What goes wrong:** Hardlink full-shadow throws if the work dir and the client are on different drives (e.g. client on `D:`, `.studio` on `C:`).
**Why:** NTFS hardlinks are intra-volume only.
**How to avoid:** `Stats.dev` same-volume check before linking; fall back to `copyFile` (Pattern 1).
**Warning sign:** `EXDEV: cross-device link not permitted`.

### Pitfall 4: Duplicate `[SharedFile]` header (verified bug)
**What goes wrong:** `swgtoolkit.cfg` ends up with two `[SharedFile]` lines.
**Why:** TWO writers each add the header — `DeployDialog.tsx:354` (`'[SharedFile]\r\n'` on create) AND `cfgActivator.activatePatch` appends `'[SharedFile]'` (`cfgActivator.ts:128`); `shadowBaseService.ts:301` has the same overlap.
**How to avoid:** Pick ONE owner. Cleanest: create the file EMPTY (no header) in DeployDialog/shadowBaseService, and make `activatePatch` the sole header writer (idempotent — check for an existing `[SharedFile]` before adding). Verify a second deploy doesn't add a third.
**Warning sign:** `[SharedFile]\n[SharedFile]` on disk (client tolerates it, so it's silent).

### Pitfall 5: Auto-select not wired → Deploy looks broken (verified)
**What goes wrong:** Deploy button greyed even with a bound client.
**Why:** `isDeployDisabled = phase !== 'idle' || !selectedClient` (`DeployDialog.tsx:438`) and nothing sets `selectedClient` from the binding.
**How to avoid:** D-12 — set `selectedClient` from `clientPath` in the open-effect (`DeployDialog.tsx:91-118`).

### Pitfall 6: jsdom-green ≠ Electron-runs
**What goes wrong:** Unit tests pass but the real Electron flow (IPC, dockview, native mount) breaks.
**Why:** Renderer tests run in jsdom; IPC/dialog/native addon are stubbed/absent (memory `design-test-hook-points-for-harness`, `feedback-executor-integration-blind-spot`).
**How to avoid:** Add env-gated test hooks (extend the `window.__*` pattern) for the binding/auto-mount/deploy paths; gate end-to-end claims on a real-Electron checkpoint, not jsdom.
