## Bug B — re-entrant scene swap: FIXED, VERIFIED LIVE

`gameLoadScene` was called from `overlay.cpp:960` inside `renderFrame()` inside `hkSwapChainPresent`.
FATAL: `InputScheme.cpp(480) fetchGroundInputMap called on a new player without releasing old one`.

**The fix took two rounds, and the second was the real one.** Draining outside Present (`438e1a6`) was
NECESSARY BUT NOT SUFFICIENT: after it landed, "Editor scene" still FATAL'd in-world but **succeeded
from the login screen**. That contrast is what cracked it — the call site is identical in both cases,
so the variable is what is already loaded, not where the call comes from. The login screen has no
GroundScene/player to release.

Ground truth: Utinni's `hkMainLoop` (`game.cpp:499-554`) is a **two-frame state machine**, not
"cleanup then load" in one call — frame N runs `cleanupScene` and latches `sceneCleaned`; frame N+1
runs `loadScene`. The engine needs a full tick between teardown and construction. Reproduced here by
re-queueing the command once after cleanup, plus **bounding the drain to a snapshot of the queue count
at entry** — a `while (count > 0)` drain would consume the re-queued command in the same pass and
collapse the very frame gap the sequencing exists to create.

**Verified live 2026-08-02:** Editor scene works from in-world AND from the login screen; Reload
current scene works. DebugView shows five clean `frame 1: cleanupScene` -> `frame 2: loadScene` cycles.

Drain point: the **preferred** `game::mainLoop` detour (not the fallback). `hkMainLoop` calls the
original tick first, so Present's entire call chain has unwound before the drain — a stack frame ABOVE
Present, not nested inside it. Matches Utinni, which already issues `game::loadScene` from this exact
call site. The post-`g_origPresent()` fallback is wired but activates only if `game::mainLoop` fails to
resolve, and its comment explicitly does NOT claim main-loop semantics.

## Bug A — HUD-blanking faults: MITIGATED, NOT PROVEN

A confirmed gap was closed: **no scene-change invalidation existed anywhere.** `g_lastHoverObj`,
`g_latchedFocus`, `g_probeHoverPtr`, `g_lastRayObj`, `g_capFocus` are borrowed `Object*` with no
ownership and no liveness signal, set to `nullptr` only at DECLARATION and never cleared again for the
life of the process. A scene swap destroys the object graph, so every one dangles — and the strip
derefs `g_lastRayObj` every frame via `getContainingBuildingId`. Now invalidated after `loadScene` and
after both `wsUnloadSnapshot`+`wsLoad` button paths, which also disarms any in-flight edit.

**Deliberately NOT claimed as fixed.** Fault counts across the whole DebugView capture:

| PID | Faults | |
| --- | --- | --- |
| 4496 | 3,424 | original repro, old build |
| 67776 / 63276 / 61760 / 61428 | 1 each | isolated, consistent with teardown collateral |
| 35476, 66584 | **0** | runs on the invalidation build |

Zero faults on the current build across two sessions including cantina work — but the original bug
appeared **once in six runs**, so two clean runs is weak evidence. Recorded as mitigated with no
counter-evidence, not as verified. Rate-limited fault logging is in place so a recurrence is cheap to
detect rather than mysterious.

## Findings filed, NOT fixed here (both pre-existing, both out of scope)

`.planning/todos/pending/cell-aware-teleport.md` carries two DISTINCT teleport defects:

1. **Cell-aware teleport.** Teleport writes the world transform only and never reparents the player's
   cell (`object::setParentCell` advertised but unbound), so teleporting INSIDE a POB leaves the player
   on the world cell and portal culling renders interiors see-through. Confirmed from both directions:
   the maintainer walked out the cantina door and rendering repaired itself, because crossing a portal
   makes the engine reassign the cell. Open question that blocks a blind fix: whether the transform
   must become cell-relative (o2p) once reparented, given `getTransformO2P` exists for the read side.
2. **Stale player pointer after reload.** Intermittent "teleport does nothing" after Reload.
   Instrumentation FALSIFIED both naive explanations: 5/5 clicks registered, 5/5 writes landed,
   read-back matched target exactly, `getPlayer()` returned null zero times. Leading hypothesis:
   `getPlayer()` briefly returns the OLD freed player after a reload — the write "succeeds" into freed
   memory and the read-back matches because it reads that same freed memory, so even instrumentation
   reports success while nothing moves. Not confirmed; the failing case has not been captured, and the
   trace needed to confirm it is already in the build.
   Note `object::isActive` (advertised, unbound) is NOT the fix — calling it on freed memory is itself
   undefined behavior.
