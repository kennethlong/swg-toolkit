**Primary recommendation:** Treat this as three build tracks that share one channel-protocol

### Pattern 1: Disk-scan-as-truth building tree (D-05)
**What:** List `interiorlayout/toolkit/edit_*.ilf` and `object/building/toolkit/edit_*.iff` in the
resolved override dir; for each `edit_<id>.ilf`, diff its nodes against the STOCK `.ilf` (resolved by
reading the DERIVED template's *own* copy of the stock template's other params — the derived template
is byte-identical to stock except `interiorLayoutFileName`, so its DERV/base/appearance fields still
describe the original building type) to compute per-row status.
**When to use:** World panel initial load and refresh; must work fully offline (D-07b).
**Gap found:** no such scan utility exists in the codebase today (`grep` for `edit_` glob patterns
returns only the two write-side files). This is genuinely new code.
**Building display name:** no `.ws` parser exists in this repo (confirmed — `find` for
`*worldsnapshot*`/`*.ws.ts` returns nothing) and building general `.ws` editing is explicitly out of
scope (Phase 7 FMT-02). Recommend: derive the human label from the derived template's own DERV/base
chunk or appearance filename (parseable today via the generic `iffTree.ts`/`findForm` — already used
by `buildingTemplate.ts`) rather than attempting any `.ws` node lookup. The numeric id (`node
1082874`) is always available verbatim from the filename and should always be shown alongside the
derived label, exactly as the sketch's real-data examples do.

### Pattern 3: `.ilf` append/delete (extends the verified format module)
**What:** `IlfNode[]` is a plain array; `parseIlf`/`serializeIlf` preserve file order, and within-cell
row **identity is positional** (`resolveRowIndex`/`resolveNode` count occurrences of `cellName` in
file order — verified `ilf.ts:144-166,180-201`). Append = push a new node to the END of the array
(guarantees it gets the highest row index in its cell, since no later node shares that cell).
Delete = filter out one node; every LATER node in the SAME cell has its row index shift down by one —
this is safe because nothing in the codebase caches a row index across a reload; every consumer
(`resolveNode`, `resolveRowIndex`) re-derives (cell, rowIndex) by CONTENT match (template + transform)
every time, never by a stored index. Confirmed this is also true for a freshly-added row: its
identity after this is just (cellName, template, transform) like any other row — no special-casing
needed once it's in the file.
**Example (pattern to add, extending the existing `editNodeTransform` shape):**
```typescript
// Source: pattern derived from packages/renderer/src/services/ilf.ts:208-228 (editNodeTransform)
export function addNode(nodes: IlfNode[], node: IlfNode): IlfNode[] {
  // Append-only: new node's within-cell rowIndex becomes (count of existing nodes
  // in that cell) automatically, because no later node shares its cellName.
  return [...nodes.map((n) => ({ ...n, transform: [...n.transform] })), { ...node, transform: [...node.transform] }];
}

export function removeNode(nodes: IlfNode[], cellName: string, rowIndex: number): IlfNode[] {
  const out: IlfNode[] = [];
  let seen = -1;
  let removed = false;
  for (const n of nodes) {
    if (n.cellName === cellName) {
      seen++;
      if (seen === rowIndex && !removed) { removed = true; continue; }
    }
    out.push({ ...n, transform: [...n.transform] });
  }
  if (!removed) throw new Error(`ilf: no node at (cell="${cellName}", rowIndex=${rowIndex})`);
  return out;
}
```
**Provider ground truth confirming this needs NO engine change:** the provider's own 2026-07-19
CONSULT-ANSWERS memo (`.planning/handoff/2026-07-19-PROVIDER-ilf-decoration-editing-CONSULT-ANSWERS.md`,
"Verdict 2") describes exactly two persistence modes: "change only this one" (derive+rebind — what
model D already does, pure data, **the mode Phase 5.1 uses**) vs. "change ALL instances" (edit the
ORIGINAL `.ilf` via a NEW provider engine surface — NOT needed here, since `mirrorToStockIlf` already
achieves "all instances visible" via the loose-override shadow-copy trick, which is pure data too).
**Confidence:** HIGH — grounded in the verified `.ilf` format module + the provider's own written
design memo, not re-derived from `docs/`.

### Anti-Patterns to Avoid
- **Caching a `.ilf` row index across a session/reload.** The whole model relies on re-resolving
  (cellName, rowIndex) by content match every time (template + transform). A UI that pins "row 21" as
  a stable id across a delete-then-reload will silently point at the wrong node.
- **Assuming `wsRemoveNode` despawns any decoration.** It operates on `WorldSnapshotReaderWriter`
  node ids only (`ms_reader.find(networkIdInt)` — verified `WorldSnapshot.cpp:2353`). An id-less
  `.ilf`-sourced decoration (stock or previously persisted) is **not** in that tree and cannot be
  targeted by id at all.
- **Leaving the `wsAddObject`-minted preview node live after a successful `.ilf`-row persist.** Once
  the new row is durably written and rebound, the temporary WS node must be torn down

## Common Pitfalls

### Pitfall 1: Assuming the ROADMAP/CONTEXT "owed" list is still owed
**What goes wrong:** Planning re-implements the agent `-1`-refused fix or the editor-scene tooling,
duplicating work and risking a conflicting second fix.
**Why it happens:** CONTEXT.md and ROADMAP.md were written/locked before commit `36ab9b7` landed
later the same day.
**How to avoid:** Verify current `overlay.cpp`/`channel.h` state before scoping SC5 tasks — treat the
mapping fix and editor-scene loader as DONE, needing only a live-fire verification pass + UI wiring
(the World panel's Scene accordion should call the already-bound `gameLoadScene`/teleport, not
reinvent it).
**Warning signs:** A plan task titled "add REBIND_REFUSED result code" or "bind game::loadScene."

### Pitfall 2: `decorationResultLabel()` silently violates SC1 today
**What goes wrong:** `REBIND_REFUSED` (-5) falls through `decorationResultLabel()`'s switch to the
`default: unknown result (${code})` branch — a raw code leaking through the one function whose whole
job is to prevent that.
**Why it happens:** The label function (renderer) and the result enum (contract) were touched in
different sessions; `channel.h`/`live-inject.ts` got the new code, `decorationChannel.ts` didn't.
**How to avoid:** Add the case as a first-wave task; write the missing test
(`decorationChannel.test.ts` has no REBIND_REFUSED assertion either).
**Warning signs:** Grep `LIVE_DECORATION_RESULT.REBIND_REFUSED` in `decorationChannel.ts` — zero hits
today.

### Pitfall 3: Row-index renumbering on delete surprising a UI that shows "row N"
**What goes wrong:** the World panel shows "alcove1 · row 3"; if the panel caches that string/number
and a different row in the same cell is deleted, the label goes stale relative to the file's actual
current state.
**Why it happens:** row index is positional and file-order-dependent, not a stored identity.
**How to avoid:** Always derive the displayed row index fresh from the current disk-scan pass, never
from a prior render's snapshot; treat it as derived display data, not a key.
**Warning signs:** A React key prop or Zustand map keyed on `rowIndex` alone (should be keyed on
content: buildingId + cellName + template + a stable ordinal recomputed each scan).

### Pitfall 4: Treating `wsAddObject`'s returned id as the decoration's permanent identity
**What goes wrong:** The `.ws` node id `wsAddObject` mints is a **live-session preview handle**, not
the decoration's persisted identity — the persisted identity is its eventual `.ilf` row (cellName +
template + transform), which has no id at all. Code that threads the WS node id through to the World
panel's row identity will break the moment that WS node is torn down (`wsRemoveNode`, or simply on
next scene load where the row spawns as a plain `.ilf` decoration again with no id).
**Why it happens:** conflating the two different addressing schemes model D deliberately keeps
separate (WS nodes = networked/authored; `.ilf` decorations = client-only, pointer-keyed, no id).
**How to avoid:** Use the WS node id ONLY transiently, for the live preview + its own despawn call;
never store it as the row's identity in `worldEditorStore`.

### Pitfall 5: `mirrorToStockIlf` reconcile-on-flip (D-09) touching every edited building, not just the one being edited
**What goes wrong:** A naive toggle implementation only affects the NEXT persist, leaving existing
edited buildings' stock-path mirrors stale (exactly the failure class that caused the 7/19→7/30
debugging night per `reference-model-d-building-id-resolution`).
**Why it happens:** the toggle is easy to wire as "read at persist time" only (which IS what D-08
wants for future persists) but D-09 additionally requires an immediate reconcile pass over ALL
already-edited buildings the moment the toggle flips.
**How to avoid:** Flipping the toggle must re-run assembly (or a lighter mirror-only add/remove step)
for every building the disk scan (D-05) already finds edited — reuse the SAME scan the World panel
tree uses as the reconcile's work list, don't build a second one.
**Warning signs:** A plan task that only threads the flag into `decorationPersistOrchestrator.ts`
without a separate "reconcile existing edits" task.

### Pitfall 6: Forgetting the agent rebuild step after any `overlay.cpp`/`channel.h` change
**What goes wrong:** The dev injector loads a stale `agent/build-agent/Release/swg_toolkit_agent.dll`
copy; changes silently don't take effect in-game.
**Why it happens:** the agent is a separate x86 CMake build from the renderer/host addon, easy to
forget mid-iteration.
**How to avoid:** `cmake --build packages/live-inject/agent/build-agent --config Release` (needs
`node` on PATH: `$env:PATH="C:\Program Files\nodejs;$env:PATH"`) after every agent-side edit; also
remember the per-inject uniquely-named DLL copy mechanism (`prepareAgentDllForInject`) means a stale
resident module can mask a rebuild if re-attaching to an already-injected process — prefer a fresh
client launch when smoke-testing agent changes.

### Pitfall 7: A new `.ilf` row for a freshly placed decoration has no cell name to write
**What goes wrong:** `IlfNode.cellName` is a required, non-optional string field. A brand-new
placement has no prior row to derive it from (unlike edit, which resolves cellName by matching an
EXISTING row's template+transform).
**Why it happens:** `CellProperty::getCellName()` is a client-side C++ INLINE method (verified
`sharedObject/src/shared/portal/CellProperty.h:249`) — no exported symbol exists to call it from the
agent's advertised-endpoint table, the exact same class of problem the v25
`getContainingBuildingId` shim was built to solve for building-id resolution.
**How to avoid:** See "Add/Remove ground truth: the one real provider gap" below — file a
change-request for a wrapping shim (`object::getContainingCellName`) using the v25 precedent; default
to the pre-wire/bind-by-name posture; degrade gracefully if the shim doesn't land before the phase's
Add slice must ship (see options below).
**Warning signs:** A plan that treats "resolve the cell name for a new placement" as a solved problem
— it is not, as of this research session.

1. **RESOLVED (planning, 2026-07-31 revision) — Cell-name resolution for a freshly placed decoration (the one real provider gap)**

     already contain >= 1 existing decoration; refuse an empty-cell placement with an honest

     scope the Add slice's FIRST version to degrade gracefully if it hasn't landed — e.g. require the

     needed) and surface "can't place in an empty cell yet" as an honest, words-not-codes limitation
     for a truly empty cell. This unblocks the demo-able 021-A flow (placing a second chair next to an
     existing one) without waiting on the provider.
