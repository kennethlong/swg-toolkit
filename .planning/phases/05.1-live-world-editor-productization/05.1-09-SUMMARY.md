## Decisions Made

- **Ack timing: on execution, not on enqueue.** Deferred actions (RELOAD_CURRENT_SCENE,
  LOAD_EDITOR_SCENE) publish `channelWriteHostCommandResult` only after the engine call actually runs
  inside the game-thread drain — truthful (the scene has genuinely swapped by the time code 1 is
  published) and stays comfortably inside Plan 08's 11s HOST_CMD timeout budget. Every path acks exactly
  once: real execution (1), unresolved endpoint (0), and queue-overflow drop (0) all reach
  `channelWriteHostCommandResult` exactly once — verified to hold on both the success path (Step 4's
  first despawn) and the refusal path (Step 4's repeat despawn), matching Plan 08's "agent always-acks"
  clause.
- **Deferred-queue extension.** Added a `Reload` kind to the 05.1-16 deferred command queue
  (`wsUnloadSnapshot`+`wsLoad`, single-pass — a different engine call pair than `gameLoadScene`/
  `cleanupScene`, with no evidence it needs the two-frame gap 05.1-16 established for scene loads) and
  epoch carriage on every `DeferredCmd` so a HOST_CMD-originated enqueue can be acked later, from the
  drain, not from the enqueue site.
- **Epoch-0 reset.** On reading a zeroed HOST_CMD epoch slot (which every fresh `openChannel` produces —
  `channel_binding.cpp:153-154`'s unconditional zero-fill runs on every open, so no region epoch survives
  a toolkit restart), the agent-local last-applied-epoch tracker is reset to 0 before no-opping. This
  guarantees a restarted toolkit's epochs 1..N can never silently collide with a stale tracker from a
  previous toolkit session. Verified in practice: the throwaway Node script zero-filled the channel on
  every open, and the agent still correctly consumed epochs 9283 and 9296 across runs rather than
  swallowing them as duplicates of a stale tracker value.
- **DESPAWN_NODE routing resolved live.** Plan 16 left this an explicit unknown ("verify live, do not
  assume"). Driven via a throwaway Node script (no UI exists yet): first despawn of node `9995372`
  returned ack code 1 (applied) and the object was removed in-game; a repeat despawn of the SAME id
  returned ack code 0 (refused); the client (`SwgClient_r`) remained running throughout. Conclusion:
  `wsRemoveNode` is safe to call directly from the render callback and does not need the deferred queue.
  The engine's own `wsIsBuildoutNode` guard refuses a stale/already-removed id cleanly rather than
  crashing, confirming the engine — not caller discipline — is the enforcement boundary (T-05.1-09a).

## Issues Encountered

**Reload world-state finding (NOT a plan 09 defect — filed as a todo).** Step 2 of the checkpoint
(RELOAD_CURRENT_SCENE) acked code 1 and the scene call itself succeeded exactly as designed, but the
resulting world was measurably degraded: the cantina building was gone, collision was gone (the
maintainer walked through walls up to NPCs known to be standing behind them), and snapshot creatures
(banthas, dewbacks) were missing. Everything returned at once after moving around. Server-streamed NPCs
were unaffected. Root cause (filed at `.planning/todos/pending/reload-scene-is-lossy.md`, commit
`9bb7ec1`): our reload is only `wsUnloadSnapshot()` + `wsLoad()`; Utinni's snapshot layer additionally
binds spatial-subdivision handles, `removeFromWorld`, `unload`, and `clearPreloadList` that we never
call, so snapshot objects are left un-registered in the render/collision world until a later spatial
pass picks them all up. A buildout-vs-authored hypothesis was considered and ruled out — buildings and
banthas returned in the same instant, which two different restore mechanisms would not do.

**Consequence for the record:** an ack of code=1 on RELOAD_CURRENT_SCENE is truthful about the CALL
succeeding but is NOT evidence the world is intact. This invalidates a verification-step assumption
Plans 12 and 15 depend on — both use reload to confirm persistence, and a correctly-persisted object can
read as missing immediately after a truthful ack=1 reload. Both plans need to account for this before
treating a post-reload absence as a persistence failure.

**Mis-celled-player-after-scene-load, extended (not new — filed under the existing teleport todo).** Step
1 (LOAD_EDITOR_SCENE) passed: DebugView showed the two-frame sequence running for the REMOTE command
exactly as 05.1-16 designed it (`frame 1: cleanupScene (scene is live)` -> `frame 2: loadScene (game
thread, outside Present)` ~200ms later -> `scene changed (loadScene) — cached object pointers
invalidated`), no crash, and the editor scene loaded correctly in offline single-player mode (no server
objects/NPCs — by design, the exact context Plan 15 step 5 requires). One known, separate defect was
observed: the player is left mis-celled after a scene load (interior not visible until crossing a
portal). This is the SAME cell-membership defect already filed for teleport
(`.planning/todos/pending/cell-aware-teleport.md`) — this checkpoint shows it is triggered by scene load
too, not teleport-specific. No new todo filed; the existing one now covers both triggers.
