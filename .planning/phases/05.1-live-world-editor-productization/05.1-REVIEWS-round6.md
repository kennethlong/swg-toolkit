## Work list (round 6): X1–X13

### HIGH

**X1 — Plan 10: `resolveOverridePair()` prescribes an invalid React hook call (3 reviewers, independent).**
`05.1-10-PLAN.md:309-311` (behavior) and `:460-461` (action) both say the helper "FIRST reads `studioDir`
via `useWorkspaceStore((s) => s.studioDir)`". The helper is a plain component-local function invoked from
event handlers (mirror-toggle `onChange`, Plan 13's Remove click, Plan 13's `handleUndo`) — a hook call
there throws "Invalid hook call" at runtime on the first click of every write action in the panel. The
hoist-and-close-over escape is foreclosed by the plan's own R2 clause (`:482-484` — no call site may cache
`studioDir` across renders/calls). The repo's own precedent is `getState()` in handlers
(`DeployDialog.tsx:139,185,327`; `useChannelReader.ts:272` — already cited at `05.1-10-PLAN.md:121-122`),
and the SAME replan's V5 fix in Plan 13 uses the correct form (`useLiveStore.getState().status`). HIGH
because the helper is the single chokepoint D-03 (Undo), D-05 (`refreshTree`), and D-09 (reconcile) all
route through.
*Fix:* replace both occurrences with `useWorkspaceStore.getState().studioDir` (fresh at call time —
satisfies R2 by construction; matches V5's pattern).

**X2 — Plans 06+10: unqualified-atomicity contract lines never amended for `diskState: 'uncertain'`;
Plan 10 holds two mutually exclusive `must_haves` (Codex + Opus, independent).**
V7 added the honest `'uncertain'` double-fault state (`05.1-06-PLAN.md:351-355`) but left the superseded
W1-era absolutes in place: `05.1-06-PLAN.md:17`, `:27` (must_have: "EVERY building's mirror state on disk
is provably unchanged"), `:365-366`, `:371-378` ("atomic on the flag AND on disk … type-visible"),
`:379-382` ("NEVER results in … disk moving for some buildings while the flag stays put"). In Plan 10 the
contradiction is between adjacent gates an executor must satisfy simultaneously: `:26` ("the history entry
says NO building's mirror was changed this call … never a mix") vs `:30` ("a failure whose diskState is
'uncertain' produces a HEDGED history message … never the unconditional wording"). Plan 10's behavior
(`:367-376`) and action (`:495-498`) already carry the correct conditional split — only the must_have
contract lines were left stale.
*Fix:* qualify all four Plan 06 clauses with "…except the disclosed `T-05.1-06d` double-fault, which
returns `diskState: 'uncertain'`"; rewrite `05.1-10-PLAN.md:26` to claim the all-or-nothing wording only
when every failure carries `diskState: 'unchanged'`, deferring the hedged case to `:30`.

**X3 — Plans 13+14: the blanket suppress branch can permanently swallow an unrelated genuinely-new row
(Sonnet).** `05.1-14-PLAN.md:310-312`'s suppress branch re-baselines the WHOLE tree snapshot and marks
nothing — but `refreshTree()` is an unscoped full-override-dir rescan, and Plan 08's poll-tick-driven
RESULT wiring (`05.1-08-PLAN.md:34/38/51`) can land a different building's brand-new row on disk in the
same window as an Undo click. If that row is first observed during the suppressed pass, it is folded into
`prevTreeRef` undiffed; no later pass can ever recover the "(NEW)" marking (one-way silent loss of a signal
sketch 021-A Frame 3 / D-03 promise). No debounce/mutex exists around `refreshTree()` (grep-verified), and
no test exercises "second building changes on disk during the Undo window."
*Fix:* scope the suppression to content identity — pass the restored row's identity key
(`buildingId+cellName+objectTemplateName`) with the flag and have the suppress branch run the normal
count-map diff with that one entry pre-consumed, instead of skipping the diff entirely. At minimum add the
regression test (unrelated new row seeded into the same snapshot as the restore must still be marked).

**X4 — Plan 13: a failed Undo (null `resolveOverridePair()`) is invisible to the toast — D-03's only guard
can silently no-op (Sonnet).** `05.1-13-PLAN.md:392-394` asserts "the toast remains visible and the user
can retry Undo", but nothing makes that true: a failed attempt does not change `pending`, so the toast's
diff effect (structural copy of `DeleteUndoToast.tsx:68-92`) observes nothing, and the original 8-second
dismiss timer keeps counting; the toast then hides with zero feedback and the entry is stranded in
`removeUndoStore.pending` with no UI surface (ledger item (g) covers only tab-nav remount). This regresses
the precedent V1 cites: `DeleteUndoToast.tsx:102-110` catches its own failure, shows the error, and
re-arms its timer. Neither Plan 13's acceptance criteria nor Plan 15's checkpoint tests this path.
*Fix:* add a transient observable signal (e.g. `lastUndoError: { id, message } | null` on
`removeUndoStore`, cleared on next attempt) that the toast watches to show the words-only reason and
re-arm its timer — preserving the toast's zero write-path knowledge; or explicitly ledger the gap as item
(h) with a test proving the entry survives. As written, neither exists.
