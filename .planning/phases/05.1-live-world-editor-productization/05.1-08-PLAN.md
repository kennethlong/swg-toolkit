## HOST_CMD ACK PROTOCOL — CANONICAL SPEC (R9 review: BB1, BB4, BB5, BB6, BB7, BB10, BB12; R10 review: CC1, CC2, CC3, CC5, CC7, CC13, CC14, CC17 — respecified as a TOTAL state × event table, not a trigger list; R11 review: EE1, EE2, EE6 — the CC17 pending-mirror clear and the row-7 studioDir guard enumerated on EVERY exit transition incl. the detach row, and the timeout derivation restated as throttle symmetry)

This section is the ONE authoritative statement of the placement-ack protocol. Restatement discipline (R10
review, CC8): Plans 04/07/09/12/14/15 may restate ONLY rules present in this section, may quote user-facing
strings ONLY character-identically to the Canonical strings list below, and any conflict between another
plan's wording and this section resolves in this section's favor — implementation-owner plans (14 for the
renderer consumer, 09/12 for the agent side) legitimately restate the transitions they implement under that
discipline. Implementation ownership: the send/observe primitives are THIS plan's Tasks 1/2; the
renderer-side consumer state machine is Plan 14 Task 3; the agent-side always-ack and epoch-0 reset rules
are Plans 09/12.

**States (renderer-side; one placement request pending at a time):**

- `idle` — no request outstanding: `pendingPlacementRef.current === null`, no armed timer.
- `pending` — exactly one outstanding request. The slot carries `{ epoch, studioDir, buildingId,
  buildingLabel, templatePath, cellName }` — `studioDir` is captured at SEND time from
  `useWorkspaceStore.getState().studioDir` (R10 review, CC2: the issuing project travels WITH the request,
  so every resolution path enforces the switch-abort LOCALLY, independent of React effect declaration
  order) — plus an armed `placementTimeoutRef` timer.

**Timeout constant (R10 review, CC3 — latency-aware; derivation restated per R11 review, EE6):**
`PLACEMENT_ACK_TIMEOUT_MS = 11_000`, derived as a 10_000 ms ack-PUBLISH budget (the agent's frame loop
answers in ~16 ms when responsive; the budget exists for ordinary in-game latency) PLUS a 1_000 ms read
margin — one MODERATE-throttle poll interval (`useChannelReader.ts:114-118`: Chromium throttles the ~33 ms
poll to ~1/s while the game holds the foreground), since the deadline bounds when the renderer READS the
ack, not when the agent publishes it. **The +1 s is NOT a true worst-case read-lag bound (EE6):** with the
toolkit occluded by the fullscreen game for more than ~5 minutes (the normal workflow), Chromium/Electron
background throttling escalates to INTENSIVE throttling (timer wake-ups ~1/minute), so read lag can reach
~60 s — far past any fixed margin. What keeps the design honest there is THROTTLE SYMMETRY, not the margin:
the timeout `setTimeout` is throttled by the SAME clock as the poll loop, so it fires proportionally late
too — it can only fire LATE, never early — and the callback's row-9 re-check no-ops it whenever the ack
already resolved on an earlier wake; throttling widens the grace, never narrows it. The margin covers the
moderate-throttle case; symmetry covers the intensive one. The honest residual (the agent is SILENT during
load/login/zoning, which routinely exceeds ANY fixed deadline — and, per the same symmetry analysis, a
renderer read-starved under intensive throttling can cross the deadline even with the agent responsive) is
handled by the hedged Canonical strings below and disclosed as Plan 15's gap ledger item (n), which names
BOTH causes.

**State × event table.** Events: `place-attempt` (user clicks "Place in game ▸"), `ack(epoch, code)` (a
fresh `lastHostCommandResult` write from the poll loop), `timeout-fire`, `detach` (`liveStore.status`
leaves `'attached'`), `project-switch` (`studioDir` changes), `unmount` (WorldPanel unmounts — R10 review,
CC1: the seventh transition the former six-trigger list never partitioned). Every (state, event) cell is
specified; there are no other cells.
