## How the design changed, and why it matters to the next reader

This plan was rewritten **four times**, each time because a live test falsified something. The final
shape is much smaller than any intermediate one. Do not reconstruct the discarded versions:

| Version | Shape | Killed by |
| --- | --- | --- |
| draft | stale-player N-tick gate + inert cell field | crew: gated the wrong trigger; the UAF cites a server path the editor client never runs |
| v27 | write o2w, then reparent | live: right coords, wrong cell — but this was CLOSE |
| v28 | reparent, suppress, write o2p, objectWarped | provider v30 |
| v30 | findCell → setParentCell → warpClient | live: landed at `(15,193,5)`; `warpClient` sends the NO-PARENT message, whose handler **un-parents on receipt** |
| **v31** | **`warpPlayer` alone** | — verified |

**The v28 shape was nearly right.** The provider's own verdict: *"the sequence you had before we
intervened was correct. The only thing missing was telling the server."* It survives as the pre-v30
fallback for exes without the row, with a UI note stating plainly that it will revert on a live server.

## Locked facts — do not re-derive

- **A raw `setTransform_o2w` is an UNSEQUENCED local write.** The server never hears it and the next
  authoritative update legitimately overwrites it (~1s revert). Invisible offline, which is why every
  editor-scene test passed.
- **`CM_netUpdateTransform` cannot place an object in a cell.** Its handler opens by un-parenting
  (`ClientController.cpp:433`). No coordinate space fixes this — the primitive is wrong for interiors.
  `sendTransform` / `CM_netUpdateTransformWithParent` is the correct one; `warpPlayer` uses it.
- **Do NOT call `setParentCell` around `warpPlayer`.** An external reparent fights the shim, which
  picks its message variant from parentage at call time (provider v31 §3).
- **`getAttachedTo` is NOT a mount probe.** Cell parentage and mount attachment share
  `m_attachedToObject`, so any player inside a POB reports non-null. Use `isChildObject` (v29) — the
  `m_childObject` flag, which cells set FALSE. Falsified live after the provider's v28 guidance said
  otherwise; they corrected it in v29.
- **`isChildObject` guard is still required** even though the teleport is one call — `warpPlayer` calls
  `setParentCell` internally, so the Release pose-corruption hazard on a mounted player is unchanged.

## Deviations from the plan as written

- **The stale-player instrumentation was descoped to a scene-epoch counter + structured write record.**
  The defect has never reproduced under instrumentation across four attempts, and the crew showed the
  cited mechanism is a server-driven path the editor client does not execute. What the counter now
  hunts is a transient NULL player in our own `cleanupScene`→`loadScene` window, which is the reachable
  hazard.
- **`PortalTransitionGuard` survives but is now only on the fallback path.** v31 does the suppression
  internally. The guard is retained because the RAII discipline is still correct for the legacy path
  and the endpoint is still global unscoped state.
- **`findCellAtWorldPosition` / `setParentCell` are bound but not in the teleport path** — placement
  routing (Plan 12) needs them.

## Known limitations, disclosed

- **After `game::loadScene`, `findCellAtWorldPosition` returns the world cell** until a manual reload.
  Provider-side, accepted as theirs, queued behind interior refresh. Workaround: reload after loading
  the editor scene.
- **Mounted-indoors** is now guarded by `isChildObject`; the earlier world-cell narrowing is gone.
