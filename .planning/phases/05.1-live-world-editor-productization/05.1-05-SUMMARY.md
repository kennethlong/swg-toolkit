### Auto-fixed Issues (checkpoint-driven, Rule 1 — bug)

**1. [Rule 1 - Bug] Esc key double-bound into SWG's own settings menu**
- **Found during:** Task 3 checkpoint, step 8 (Esc-cancel verification)
- **Issue:** The strip's Esc KEY binding also toggled SWG's in-game settings menu. Root cause is structural: SWG polls game input via DirectInput, not the Win32 message queue, so `hkWndProc` cannot CONSUME a keystroke — gating on `!io.WantCaptureKeyboard` makes ImGui OBSERVE without CONSUMING, so the keystroke always also reaches the game. Sketch 020-A never specified an Esc KEY in the first place (only an on-strip Esc BUTTON, `im-btn ghost`) — F and G/R are the only sketch-specified KEYS.
- **Fix:** Removed the Esc KEY binding entirely; the on-strip Esc BUTTON (unaffected by this defect, since it never round-trips through DirectInput) remains the only way to cancel an armed edit via input other than pressing F/G/R again.
- **Files modified:** packages/live-inject/agent/overlay.cpp
- **Committed in:** `2ec00e3`
- **Known limitation carried forward:** no overlay key can be claimed EXCLUSIVELY on this client without engine-side DirectInput arbitration — F/G/R also double-fire into the underlying game input, same as the mouse double-input limitation `hkWndProc`'s own comment already documents. Not fixable within this plan's scope; documented here for the next agent-input-related plan.

**2. [Rule 1 - Bug] Stale pre-shim building-id fallback made the refusal path unreachable**
- **Found during:** Task 3 checkpoint, step 7 (refusal-path verification) — everything was armable, including buildings hovered from OUTSIDE, so 020-A's `failed` state had never actually been exercised end-to-end.
- **Issue:** `armDecorationEdit` contained `if (bldgId == 0) bldgId = (g_lastRayId != 0) ? g_lastRayId : g_pickedId;`, a workaround whose own comment said "Until the provider ships it (REQUEST 2026-07-30)." The provider DID ship `getContainingBuildingId` (v25, `engine_hookpoints.inc:446`, proven live 2026-07-30), after which `bldgId==0` became AUTHORITATIVE ("world-cell objects report 0, no PortalProperty") — but the fallback stayed, silently overriding a definitive NO with the picked object's own id, arming a building as its own containing building.
- **Fix:** The fallback now applies ONLY when the slot is genuinely unresolved (not when it resolves to a definitive 0).
- **Files modified:** packages/live-inject/agent/overlay.cpp
- **Committed in:** `cb6f369`

## Issues Encountered

### Step 8 PARTIAL — Teleport works; "Editor scene" crashed (pre-existing, NOT this plan, ROUTED to 05.1-16)

**Teleport: VERIFIED WORKING** (maintainer, 2026-08-02). This matters as more than a passed step — it
is the **control that scoped the fix**. Teleport is invoked from the SAME overlay button surface, in
the SAME `renderFrame()`/Present context, and does not crash. So "called from inside Present" is not
by itself sufficient to fault; the unsafe class is narrower — calls that DESTROY AND RECREATE the
player/scene (`gameLoadScene`) versus calls that merely move the existing player (teleport). That
distinction is exactly what the FATAL text reports ("...on a NEW player without releasing OLD one"),
and it halved 05.1-16's scope: queue scene-LIFECYCLE calls only, leave teleport on its proven direct
path rather than adding a frame of latency and diff surface to a working call. 05.1-16 carries the
resulting per-action routing table for Plan 09; `DESPAWN_NODE` is recorded there as UNKNOWN rather
than assumed either way.

**"Editor scene" crashed the client.** Client-side FATAL captured via DebugView:
`InputScheme.cpp(480) FATAL: InputScheme::fetchGroundInputMap called on a new player without releasing old one`, stack: `GroundScene.cpp(3868/823/966)` -> `Game.cpp(222/1857/1846)` -> `engine_advertise.cpp(331)` (the advertised `game::loadScene` shim) -> agent -> `Graphics.cpp(1171)` (INSIDE the present frame).

**Root cause:** `gameLoadScene` is called at `overlay.cpp:960` inside `renderFrame()` (`:713`), which itself runs inside `hkSwapChainPresent` (`:1028`) — i.e. a scene swap is issued RE-ENTRANTLY from the render callback.

**Attribution — confirmed NOT this plan's defect:** this plan's diff touches `gameLoadScene` zero times. The call arrived in commit `36ab9b7` (an earlier, already-shipped commit), and the 2026-07-30 handoff already listed "editor-scene verify" as an OWED follow-up — this checkpoint was the first time the button was ever actually pressed. Reproduces identically both inside a POB and outside any building, so POB/cell state is not causal — the re-entrancy itself is the defect.

**Also captured — Bug A, HUD disappearance (pre-existing, same root-cause family, also routed):** one run logged 3,424 CONSECUTIVE `overlay: SEH fault in renderFrame — frame skipped` events, one per frame, starting on entry to a cell-heavy POB; five other runs logged zero. Suspected cause: the strip's per-frame Hover branch calls `getContainingBuildingId(g_lastRayObj)` on a one-frame-stale BORROWED `Object*`, and `renderDecorationStrip()` runs BEFORE the hover-tracking block that maintains that pointer. Blast radius is total because `hkSwapChainPresent` wraps ALL of `renderFrame()` in one `__try/__except`, so one bad call anywhere in the strip silently blanks the ENTIRE overlay, not just the strip.

**Disposition:** NOT fixed in this plan. Routed to new plan **05.1-16** ("Game-thread command queue + overlay fault containment"), inserted into wave 2, scoped to run AFTER 05.1-08 and BEFORE 05.1-09 (Plan 09 dispatches scene-swap HOST_CMD actions from the frame loop and would otherwise reproduce Bug B — the re-entrant `gameLoadScene` crash — on its own checkpoint). 05.1-16 closes both the deferred game-thread command queue (for scene-swap safety) and per-frame strip fault containment (for Bug A) as one plan, per the maintainer's explicit choice of "scoped plan BEFORE 09" over the alternative of folding the fix into 09 itself.
