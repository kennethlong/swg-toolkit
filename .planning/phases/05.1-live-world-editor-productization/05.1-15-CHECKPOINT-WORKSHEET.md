### 🔧 Reusable capability built this session — `.ws` node parsing

No `.ws` parser exists in the repo (exterior node editing is still a pending todo), which blocked
step 11's setup until one was written ad hoc. The record layout, verified against a known node:

```
FORM <len> NODE            <- outer form; NODE tag at h
  FORM <len> "0000"        <- version form at h+4
    DATA <len=0x34>        <- 52-byte payload, tag at h+16, payload at h+24
      +0  int32  nodeId
      +4  int32  parentNodeId
      +8  int32  objectTemplateNameIndex   -> index into the OTNL name table
      +12 int32  cellIndex
      +32 float  x     +36 float y     +40 float z
      +44 float  radius (512.0 = cs_wsDefaultAddRadius)
      +48 int32  (NOT a portal-layout CRC — see below)
```
`OTNL` chunk: `int32` name count at +8, then that many NUL-terminated ASCII names.
Tatooine: 15,808 node records, 1,178 interned names.

**Falsified while probing:** `payload+48` is NOT an interior/portal indicator. Banks and shuttleports
(certainly enterable) read 0 while filler buildings (certainly not) read non-zero — the exact inverse.
Do not use it to infer enterability.

**The authoritative enterability test is the TRE**, via `<scratchpad>/list-interiors.cjs`: a building
is decoratable iff an `interiorlayout/<portal-layout>.ilf` exists. Only **298** such layouts exist
against ~1,178 building templates. Confirmed absent for banks, shuttleports, parking garages and
filler buildings; present for cloning facilities, starports, guild halls and hospitals. Note `.ilf`
names follow the PORTAL LAYOUT, not the building template — `shared_cantina_tatooine.iff` uses
`shared_cantina_mos_eisley_tatooine.ilf` — so the names cannot be assumed to correspond.

Both scripts are worth promoting to `packages/harness/scripts/` — Phase 5.2's asset-discovery and

### ✅ "No project selected" now fails clearly — and NOT where it first appeared it should

**A wrong fix was attempted and caught by the test suite. Recorded because the correction is the
useful part.**

The obvious guard — reject the capture when `studioDir === null` — is **wrong**, and an existing
test pins exactly why: *'resolves to true when studioDir is null (no bound project) — no regression'*.
The override dir is resolved from the **client exe** (`resolveRunningClientOverrideDir`), not from
the project, so a persist whose every input resolves loosely genuinely works with no project bound.
An upfront `studioDir` gate breaks that supported case; it broke 4 pre-existing tests immediately.

The real precondition is a **populated TRE mount** (`useTreStore.vfsEntries`), and it only bites when
`makeReadVfs`'s override-dir-first lookup misses. So the distinction lives there:

```
no TRE archives are mounted — open a project so <path> can be read from the client's data
```

instead of `readVfs: no VFS entry and no loose file for <path>`, which reads as "that asset is
missing" when the real state is "nothing is mounted to look in".

**Answering the maintainer's design question directly: a project should NOT be required to launch.**
Attaching without one is legitimate — read-only live inspection of transform/template/liveness is
useful and needs no project. Only the EDIT path needs mounted data, and it now says so in words.

The risk: if `edit_<id>.ilf` were derived from pristine stock rather than from the current mirror,

mirror path.

**Measured against pristine stock extracted from the TREs**
