# Plan 05.1-18 — Cell-aware teleport

<objective>
Make a teleport put the player in the right CELL, not just at the right coordinates. Today the write
lands perfectly and the player still renders the interior wrong, because nothing reparents them.

The provider shipped the missing capability as **v27** the same day the defect was characterised, so
this plan consumes it. It also adds cheap instrumentation for a second, unproven defect rather than
building machinery against something never observed.
</objective>

<evidence>
## LOCKED — measured live 2026-08-02, DebugView capture. Do NOT re-derive or contradict.

1. **Our write is CORRECT. This is not a transform bug.** Nine teleport clicks across two sessions, every
   one:
   ```
   overlay: teleport click    — player=2AF9B9F0 target=(3428.0, 8.0, -4788.0)
   overlay: teleport read-back — now=(3428.0, 8.0, -4788.0) wanted=(3428.0, 8.0, -4788.0)
   ```
   `now == wanted`, exactly, every time. Do not "fix" the write path.
2. **The player physically moves to the target and stays in the WRONG CELL.** Portal telemetry across a
   teleport from inside the cantina: position went `3437.24 → 3430.48 → 3428.32` (target X `3428.0`)
   while the probe continued to report **`cell=cantina`**. The player is at the doorway coordinates
   with the interior cell's portal set still active around them — which is what the maintainer
   described as *"moved forward to the wall in front of me, not to the exterior location."*
3. **28 `DOORHIT-WAKE` portal sweeps fire immediately after EACH teleport**, alternating
   `private_room ↔ cantina`, symmetric across both clicks. That is the `positionChanged` line-sweep
   (`CellProperty.cpp:150-176`) evaluating a teleport-length segment against the current cell's portal
   list. Normal walking produces occasional single `DOOR` lines; 28 in a burst is teleport-induced.
4. **After a `loadScene`, portal traversal stops entirely**: `[PortalCullProbe]` emitted **1095 lines
   before** the editor-scene load and **exactly 0 after**, across 22 seconds and 7 teleports until
   shutdown. The probe is `REPORT_LOG(true, …)` inside `RenderWorld`'s traversal — unconditional — so
   silence means the traversal is not executing. This is consistent with world-cell parentage after a
   scene load, and it is why neither interior nor exterior of the cantina drew.
5. **v27 SHIPPED the fix** (provider commit `b9363b5b0`): `object::setParentCell`
   (`engine_hookpoints.inc:447`) and `cellProperty::getWorldCellProperty` (`:448`).
   `object::getParentCell` was already advertised (`:178`). **We bind none of the three.**
6. **Provider's answers to the two questions we refused to guess at**, verified in their source:
   - **Transform: write `o2w`, do NOT convert.** `attachToObject_w` (`Object.cpp:1956`) derives o2p from
     the current world frame; `setTransform_o2w` (`:1450`) is itself cell-aware. Independently derived
     twice by the review crew — **this one is settled, three ways.**
   - **Ordering: write the transform FIRST, then reparent.** Their rationale — that reparent-first
     makes `cellChanged` observe a stale position — is **NOT the real reason** (see axiom 6b), but the
     conclusion is right.

6b. **ORDERING IS SETTLED, and the deciding fact is one everybody initially missed** (crew review,
    independent derivation): **`setParentCell` does NOT run the portal line-sweep at all.** It fires
    only `cellChanged(false)` (`Object.cpp:1408`), and `CellPropertyNamespace::Notification` overrides
    only `getPriority`/`positionChanged`/`positionAndRotationChanged` (`CellProperty.cpp:42-66`) — not
    `cellChanged`. **The sweep is a side effect of the TRANSFORM WRITE, and only the transform write.**

    So the real question is whether the sweep runs before or after our authoritative cell assignment:

    | Order | Sweep runs | If the sweep picks a cell |
    | --- | --- | --- |
    | **A — write, then reparent** | first, against the OLD cell | **unconditionally overwritten** by our trailing `setParentCell(C)`. Final cell is C in every case. Self-correcting. |
    | B — reparent, then write | **last** | **final and uncorrected** — a permanent, silent mis-parent, which is exactly the value `getContainingBuildingId` placement routing reads |

    Order A trades a higher-probability *transient* event for Order B's lower-probability *permanent*
    one. **On worst case Order A strictly dominates.**

    Two corollaries that retire earlier arguments — do not resurrect them:
    - The provider's stale-`cellChanged` rationale is **cosmetic**. `Object::cellChanged` is
      non-virtual (`Object.h:366`), so its observer set is closed and enumerable; all five re-derive
      from current state and **none caches a position**. The one that reads position at all
      (`Footprint::cellChanged`) is a no-op on the client for an interior destination.
    - The "six engine call sites reparent first" argument is **void**. Those sites bracket the
      **transform write only** — never `setParentCell` — which is itself direct confirmation that the
      sweep belongs to the write. Their cell-first choice is *conditional on suppression we do not
      have*, so it is not evidence for unsuppressed Order B.
7. **`object::setParentCell` is GAME-THREAD-ONLY** (`engine_advertise.cpp:1077`). The agent's D-03 poll
   thread (`agent_main.cpp:145`, a separate remote thread) must never reach it.
8. **A null cell FATALs the client.** `Object::setParentCell` `NOT_NULL`s its argument
   (`Object.cpp:1389`). The provider's shim returns `0` first, but the caller must still pass
   `getWorldCellProperty()` to mean "outside" — **never null**.

## LOCKED — the stale-player defect has NEVER been reproduced

9. Reported twice at the 05.1-16 checkpoint. **Two deliberate, instrumented reproduction attempts have
   now failed.** In the second, the player pointer *did* change across a genuine scene recreate
   (`2B018640 → 36C4EDD0`) — the precondition the hypothesised mechanism requires — and all seven
   subsequent writes landed exactly. The first click came 4.68 s after `loadScene`, past any plausible
   use-after-free window.
10. **CORRECTED — the defect is a transient NULL, not a use-after-free** (crew review, verified
    independently against source this session). An earlier draft cited `GameNetwork::startScene()`
    (`GameNetwork.cpp:480-505`), which does `delete gs` before the replacement is built. **That is the
    server-driven multiplayer zone path and the editor client does not execute it.** What our
    "Load editor scene" actually runs is `game::loadScene` → `Game::setScene(..., immediately=true)`,
    which skips the cutscene defer entirely, and:
    - `Game::cleanupScene()` (`Game.cpp:989-995`) is `ms_scene->quit(); _setScene(0);` — **quit, not
      delete**.
    - `Game::_setScene(Scene*)` (`Game.cpp:1865+`) assigns `ms_scene = newScene` and **never deletes the
      old scene** — it leaks it.

    So on our path `Game::getPlayer()` (`Game.cpp:2214-2217`, a `dynamic_cast` on `ms_scene`) goes
    **valid → null → valid-new**. It never dereferences freed memory. The window is created by
    **our own** two-frame `cleanupScene` → `loadScene` sequence (05.1-16), and a click landing in it
    gets a null player — already logged today at `overlay.cpp:1409`, and reported ZERO times in both
    repro attempts, consistent with narrowly missing a one-frame window rather than with the theory
    being wrong.

    **Consequence:** the fix, if confirmed, is trivial — refuse or retry the click during the gap
    instead of silently no-opping. Do NOT build pointer-staleness machinery for a null-return race.
11. **Consequence for this plan:** the earlier draft's N-tick stability gate is CUT. It gated the wrong
    trigger (`wsUnloadSnapshot`+`wsLoad` cannot reach `Game::ms_scene`), its tick counter was
    framerate-coupled against a window whose length is content-dependent, and it would have been built
    against a defect never once observed. Instrument, do not gate.

## LOCKED — v28 SHIPPED the rest of the idiom; the ordering analysis above is now MOOT

All four rows this plan previously listed as unavailable landed in **v28** (`155` names, restaged):

| Row | Signature | Use here |
| --- | --- | --- |
| `cellProperty::setPortalTransitionsEnabled` | `void (bool)` | suppress the sweep across the write |
| `collisionWorld::objectWarped` | `void (Object*)` | reconcile collision after a discontinuous move |
| `clientWorld::findCellAtWorldPosition` | `void* (float x,y,z)` | **never null** (world-cell fallback) — resolves the coordinate-only case |
| `object::getAttachedTo` | `void* (void*)` | non-null ⇒ mounted ⇒ refuse to reparent |

**Consequence: adopt the engine's own idiom whole** (`GroundScene.cpp:1492-1497`), which the provider
handed us verbatim and which they independently confirmed is also what
`ClientInteriorLayoutManager::applyInteriorLayout` uses internally:

```
setParentCell(C);
setPortalTransitionsEnabled(false);
    setTransform_o2p(...);            // o2p, because you have ALREADY reparented
setPortalTransitionsEnabled(true);
collisionWorld::objectWarped(player);
```

With the sweep suppressed, **axiom 6b's ordering question stops mattering** — the hazard it reasoned
about cannot fire. Keep 6b in the record because it explains WHY the bracket is required, but do not
implement the unsuppressed transform-first sequence or the three-call variant; both are superseded.

> ⚠ **`setPortalTransitionsEnabled` is GLOBAL, UNSCOPED state — no RAII, no refcount** (provider's
> explicit warning). An early return, a `break`, or an SEH unwind between `false` and `true` leaves
> portal transitions off **for the rest of the session**, and the resulting symptom will look nothing
> like its cause. **Wrap it in an RAII guard whose destructor re-enables**, and never call the raw
> setter from more than that one place.

**The mounted-player hole closes too:** refuse the reparent when `getAttachedTo` returns non-null,
rather than shipping "do not teleport while mounted" as a disclosed limitation.

**Do NOT reach for `getParentCell` as a cheap mount proxy — it is actively the wrong tool, not merely
unavailable.** Mount attachment and cell attachment share the same `m_attachedToObject` field,
distinguished only by the `m_childObject` flag, and `getParentCell()` (`Object.cpp:1372-1383`)
deliberately walks *through* mount attachment to resolve the mount's ambient cell. A mounted and an
unmounted player therefore report the same parent cell **by design**. Downward raycasts and height
heuristics were also considered and rejected as unreliable for gating a silently-corrupting call.

All rows are asked for in the follow-up provider note. Until they land, this plan uses the derived
ordering (axiom 6b) and accepts the sweep churn.

<notes>
HANDOFF TO PLAN 11 — what bookmarks must carry. **A `CellProperty*` is a single-frame value, not a
handle.** It dies with its building on any scene reload, and the address can be recycled — the same ABA
class as [[raw-pointer-identity-aba-across-process-boundary]]. Bookmarks must therefore persist the
**building `NetworkId` + cell index/name** and re-resolve the pointer at use time, never store the
pointer. Plan 11 should not describe bookmarks as cell-aware for coordinate-only destinations until the
resolver row lands.

STILL OPEN AFTER THIS PLAN, deliberately:
- **Four provider rows requested** — `setPortalTransitionsEnabled`, `CollisionWorld::objectWarped`, a
  child-object guard, and `ClientWorld::findClosestCellObjectFromWorldPosition`. The last one is what
  makes coordinate-only interior teleports resolvable, and it is also what placement routing needs.
- **The ordering question is CLOSED** (axiom 6b) — transform-first, because `setParentCell` does not
  sweep and therefore whichever call runs last determines the final cell. This supersedes an earlier
  draft that declined to resolve it; the trace was available and the punt was a mistake. The provider
  reaches the same conclusion from a rationale that does not survive tracing (their stale-`cellChanged`
  concern is cosmetic), so the ordering is right but the reasoning behind the contract comment is not —
  reported to them as data, not as a correction demand.
- **Collision position cache — SOLVED by v28.** `CollisionProperty::m_lastTransform_w/_p` is written
  only via `storePosition()`, reached only from `objectWarped()`, and `CollisionWorld::moveObject`
  compares against it. Without that row both orderings left the collision system reconciling against a
  stale pre-teleport position. `collisionWorld::objectWarped` shipped in v28 and Task 2 calls it, so
  this is closed — the earlier three-call workaround that partially recovered it is superseded.
