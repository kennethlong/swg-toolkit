<objective>
Build D-02/D-03's Remove capability: a World-panel row action, guarded by an undo toast (no confirm dialog,
the exact `DeleteUndoToast.tsx` pending-diff precedent scoped to decoration rows), that removes a `.ilf` row
via Plan 01's `assembleDecorationEdit(kind='remove')` and re-derives the building template — the SAME
model-D data path as moving a stock table, per D-02 ("any decoration is removable, stock included; the stock
file is never touched, so removal is inherently reversible"). Undo re-adds the row via the SAME
`kind='add'`-equivalent data path (not a bespoke "undo" mutator), matching the phase's "one code path" ethos.

For D-04's live-despawn branch: `removeDecorationRow` checks whether the target row is CURRENTLY associated
with a live WS node id the toolkit is tracking from this session (via `worldEditorStore`'s session overlay —
populated when Plan 12's placement flow spawns a node, before its own automatic post-persist cleanup would
otherwise run, or by any future design that leaves a node live longer). If so, it calls
`hostCommand.sendDespawnNode` before/alongside the data removal; otherwise the removal is data-only and the
row's status reads "removed — reload scene to see it gone" (matching D-10's honesty-pattern precedent for
mirror-off warnings) until the user reloads.

Purpose: close SC4's REMOVE path end-to-end (data-only guaranteed; live despawn opportunistic where tracked).

and the World panel's per-row Remove action, fully tested.
