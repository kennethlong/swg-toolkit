## ⚑ ROUND-3 WORK-LIST — ranked by severity and cross-reviewer convergence

### R1 — [HIGH] `reconcileMirrorMode` never receives the `buildingTemplates` map → D-09 reconcile is inert/throws for every building while the flag still flips
**Codex H1 + Opus H1 (independent 2-way convergence; same seam family as Cursor's R2).** The mirror target is
derived only from the stock building template: `readInteriorLayoutFileName(readVfs(edit.buildingTemplateVfsPath))`
(`decorationPersist.ts:120-125,199`). R3 established that `buildingTemplateVfsPath` is NOT recoverable from
override-dir bytes and must come from Plan 02's `worldEditorBuildingTemplates` map via
`scanWorldEditorState(overrideDir, buildingTemplates)` (Plan 04 ROUND 3). Plan 13 was updated to consume it —
**Plan 06's `reconcileMirrorMode` was not.** Its `<interfaces>` still cites the stale one-arg
`scanWorldEditorState(overrideDir)`, its behavior says "reads `scanWorldEditorState(overrideDir)` for the full
list", and it specifies no fail-closed branch for an empty path. Result: every building carries
`buildingTemplateVfsPath: ''` → `writeStockMirror`/`removeStockMirror` get no path → **D-09 reconcile-on-flip is
dead for every building** — the exact "flag lies about disk / stale mirror" class D-09 exists to prevent (the
7/19→7/30 failure night the maintainer cited).
**Fix:** `reconcileMirrorMode` reads `readWorkspaceJson(studioDir).worldEditorBuildingTemplates ?? {}` (it already
has `studioDir`) and calls `scanWorldEditorState(overrideDir, map)`; add a fail-closed words-only `failures`
entry for any building whose `buildingTemplateVfsPath` is `''`; update Plan 06's `<interfaces>` to the two-arg
signature. → **Plan 06** (+ interface citation).

### R2 — [HIGH] `refresh()` call sites reuse mount-cached `meta` → the pre-persist (empty) map reaches the store → `buildingTemplateVfsPath` stays `''` on the tree after a live persist
**Cursor HIGH (same seam as R1, different facet).** Plan 06 writes `worldEditorBuildingTemplates` to disk at
CAPTURE time. Plan 14 Task 2's history-triggered refresh reuses "the SAME `meta` Plan 10's mount effect already
resolved" — but that `meta` was read once on mount, BEFORE any persist wrote the map. So the common flow
(persist in game → select row → Remove/detail, without manually hitting live-strip Refresh) passes `{}` into
`refresh()` and every building's `buildingTemplateVfsPath` renders `''`, defeating R3 end-to-end for Remove.
Plan 13 re-reads `meta` at click time but still sources `building.buildingTemplateVfsPath` from the tree row that
the stale refresh populated.
**Fix:** every `refresh(overrideDir, …)` call site (mirror toggle, mount, history effect, post-remove, post-ADD)
must `readWorkspaceJson(studioDir).worldEditorBuildingTemplates` **at call time** — never cache `meta` from
mount for the second argument. Optionally add a refresh-on-`recordPersistResult` hook in Plan 08 so wave-4 Remove
isn't gated on a manual strip refresh. → **Plans 10, 13, 14** (+ optional 08).

### R3 — [HIGH] `rowIndex`-keyed session state (`sessionOverlay` / `selectedRowId` / the "(NEW)" diff) is silently invalidated by the new positional `removeNode` → stale badge misattribution + false "(NEW)" tags
**Sonnet HIGH (new — unflagged in any prior round or R1–R13).** Plan 04 keys row identity everywhere as
`${buildingId}:${cellName}:${rowIndex}` and guarantees `rowIndex` is "ALWAYS recomputed fresh from the current
parse pass, never cached" — correctly, on the scan-tree side. But `worldEditorStore.ts`'s
`sessionOverlay: Map<rowId, 'armed'|'saved'|'failed'>` and `selectedRowId` use that same composite key, and Plan
04's own spec says `refresh()` "does NOT clear sessionOverlay/history". `.ilf` rows are positional — `removeNode`
(Plan 01) removes index N and shifts every later same-cell row's effective index down by one. Remove (new this
phase, Plan 13) is the first operation that shifts indices out from under a live session, and nothing
invalidates the overlay/selection layer when it does.
- **Scenario A (stale badge):** arm+persist row 4 → `sessionOverlay['b:cell:4']='saved'`; Remove row 1 → disk row
  4 is now index 3, but overlay is untouched; a later ADD appends a brand-new decoration at index 4 that
  silently inherits the stale `'saved'` badge.
- **Scenario B (false "(NEW)"):** Plan 14's "(NEW)" tag = "row ids present after refresh but absent before". Any
  Remove with decorations after it in the same cell renumbers them → those untouched rows get new composite ids
  → mislabeled "(NEW)".
This is the project's own named "stale override" failure class one layer up the stack (session UI state instead
of disk mirror state).
**Fix:** either (a) `refresh()` reconciles `sessionOverlay`/`selectedRowId` against the new tree — drop overlay
entries whose composite id no longer resolves, re-key by content (template+cellName) not numeric index — or (b)
give decorations a scan-stable identity that survives a same-cell removal (a monotonic per-building counter
stamped at ADD time) instead of positional `rowIndex`. → **Plans 04, 10, 13, 14** (design decision required —
see Recommended approach below).

### R4 — [HIGH] D-13 detail card renders **translation columns only**, discarding 9 of 12 transform components → a rotate-only edit renders identical before/after and reads "nothing changed" — directly undermining SC5
**Opus H3 (new — locked-decision narrowing that the R5 fix left in place).** R5 made the data reachable
(`PersistHistoryEntry.beforeTransform`/`afterTransform` = the 12-element o2p arrays, populated by Plan 08), but
Plan 10's render spec narrows it back: *"both transforms' translation columns (e.g. before (12.3,0.0,−4.1) →
after (12.9,0.0,−3.6)) plus cell/row"*. Consequences: (a) the panel "full readout" carries no more than the
strip's compact positional Δ, collapsing the two-surface distinction D-13 (locked, no discretion) draws; (b) the
9 rotation/scale components are dropped; (c) **for a rotate-only edit the field renders identical before/after
triples** — on the exact edit class SC5 exists to certify ("Rotation edits persist and reload correctly"). Not
disclosed in Plan 15's gap ledger.
**Fix:** render the full 12-element before/after transforms (or position + a derived yaw/orientation delta) in
the detail card, and add a Plan 10 test asserting a rotate-only history entry produces a *visibly different*
before/after readout. If position-only is genuinely intended, D-13 must be amended by the maintainer and the
reduction recorded in Plan 15's ledger (per R5's own resolution rule — the locked decision wins by default). →
**Plan 10** (+ Plan 15 ledger if descoped).

### R5 — [HIGH] Plan 04 imports `sanitizeId` from Plan 01 but sits in the same Wave 0 with `depends_on: []` → R1's Wave-boundary defect class recurs
**Opus H2 (new).** `sanitizeId` is module-private today (`decorationPersist.ts:80`); Plan 01 Task 3 adds the
`export`. Plan 04 Task 1 action says "Import `sanitizeId` from `./decorationPersist` (Plan 01's now-exported
helper)" — yet Plan 04 is `wave: 0, depends_on: []`, running in parallel with Plan 01, and its own
`<verification>` requires a clean `tsc --noEmit`. If Plan 04 executes first, the import doesn't exist yet. The
import is also **unnecessary**: Plan 04's own text says the map key is "the SAME sanitized `<id>` the filename
suffix already is" — the `edit_<id>.ilf` suffix is already `sanitizeId`'s output.
**Fix (cheapest, no wave cascade):** drop the `sanitizeId` import from Plan 04; key the map directly off the
filename suffix and document that the suffix *is* sanitized output. (Alternative — adding
`depends_on: ["05.1-01"]` — cascades 04→wave 1, 06→2, 10→3, 11→4, 13→5, 14→6, 15→7; avoid.) → **Plan 04**.

### R6 — [HIGH/MEDIUM] `reconcileMirrorMode` persists `mirrorToStockIlf` even when `failures.length > 0` → the flag claims a disk state that is false for the failed buildings (D-09)
**Codex HIGH#2 + Opus M1 (severity split — treat as HIGH; it is the literal D-09 invariant).** R8 made reconcile
return `{ failures }`, but Plan 06 still calls `updateWorkspaceMeta(studioDir, { mirrorToStockIlf: nextValue })`
unconditionally, and Plan 10 only `log('warn', …)`s the failures — no rollback, no durable surface. If OFF fails
to delete one mirror (or ON fails to create one), the persisted flag lies about disk — reopening D-09's
stale-override class.
**Fix:** persist `mirrorToStockIlf` only when `failures.length === 0`, OR persist it and durably record the
failed building ids so the next reconcile retries them and the UI/settings stay aligned with disk. → **Plan 06**
(+ Plan 10 failure surfacing).

### R7 — [MEDIUM] Remove undo re-adds via append (not original row position) → reorders the cell and shifts later row identities
**Codex MEDIUM + Sonnet MEDIUM (2-way).** Plan 01 defines `addNode` as append-only; Plan 13's undo re-adds the
removed `IlfNode` via that same `kind='add'` path (D-01 "one code path"), so an undone middle row lands at the
end of its cell, changing row identity/order and compounding R3's stale-key problem. D-02's "inherently
reversible" framing doesn't disclose that Undo reorders the cell.
**Fix:** add an insert-at-cell-row helper for undo, OR explicitly scope undo to "visual re-add only" and disclose
the reorder in Plan 15's ledger alongside the existing 8s-window scoping note. → **Plans 01, 13** (+ Plan 15
ledger).

### R8 — [MEDIUM] Plan 10 real `tsc` errors: `liveStatus.clientLabel` and `resolveScanRoot` null-branch
**Opus M2 + M3.**
- **M2:** Plan 10 uses `liveStatus.kind === 'attached' ? liveStatus.clientLabel …` but the attached union is

  (`:237`, set `:394`). As written this is a `tsc` error. Use `useLiveStore((s) => s.clientLabel)` (the accessor
  `useChannelReader.ts:173` already uses).
- **M3:** `resolveScanRoot(...): string | null` feeds four `string`-typed consumers (`makeReadVfs`,
  `reconcileMirrorMode`, `refresh`, `removeDecorationRow`), but no plan specifies the null branch (unbound
  project / offline is a normal D-07b state). Specify a words-only disabled/refuse state matching the Scene
  accordion's "no live session" precedent. → **Plan 10** (+ 04/13).

### R9 — [MEDIUM] `resolveScanRoot`'s revised signature still doesn't type-check against `resolveOverrideDir`

## Consensus summary

- **Verdict:** NOT CONVERGED. 4 of 5 reviewers found HIGHs; the factual reviewer (Fable) is clean — the revision
  injected no fabrications, so this is purely a wiring-completeness round.
- **The dominant signal (convergence-from-divergence):** Codex (call-graph), Opus (spec), and Cursor
  (line-level) — three different angles — all landed on the **`worldEditorBuildingTemplates` map →
  `reconcileMirrorMode` / `refresh` / D-09 mirror-state** seam (R1 + R2 + R6). R3 (the durable map) was threaded
  to the scan (04), the contract (02), and Remove (13), but never to the function D-09 actually depends on (06's
  `reconcileMirrorMode`) or to the refresh call-time read. **Fix R1+R2+R6 together** — they are one seam.
- **Two independent single-reviewer HIGHs worth equal weight:** Sonnet's R3 (row-identity vs positional remove —
  the exact project failure class, and it survived four prior reviewers precisely because it lives in the
  *interaction* between three individually-correct plans) and Opus's R4 (D-13 transform narrowing breaks SC5 on
  rotate-only edits — ties a locked decision to a success criterion).
- **Agreed cleared:** the R1–R13 Round-2 items other than the seam gaps above, the map key convention,
  `makeReadVfs` export, `removeDecorationRow(mappingName)`, the `12→05` dependency edge, and every ground-truth
  citation.
- **Recommended fix approach:** R1+R2+R6 as one Plan-06/10/13/14 seam pass; R5 as a one-line Plan-04 import drop;
  R4 as a Plan-10 render+test fix; R3 needs a design pick (reconcile-overlay-on-refresh vs scan-stable identity)
  — recommend (a) refresh() reconciles sessionOverlay/selectedRowId against the new tree, cheapest and localized
  to the store. All are targeted edits; no re-architecture.
