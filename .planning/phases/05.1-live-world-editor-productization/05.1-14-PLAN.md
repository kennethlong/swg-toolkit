decorations yet — add one to an existing building first" or similar), rather than silently failing or
guessing a cell name. The permanent fix (a real provider shim resolving any cell) is filed as a change-request
handoff in Plan 15, per the cross-repo protocol — this plan does NOT edit `../swg-client-v2`.

**CROSS-AI REVIEW REVISIONS (2026-08-01, C6 — HIGH, split across three reviewer facets):**
- **Fable's facet (eligible-building set narrower than RESEARCH's own recommendation):** `worldEditorStore.
  tree` is populated ENTIRELY from `worldEditorScan.ts`'s disk scan of the override dir (D-05) — buildings that
  have NEVER been edited (no `edit_*.ilf` on disk yet) are simply absent from the tree, even if their STOCK
  `.ilf` (readable offline via the mounted VFS) already has >=1 decoration and could, per RESEARCH's own
  stated recommendation, supply a borrowable cellName. Building the stock-`.ilf`-fallback lookup RESEARCH
  envisioned would require the World panel to also enumerate and let the user select never-edited buildings —
  a materially larger scope addition (a new building-discovery UI + a new stock-scan code path) than this
  targeted revision should absorb this late in the phase. Per this plan's own scope-reduction rules (a
  genuine "missing UI to select an unedited building" gap, not laziness), this revision EXPLICITLY DISCLOSES
  the narrowing rather than silently shipping it: ADD is available only for buildings ALREADY visible in the
  World panel's tree (i.e., previously-edited ones with >=1 decoration) — Task 2's behavior spec and this
  plan's `must_haves` say so in these exact words, and Plan 15's sign-off checklist records it as an observed
  scope note, not a silently-passed check.
- **Codex/Sonnet's facet (wrong-cell/wrong-room risk within the borrowed building):** Plan 12 now adds a
  building-ID cross-check guard (refusing a click in the WRONG building), but nothing can verify the click
  landed in the CORRECT ROOM within a multi-cell building (no advertised endpoint resolves a click's cell
  name — that is the exact gap the Plan 15 change-request exists to close). Task 2 below adds an explicit,
  visible warning to the placement-active toast copy: "place only in the SAME ROOM as the decoration you
  selected — this building may have other rooms the toolkit can't tell apart yet." This does not eliminate
  the risk (no code fix is possible without the provider shim) but makes it an INFORMED risk, not a silent
  one.
- **Sonnet F9 / Cursor M5:** the "(NEW)" row marker was named in this plan's `sketch_elements` frontmatter in
  the original version but never appeared in any task's actual behavior/action text or test assertions. Task 2
  below adds it explicitly.

**ROUND 4 REVISION (2026-08-01, REVIEWS.md W2 — HIGH, Sonnet):** the original Task 2 tracked "(NEW)" via a
raw positional-id Set diff ("row ids present in this session's history-triggered refresh but not seen in the
PREVIOUS refresh's row-id set"). Because `worldEditorRowId` embeds the numeric `rowIndex`, ANY reindex of a
cell — not just this plan's own ADD, but Plan 13's Undo re-adding a row at the END of its cell (D-01's
append-only mandate) — shifts every later same-cell row's id, and a raw before/after id-Set diff would then
misread the RESHUFFLED (but not actually new) rows as "(NEW)" too. Task 2 below replaces the positional-id
diff with a count-map walk over the whole tree that SHARES ONLY the content-identity KEY (buildingId+
cellName+objectTemplateName) and the duplicate-ambiguity posture Plan 04's `refresh()` already established for
`sessionOverlay` reconciliation — **(ROUND 5, V9 — MEDIUM, Opus+Fable, honest-framing fix)** this plan does
NOT literally reuse `refresh()`'s routine: Plan 04 walks SPARSE overlay entries with a positional-nearest
tiebreak, while this plan walks the FULL new tree against a per-building count map with a consumption-order
tiebreak — a different algorithm for a different purpose (detecting excess content vs. reconciling existing
status), sharing only the identity key and the "duplicates are ambiguous" posture. The count-map mechanism
itself is fully defined in THIS plan's Task 2 — nothing is imported from Plan 04 for this purpose, and no
plan claims otherwise. A row is "(NEW)" only when its CONTENT has no matching occurrence in the
immediately-prior tree snapshot for that building, never merely because its numeric position changed.

**ROUND 5 REVISION (2026-08-01, REVIEWS.md V2/V3/V9):**
- **V2 (HIGH, Sonnet):** the ROUND 4 diff/`prevTreeRef` update ran ONLY when `worldEditorStore.history` grew.
  Remove grows history; Undo (Plan 13) does not — its own `refreshTree()` call never triggered a diff pass, so
  `prevTreeRef` went stale the instant Undo restored a row. The NEXT unrelated history-growth event anywhere in
  the session then diffed against that stale snapshot and mislabeled the ALREADY-RESTORED row "(NEW)" — the
  exact class W2 was filed to close, reopened one layer down. Task 2 below keys the diff effect off the `tree`
  reference itself (`useEffect(..., [tree])`), so EVERY `refreshTree()`-triggered update — mount, manual
  refresh, mirror toggle, Remove, Undo, ADD-confirm — advances `prevTreeRef` uniformly; `prevTreeRef` can never
  go stale between refreshes again. Undo's OWN update is a SILENT re-baseline (via Plan 13's
  `suppressNextDiffRef` groundwork, consumed and cleared here): the diff pass advances `prevTreeRef` to the
  restored tree WITHOUT computing/marking any "(NEW)" row, since a restore is never a fresh placement even at
  the instant it reappears — closing V2 at BOTH the "later misattribution" layer AND the "Undo's own instant"
  layer a pure content-diff would otherwise still get wrong (content genuinely reappearing looks identical to
  content genuinely appearing, to a diff with no other signal).
- **V3 (HIGH, Opus):** the ROUND 4 spec had no stated initial value or first-pass rule for `prevTreeRef`, and
  directed "a building absent from the previous snapshot contributes an empty count map — ALL of its rows are
  then genuinely new." Two reachable sequences fell out of this: every World-tab mount (tree goes `[] →
  populated`, marking the WHOLE tree "(NEW)"), and the first persist in any building (the whole building
  appears at once per D-05's disk-scan scope, marking every stock row "(NEW)"). Task 2 below initializes
  `prevTreeRef` to a `null` sentinel; the FIRST diff pass after mount seeds `prevTreeRef` from the current tree
  and marks NOTHING "(NEW)"; and REVERSES the absent-building rule — a building absent from the previous
  snapshot now contributes ZERO "(NEW)" rows (a whole-building first observation is never a placement).
