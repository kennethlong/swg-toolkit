## Bug B — re-entrant scene swap from inside Present (CRASHES THE CLIENT)

Maintainer clicked "Editor scene" while **inside the cantina** (a POB with live cell/portal state).
Client FATAL, symbolized:

```
InputScheme.cpp(480) : FATAL 5fd41635: InputScheme::fetchGroundInputMap called on a new player
                       without releasing old one [[swg,single_player,player,4611686018427387938]]
  GroundScene.cpp(3868) / GroundScene.cpp(823) / GroundScene.cpp(966)
  Game.cpp(222) / Game.cpp(1857) / Game.cpp(1846)
  engine_advertise.cpp(331)        <- the advertised game::loadScene shim
  <agent 0x6C8D3AD8 / 0x6C8D228A / 0x6C0521DF>
  Graphics.cpp(1171)               <- WE ARE INSIDE THE GRAPHICS/PRESENT FRAME
  Game.cpp(1725) / Game.cpp(1074) / ClientMain.cpp(429)
```

Call site: `overlay.cpp:960` `gameLoadScene(s_edTerrain, s_edPlayer)` inside `renderFrame()` (:713),
which runs inside `hkSwapChainPresent` (:1028). The ImGui button handler swaps the scene
**synchronously from within the present callback**; the engine tears down and rebuilds the scene
mid-frame and the old player's ground input map is never released.

PRE-EXISTING: `git diff` of 05.1-05 touches `gameLoadScene` **0 times**; the call arrived in
`36ab9b7`. The July handoff already listed the editor-scene verify as *owed* — this checkpoint is the
first time the button was ever pressed.

Repro context: first hit **inside the cantina** (a POB with live cell/portal state), then retried
**outside any building — it FATALs there too** (maintainer, 2026-08-02). So POB/cell state is NOT
causal and the initial "maybe interior teardown skipped the input-map release" reading is FALSIFIED.
The defect is the **re-entrant call itself**, unconditionally: `loadScene` issued from inside the
present callback is unsafe regardless of where the player is standing. Do not scope the fix to the
interior case.

Prior art: the July CONSULT-UTINNI synthesis already locked a **game-thread command queue** as the
architecture. The Slice-0 buttons never got one. `game::mainLoop` is advertised (client catalog
row 74) and is the natural drain point.

**SCOPE DISCRIMINATOR — Teleport is a WORKING CONTROL (maintainer, 2026-08-02).** Teleport is invoked
from the same overlay button surface, in the same `renderFrame()`/Present context, and does NOT crash.
So "called from inside Present" is not sufficient to fault — the unsafe class is narrower:

| Call | From Present | Why |
| --- | --- | --- |
| Teleport | **safe** | moves the EXISTING player; no lifecycle churn |
| `gameLoadScene` | **FATAL** | DESTROYS and RECREATES player + scene mid-frame — precisely what `fetchGroundInputMap called on a new player without releasing old one` reports |

Queue **scene-lifecycle** calls only. Do NOT route teleport (or other non-lifecycle calls) through the
deferred path — that would add latency to a proven-working surface for no benefit, and it widens the
diff for no reason.

`wsRemoveNode` / DESPAWN_NODE is **UNKNOWN**: it mutates world-snapshot state but does not recreate the
player. Do not assume either way — Plan 09 owns its live verification.

## Bug A — per-frame strip reads fault the render callback (HUD VANISHES)

One run (PID 4496) logged **3,424 consecutive** `overlay: SEH fault in renderFrame — frame skipped`,
one per frame, beginning immediately after `[PortalCullProbe] DOOR ... cell=hall3/bedroom3/kitchen/
elevator1/livingroom1/foyer1` — i.e. on entering a cell-heavy POB. Five other runs logged **zero**.
Intermittent, pointer-dependent.

Suspect: the strip's Hover branch runs every frame with a BORROWED `Object*`:

```cpp
if (swg::endpoints::getContainingBuildingId) bldgId = swg::endpoints::getContainingBuildingId(g_lastRayObj);
...
buildStripLabel(...)   // -> getObjectByIdAdvertised(&bid) -> getTemplateFilename(bldg)
```

`renderDecorationStrip()` is called BEFORE the hover-tracking block that maintains `g_lastRayObj`, so
it always reads the PREVIOUS frame's pointer — which can be freed as objects stream in/out.
Null-checking the SLOT does not help; the ARGUMENT is what is bad. See
[[raw-pointer-identity-aba-across-process-boundary]].

Blast radius is total because `renderDecorationStrip()` is called early in `renderFrame()`, and
`hkSwapChainPresent` wraps the WHOLE of `renderFrame()` in one
`__try/__except(EXCEPTION_EXECUTE_HANDLER)`. One bad call in the new strip therefore blanks the
ENTIRE overlay — including every pre-existing working panel — silently and permanently.
</evidence>
