## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Bug] Cell-containment defect found and fixed mid-checkpoint**
- **Found during:** Task 3 (blocking live checkpoint), cantina door-close/open test
- **Issue:** `attemptPlacementSpawn()` parented the `wsAddObject` spawn to the BUILDING object, leaving a POB's contents resident in the WORLD cell — geometrically inside the building but not portal-resident in its interior cell. Reproduced twice: visible through the open cantina doorway, disappeared the instant the door closed, reappeared when it opened (second repro placed deep in the main room to rule out a doorway/threshold confound).
- **Fix:** Reparent the freshly spawned object into the cell at the placement point via `findCellAtWorldPosition` + `setParentCell`, reusing the already-resolved `spawned` Object* from the auto-arm tail. Write-then-reparent order preserved (the transform is already written in WORLD space by `wsAddObject`; no cell-relative pre-conversion — `setParentCell` converts through the source cell's transform itself, avoiding the v30 `warpPlayer` bug class). `isChildObject` mount guard refuses the reparent on a mounted/child object. `setParentCell==0` and unresolved endpoints fail closed with a words-only reason. `objectWarped(spawned)` mirrors the collision-resync call `teleportPlayerToWorldPos`'s fallback path already makes.
- **Files modified:** `packages/live-inject/agent/overlay.cpp`
- **Verification:** Live-verified in the cantina across the door-close/open test, twice, including a repro placed deep in the main room.
- **Committed in:** `93a8a3c` (landed before this close-out session; kept untouched by Part 1's probe removal)

## Evidence-Attribution Correction

The maintainer's original checkpoint report — "placed from the doorway, renders in world space" — was cited during the session as proof that `attemptPlacementSpawn` was broken, and it drove fix 93a8a3c. **That attribution does not hold up and must not be repeated.** The report almost certainly came from the LEGACY "Insert at cursor" button (`overlay.cpp:1247`, prior to its retirement in d82f659), which hardcoded `wsAddObject(..., 0)` — `containedById 0` means "the world sphere tree," verified against `swg-client-v2 WorldSnapshot.cpp`. That is a structurally different code path from this plan's `attemptPlacementSpawn`.

93a8a3c is still the correct fix, but it is justified by three things that are NOT that original report:
1. Client `containedById` semantics (0 = world, confirmed against `WorldSnapshot.cpp`).
2. The provider's explicit v27 handback statement that "`setParentCell` is what makes a newly placed interior object actually LIVE in that cell rather than merely sit inside it geometrically."
3. The verified after-state — the door-close/open repro against `attemptPlacementSpawn`'s own actual spawn path, performed twice, once deliberately away from any doorway confound.

## Known Carve-Outs (documented, not silently passed over)

Per this phase's own convention (05.1-15's `must_haves`): a documented gap is recorded here explicitly, never presented as fixed.

**1. Visual continuity after an ADD-persist does not hold for the rest of the session, contrary to this plan's own text and sketch 021-A Frame 3.**
The reconciliation despawn (`wsRemoveNode` of the temporary `wsAddObject` preview node, in `applyPendingRebind`'s `DECO_RESULT_OK` branch) makes the object VANISH on Persist for an OCCUPIED building, because that despawn assumes the building re-renders from the new `.ilf` — which an occupied building never does (no per-building interior refresh exists yet). The object is NOT lost; it returns on the next interior rebuild (confirmed live on zone-in). Root cause is the pre-existing gap filed at `.planning/handoff/2026-08-02-CHANGE-REQUEST-interior-refresh.md`. Fires on ADD only — an EDIT-persist keeps the object visible, since the despawn is gated on `wasAdd`.

**2. Cell name is operator-supplied, not derived, and this was demonstrated live.**
`g_capCellName` is copied verbatim from the `HOST_CMD` `STR2` payload and is never resolved from the placement point, so a wrong caller-supplied name writes a wrong-cell row that looks healthy on disk. Demonstrated live: a foyer placement was recorded as `foyer1` purely because that string was the one passed in. This is Plan 05.1-15's change request — see the reshaped version below, which is now much smaller than originally scoped.

**3. "Place here" button acts on a STALE ray sample.**
Filed at `.planning/todos/pending/place-here-button-stale-ray-sample.md` (committed in this close-out). The hover ray is only sampled while `!io.WantCaptureMouse`, so it freezes the instant the cursor moves onto the placement strip. The floor-click path re-checks that flag at click time and is unaffected; the "Place here" button does not, and can place at a stale target. Not a reproduced live defect — a latent correctness hazard, disclosed rather than silently left implicit.

**4. GIZMO World/Local mode radios were removed with the Slice-0 window (`d82f659`).**
`g_gizmoMode` (default `1` = Local) now has no writer anywhere in `overlay.cpp` — confirmed by inspection, one read site (`renderFrame`'s `ImGuizmo::MODE` selection), zero write sites. G/R translate/rotate still work fully from the 020-A strip. This is recorded as an accepted narrowing, not a fix: the maintainer was offered a rehome for the mode toggle during the checkpoint session and did not request one.

## Reshaped Change Request (inherited by Plan 05.1-15)

Session research shrank Plan 15's owed cell-name-resolution change-request dramatically. Recorded here so Plan 15 does not re-derive it or file the larger original request:

- `CellProperty::getCellName()` ALREADY EXISTS in the client and returns the literal cell-name string (`swg-client-v2 src/engine/shared/library/sharedObject/src/shared/portal/CellProperty.h:120`, inline definition at `:249` returning `m_cellName`). A `getCellNameCrc()` sits beside it at `:121`/`:256`.
- It is INLINE, so there is no out-of-line symbol to advertise/hook directly — that, and only that, is why the toolkit cannot read it today.
- The toolkit already holds the `CellProperty*` this needs: `clientWorld::findCellAtWorldPosition(x,y,z)` is advertised (v28, never null, annotated "placement routing"), and the 93a8a3c fix already calls it.
- The ask therefore collapses from "build a `getContainingCellName` resolution shim" to "advertise a one-line wrapper exposing the existing inline `CellProperty::getCellName`":
  ```
  findCellAtWorldPosition(placementPoint) -> CellProperty*   [already have]
  getCellName(cellProperty)               -> "foyer1"        [the only remaining ask]
  ```
- This derives the name from the PLACEMENT POINT, matching the maintainer's recorded design intent in `.planning/todos/pending/exterior-ws-node-editing.md`.

The handoff document itself is Plan 15's deliverable and is intentionally not written here.
