# Plan 05.1-17 — Make the editor's reload atomic

<objective>
Reload works now. The engine defect behind the lossy reload was the provider's, and they fixed it —
verified live this session. What is left is that reload completes **asynchronously over ~1-2 seconds**,
while Plans 12 and 15 reload and then immediately check whether an object is present.

This plan makes a reload atomic so that `ack=1` means "the world is rebuilt," and a verification step
can trust it. It also closes three queue hazards a review found in the path it routes through.

It is NOT a fix for a broken reload. Do not describe it as one.
</objective>

<evidence>
## LOCKED — measured live 2026-08-02 on the restaged exe. Do NOT re-derive or contradict.

1. **The root cause was an engine defect and it is FIXED UPSTREAM.** `WorldSnapshot::loadStep()` used to
   be pumped only from `GroundScene::updateLoading()`, which early-returns unless `m_loading` — so an
   in-world `load()` started a parse nothing would ever advance. Provider commit **`04c3f8e11`** hoists
   the pump into `GroundScene::update()`, per-frame, unconditional. Nothing in this plan re-implements
   that, and no agent-side workaround for it is in scope.
2. **Verified live:** after "Reload current scene" in-world, the world returns — buildings, collision,
   and snapshot creatures (banthas/dewbacks) — **in one to two seconds, progressively.** No wandering
   required. The pre-fix behavior (indefinite absence until an unrelated call force-finished the parse)
   is gone.
3. **THE REMAINING PROBLEM, and this plan's entire justification:** that rebuild is **asynchronous**.
   Plan 05.1-12's ADD checkpoint says *"Trigger 'Reload current scene'. Confirm exactly ONE instance of
   the new object is visible"*, and Plan 05.1-15 reloads to confirm a rotation persisted. Both read the
   world during the 1-2s window and can see a correctly-persisted object as MISSING.
4. **Interior-NPC loss is FIXED upstream (`0b2e9259c`), and it left a residual that changes this
   plan's scope.** We measured that a reload permanently stripped interior NPCs (exterior unaffected);
   the provider confirmed the mechanism — `unload()` deleted snapshot roots unconditionally, cascading
   through `PortalProperty : Container` → cells → `CellProperty : Container` → occupants — and guarded
   it with the same `isClientCachedOnly` predicate `update()`'s drain already used. Live-verified: 54
   occupants survived on node 1082874.

   **THE RESIDUAL — a kept building renders its PRE-EDIT state.** A surviving root collides with the
   re-parsed node on the next `load()`: `createObject` returns `CEC_objectAlreadyExists` and `update()`
   strips the NEW node's sphere handle. The building stays on screen as it was on disk **before the
   edit**, until a zone change or relog. Unoccupied buildings reload and show edits normally.

   **This plan CANNOT fix that.** Task 2's completion poll makes a reload *atomic*; it does nothing
   about a kept root rendering stale geometry. Atomicity and correctness are separate problems, and
   only the first is in scope here.

   **Consequence — reload is NO LONGER the verification instrument for interior work.** Plans 12 and 15
   move to per-building interior refresh (`.planning/handoff/2026-08-02-CHANGE-REQUEST-interior-refresh.md`,
   filed to the provider inbox). This plan covers the coarse full-reload path only. The disclosure at
   the reload control changes accordingly — see Task 3.

   **MEASUREMENT RULE that came out of getting this wrong twice: any observation about server-streamed
   content taken after a `game::loadScene` is INVALID** — the editor scene has no server session and
   shows zero NPCs of any kind. Two earlier readings of this defect ("all NPCs drop", then "there are
   no cantina NPCs at all") were both artifacts of that. Do not re-derive either.
5. **Use `worldSnapshot::wsIsParsePending` (v28) — POLL, do not force.** `int (void)`; `1` = parse in
   flight, `0` = idle/complete. It is **the only `ws*` row with no `finishLoadNow()` prologue**,
   deliberately pure and non-forcing (`engine_hookpoints.inc:346`). The provider shipped it in direct
   response to this problem and explicitly asked us to drop the force-finish workaround.
6. **Neither alternative works — do not substitute either.**
   - `wsGetNodeCount` DOES force-finish (`WorldSnapshot.cpp:1780-1791`). An earlier draft of this plan
     used it as a completion barrier. **That approach is RETIRED**: it paid essentially the whole
     remaining parse synchronously (one frame advances ~40 ms of a ~3.1 s parse), producing a 1-2 s
     client freeze on every reload.
   - `wsGetGeneration` bumps on load/unload only (`:1918`) and says nothing about the parse.
   - `getLoadingPercent` looks right and is not: it returns `0` while parsing AND reports preload
     percentage afterwards, so `0` is ambiguous.

## LOCKED — polling is safe from our drain point (crew review RT-06)

7. **We drain OUTSIDE `GroundScene::update()`'s dynamic extent.** `GroundScene::update()` is reached
   from *inside* `Game::runGameLoopOnce` (the advertised `game::mainLoop`, `engine_advertise.cpp:788`)
   via `IoWinManager::processEvents` → `IOET_Update` → `GroundScene::processEvent`
   (`GroundScene.cpp:2179-2200`). Our drain runs **after** the original returns, so it does not nest,
   and a poll from there observes a consistent between-frames state.
8. **The engine advances the parse on its own, every frame**, since `04c3f8e11` hoisted `loadStep()`
   into `GroundScene::update()`. We do not need to pump it and **must not** — polling is purely
   observational. **Do not add re-entrancy defenses; there is nothing to defend against.**

## LOCKED — three hazards in the deferred queue (Cursor RT-02 review, file:line verified)

7. **Cross-kind interleaving is a real ordering bug.** `LoadScene` is a two-frame command: frame 1 calls
   `cleanupScene()` and **re-enqueues itself at the BACK of the ring** (`overlay.cpp:925-927`). If a
   `Reload` is already behind it in the same drain snapshot, the drain runs: cleanup → **Reload** →
   (next tick) `gameLoadScene`. The `Reload` therefore executes against a scene `cleanupScene` already
   tore down, and the load lands on top of whatever that left. The `toProcess` snapshot (`:887`)
   prevents frame 2 running early but does **not** protect against a different command in between.
   Pre-existing, but this plan routes two more callers into the queue and makes it reachable.
8. **Invalidation is ordered wrong.** The deferred `Reload` calls `invalidateSceneCachedPointers` only
   AFTER `wsLoad` (`:951-952`), but the object graph dies at `wsUnloadSnapshot`. `LoadScene` already
   invalidates before its teardown (`:917-922`).
9. **Enqueue has no coalescing** (`:807-821`) and the queue holds 4. Four reload clicks queue four full
   reloads back-to-back.

## CORRECTIONS to this plan's own earlier drafts — do not restore either

1. ~~"Force the parse to completion with `wsGetNodeCount` after `wsLoad`."~~ **RETIRED** at the
   provider's request (axiom 6) — it froze the client for 1-2 s per reload. The poll model replaces it
   and deletes the fallback-path special-casing, the head-of-line blocking, and the path-conditional
   ack semantics that came with it.
2. ~~"The barrier never runs inside the render callback."~~ **Was false** — `overlay.cpp:1492-1493`
   drains inside `hkSwapChainPresent` when the `mainLoop` hook is unavailable. Moot now (a poll is
   cheap anywhere), but the fallback drain path is real and Task 2 must not assume it away.
</evidence>

    reasoned exception to 05.1-16's "do not route working paths through the queue".

    **2d — fix the invalidate ordering** (axiom 8): invalidate BEFORE `wsUnloadSnapshot`, matching the
    `LoadScene` precedent. Keep distinct dbg reason strings for the three origins if cheap.

    **2e — guard the cross-kind interleave** (axiom 7). A `Reload` must not execute between a
    `LoadScene`'s two frames. Three parts, all REQUIRED — a partial implementation here is worse than
    the bug it fixes (crew review RT-07 Q1):

    1. **Detection must be exact.** "Mid-sequence" means *a `LoadScene` is in the ring with
       `sceneCleaned == true`* — the state set when frame 1 re-enqueues (`:925-927`). Do **NOT** use
       "any `LoadScene` in the queue": for `[Reload, LoadScene(frame 1)]` the `Reload` running first is
       SAFE, and deferring it would be a needless behavior change. Either scan the ring for that
       condition or maintain a latch set at `:926` and cleared at `:936`; the latch is simpler. State
       which you chose.
    2. **Defer by re-enqueue, then `break`.** Re-enqueued items fall outside the `toProcess` budget
       (`:881-886`), so they cannot be re-picked in the same pass and cannot livelock. **The `break` is
       load-bearing** — deferring and then falling through to execute the `Reload` body would both run
       it AND double-ack.
    3. **Handle re-enqueue failure — this is the ack-stranding trap.** The `Reload` has already been
       dequeued. If the re-enqueue fails (queue full), the command is LOST and a remote
       `hostCmdEpoch` receives **zero** acks, violating exactly-one-ack-per-epoch. Mirror the existing
       `LoadScene` precedent verbatim (`:927-931`): on failure,
       `if (cmd.hostCmdEpoch != 0) channelWriteHostCommandResult(0, cmd.hostCmdEpoch);`

    Do NOT change the `LoadScene` two-frame sequence itself.

    **2f — coalesce, but ONLY epoch-0 into epoch-0** (axiom 9). The naive rule "collapse a `Reload`
    when one is already pending for the same scene" is **UNSAFE** and must not be implemented: a remote
    `Reload` carries a `hostCmdEpoch` that is marked applied BEFORE enqueue (`:1000`), so the renderer
    is already waiting on it. Coalescing it away — or overwriting a pending slot's epoch — strands that
    epoch to an 11 s timeout (crew review RT-07 Q2).

    The ONLY safe coalesce is:

    | Pending | Incoming | Action |
    | --- | --- | --- |
    | epoch 0, scene X | epoch 0, scene X | drop incoming, return success |
    | anything else | anything else | enqueue separately — never merge |

    That closes local click-spam, which is the actual reported problem. Remote duplicate reloads
    continue to enqueue separately and each gets its own ack; do NOT add a supersede policy, because
    Plan 08's ack vocabulary has no code meaning "superseded."

<notes>
WHAT THIS UNBLOCKS, AND WHAT IT DOES NOT. A reload that acks on rebuild is trustworthy **as a timing
signal** — no verifier will read a half-built world. It does NOT make reload a valid way to verify an
interior edit: axiom 4's kept-root staleness is a correctness problem this plan cannot touch. Plans
05.1-12 and 05.1-15 therefore move to per-building interior refresh and carry
`verification_instrument_changed` blocks; do not "restore" their reload-based steps on the strength of
this plan.

NO HEAD-OF-LINE BLOCKING, and that is a change from the previous draft. The retired barrier held the
whole drain loop for 1-2s; a poll does not. A `LoadScene` queued behind a pending reload proceeds
normally. If you find yourself reasoning about drain-loop starvation here, something has reintroduced
the force-finish.

WHY THE PREVIOUS DESIGN WAS RETIRED, recorded so it is not re-proposed. This plan originally used
`wsGetNodeCount` as a completion barrier, exploiting its `finishLoadNow()` prologue. It worked, but it
paid essentially the entire remaining parse synchronously — one frame advances ~40 ms of a ~3.1 s parse
— i.e. a 1-2 s client freeze on every reload. The provider shipped `wsIsParsePending` (v28) specifically
so we would not have to, and explicitly asked us to drop the workaround. The poll is strictly better:
no freeze, no head-of-line blocking, no fallback-path special-casing, and the ack means the same thing
on every path.

and cell-aware teleport (Plan 05.1-18); `getShutdownPhase`
(`.planning/todos/pending/agent-clean-shutdown-signal.md`); exterior `.ws` node editing.
