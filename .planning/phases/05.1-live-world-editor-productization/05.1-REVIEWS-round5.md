## ⚑ ROUND-5 WORK-LIST — ranked by severity, deduped across reviewers

### V1 — [HIGH] Undo's add-back has no source for `overrideDir`/`readVfs`/`studioDir` — `resolveOverridePair()` is component-local to WorldPanel, unreachable from `RemoveUndoToast` (found independently by Codex, Cursor, AND Opus)

**Where:** `05.1-13-PLAN.md` Task 2 behavior ~333–346, action ~384–393, `<interfaces>` ~215–218; acceptance
criteria ~429–436.

**Defect:** Plan 13's prose and threat model claim "both Remove and Undo resolve through the same helper," but
the actual wiring gives `RemoveUndoToast` only `onUndoComplete: () => void`. The Undo re-add is a disk-writing
`kind='add'` path needing the same deps as Remove (`studioDir`, `overrideDir`, `readVfs`, building), and Plan
13's own `<interfaces>` block states `resolveOverridePair()` is **component-local in `WorldPanel.tsx`, not a
module export** — the toast in a sibling file cannot call it. An executor must invent semantics; the obvious
invention (inline `resolveScanRoot`/`makeReadVfs` in the toast) reintroduces exactly the unguarded
`string | null` second-resolution W3 was filed to eliminate. This makes D-03's undo guarantee (the only guard
on a destructive no-confirm action) unimplementable as written, and unwinds W2 too: `onUndoComplete` fires
only "after the add-back resolves," so if the add-back can't be constructed, `refreshTree()` never fires.

**Minimal fix (all three reviewers converged on the same shape):** Keep `RemoveUndoToast` purely
presentational (like `DeleteUndoToast.tsx:96–101`). Replace the inline add-back with a required prop
`onUndo: (entry: RemovedRowEntry) => void`. `WorldPanel.tsx` owns the whole restore: `resolveOverridePair()`
(null → words-only no-op, same reasoning as Remove) → `restore(id)` → add-back helper with the fresh pair →
`refreshTree()`. Collapse `onUndoComplete` into `onUndo` or keep it as the success-only hook. Extend Task 2's
acceptance criteria so the "mocked `resolveOverridePair()` returns `null` ⇒ zero write calls" assertion covers
the **Undo** path, not only Remove.

### V2 — [HIGH] Plan 14's "(NEW)" diff and Plan 13's Undo refresh are wired to DIFFERENT triggers — Undo never advances `prevTreeRef`, so a restored row gets a delayed, misattributed "(NEW)" on the next unrelated history event (Sonnet)

**Where:** `05.1-14-PLAN.md:257–295` × `05.1-13-PLAN.md:340–344,384,393`; surfaced by `05.1-15-PLAN.md:211–214`.

**Defect:** Plan 14's diff pass + `prevTreeRef` update run only when `worldEditorStore.history.length` grows.
Remove grows history (Plan 13 records a `recordPersistResult` entry); Undo does not — its W2 fix only calls
`refreshTree()` directly. So after an Undo, the tree contains the restored row but `prevTreeRef` still lacks
it. Plan 15 step 8's "no '(NEW)' immediately after Undo" check passes **by accident** (no diff runs in that
window at all). On the next history-growth event anywhere in the session (a later ADD, another Remove, an
arm-failure record), the diff finally runs against the stale snapshot and marks the **already-restored,
unrelated row** as "(NEW)" — the exact failure class W2 was filed to close, reopened one layer down.

**Minimal fix:** Give the diff ONE trigger both paths hit — (a) key the effect off the `tree` reference
itself so EVERY `refreshTree()` (mount/manual/mirror-toggle/Remove/Undo/ADD-confirm) advances `prevTreeRef`
uniformly, or (b) have Undo's handler explicitly invoke the same diff-pass function. Either way, extend Plan
15 step 8 to also verify that a *subsequent, unrelated* history-growth event after the Undo marks only the
genuinely new row. (Note: fix composes with V1 — once WorldPanel owns Undo, option (a) is the natural shape.)

### V3 — [HIGH] Plan 14's "(NEW)" diff has no first-pass seed rule, and the absent-building rule points the wrong way — the WHOLE tree renders "(NEW)" on every World-tab mount and on the first persist in any building (Opus)

**Where:** `05.1-14-PLAN.md` Task 2 behavior, `prevTreeRef` paragraph ~264–285.

**Defect:** `prevTreeRef` has no stated initial value or first-pass rule, and the spec explicitly directs "a
building absent from the previous snapshot contributes an empty count map — ALL of its rows are then genuinely
new." Two reachable sequences fall in: (1) every World-tab mount — Plan 10's mount effect calls
`refreshTree()`, tree goes `[] → populated`, every decoration in the project renders "(NEW)"; dockview
close/reopen re-triggers it. (2) The first persist in a building — per D-05 the tree only contains buildings
with an `edit_*.ilf`, which is the whole layout, so a first plain EDIT makes a building appear with ALL its
rows and every stock row gets tagged "(NEW)". Defeats SC4's two-surface confirm and sketch 021-A Frame 3
("a *single* row marked distinctly as new"). None of Task 2's three existing assertions catches it — all seed
a non-empty prior snapshot.

**Minimal fix:** (1) Initialize `prevTreeRef` to a `null` sentinel; on the first diff pass, seed from the
current tree and mark NOTHING "(NEW)". (2) Reverse the absent-building rule: absent building ⇒ zero "(NEW)"
rows (whole-building appearance is a first observation, not a placement). Optionally stronger (closer to the
sketch's intent): gate the diff on the triggering history entry's `kind === 'add'` so only an ADD persist can
produce a "(NEW)". Add a test: fresh mount over a seeded 2-building/3-decoration tree ⇒ zero "(NEW)" markers.

### V4 — [HIGH] Plan 06's rollback captures bytes on the WRONG branch, re-derives instead of restores, and keys `applied` by building while the mutated resource is a PER-TEMPLATE mirror path — a rollback can rewrite a shared mirror with the wrong building's bytes (Opus; grounded in real source)

**Where:** `05.1-06-PLAN.md` behavior ~292–305, must_have truth line 27, success criteria ~488.

**Defect:** The spec tracks `applied: { buildingId; action: 'wrote'|'deleted'; bytes? }` with "bytes captured
for a **'wrote'** entry" — but a `'wrote'` rollback is a delete (needs no bytes) and a `'deleted'` rollback is
the one that needs the file's actual pre-call bytes, which the spec instead re-derives "from the SAME
`editedIlfBytes` this call already read." Ground truth: `decorationPersist.ts:200` builds the mirror path from
`readInteriorLayoutFileName(stockIff)` — **per stock template, not per building instance** (the code's own log
at `:203` says "per-TEMPLATE"). Two buildings sharing a layout map to ONE mirror file; `reconcileMirrorMode`
iterates buildings. Repro: OFF pass, A and B share a template, C throws. A deletes the shared mirror
(`applied=[{A,'deleted'}]`); B sees it absent, is never recorded; rollback re-writes the mirror from **A's**
`editedIlfBytes` — but if B persisted most recently, the pre-call bytes were B's. Disk now differs from
pre-call state, contradicting the must_have "EVERY building's mirror state on disk is provably unchanged."
Secondarily, keying by `buildingId` lets the rollback loop double-act on one file.

**Minimal fix:** (1) Capture bytes on the `'deleted'` branch by reading the mirror file BEFORE unlinking;
restore those exact bytes. Drop `bytes` from `'wrote'` (inverse = unconditional delete). (2) Key `applied` —
and phase-2 write/delete/skip decisions — on the resolved **stock mirror path**, not `buildingId`. (3) Fix the
W1 acceptance test to assert byte-equality against a fixture whose pre-call mirror content **differs** from
the building's current `editedIlfBytes` — the current test cannot detect this bug.
